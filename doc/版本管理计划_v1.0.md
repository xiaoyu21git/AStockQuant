## 2. 版本号规则

```
v<主版本>.<次版本>.<修订版本>

主版本 (major): 架构级变更，不向后兼容
次版本 (minor): 功能模块闭环完成
修订版本 (patch): 修复/微调，不变功能面
```

## 3. 升级标准

### 3.1 修订版升级 (v0.10.x → v0.10.x+1)

| 条件 | 标准 |
|------|------|
| 触发 | 阻断 bug / 回归问题 / 小范围修补 |
| 变更范围 | 单模块或局部，不变接口语义 |
| 审核 | 编译通过 + 该模块回归通过 |
| 周期 | 按需，不设固定时间 |

### 3.2 次版本升级 (v0.10 → v0.11)

| 条件 | 标准 |
|------|------|
| 触发 | 功能模块闭环验收通过 |
| 变更范围 | 新增页面/服务/链路 |
| 审核 | 完整编译 + 全链路回归 + 基线对账 |
| 周期 | 每完成一个功能闭环，约 2-4 周 |

### 3.3 主版本升级 (v0.x → v1.0)

| 条件 | 标准 |
|------|------|
| 触发 | 4 条主链全部闭环 + PG 迁移完成 |
| 审核 | 全链路回归 + 真源对账 + 主库冻结 |
| 周期 | 0.11.x 全部闭环后 |

## 6. 版本升级执行流程

```
1. 确认当前版本号
2. 对照升级标准逐项检查
3. 编译 + 回归全部通过
4. git tag vX.Y.Z <commit> -m "说明"
5. 更新本文档"当前版本"行
6. 如为次版本: dev 合入 main
7. 如为阻断修复: cherry-pick 到 stable
```

---

## 7. 合入规则

```
实验代码 (stash)
  → dev (编译 + 自测通过)
    → 功能闭环验收
      → main (打 tag)
        → 阻断修复 cherry-pick → stable
```

- **禁止** 未经 dev 验证直接合入 main
- **禁止** main 上做功能开发
- **禁止** 跨版本混合提交
