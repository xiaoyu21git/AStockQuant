# 稳定版与推进版执行清单

## 1. 使用方式

这份清单用于把双线版本策略落到日常执行中：

- 稳定版用于测试、回归和对外验证。
- 推进版用于持续开发、性能优化和架构收口。

两条线不共享同一节奏，也不共享同一变更目标。

## 2. 稳定版执行清单

### 2.1 允许做的事情

- 修复阻断性缺陷。
- 修复回归问题。
- 修复已经验证会破坏主链的小问题。
- 做不改变语义的小范围性能修补。

### 2.2 不允许做的事情

- 不改核心数据结构。
- 不改运行链的主流程。
- 不引入大范围兼容层。
- 不把推进版中的未完成能力直接合入。

### 2.3 稳定版每次发布前必须检查

1. 数据管理主链是否可用。
2. 因子工作台是否还能正常打开和回退。
3. 策略回测是否能完整执行并返回结果。
4. 清洗功能是否能稳定跑通。
5. 关键页面是否无致命错误。
6. 最近一次修复是否已通过回归验证。

### 2.4 稳定版发布原则

- 只接收已验证修复。
- 不接收未完成重构。
- 不接收只在推进版成立的临时实现。
- 发布后保持基线不漂移。

## 3. 推进版执行清单

### 3.1 当前推进重点

- 因子回测统一。
- 数据清洗性能优化。
- 因子服务与回测服务的职责收口。
- PostgreSQL 目标库冻结与迁移准备。
- 风险管理链补齐。
- 交易执行链补齐。

### 3.2 推进版允许做的事情

- 调整内部结构。
- 重构服务职责。
- 补齐缺失模块。
- 优化性能热点。
- 迁移数据存储结构。

### 3.3 推进版每次合并前必须检查

1. 是否影响稳定版已有主链。
2. 是否新增了未收口的兼容分支。
3. 是否已经有最小验证路径。
4. 是否已经有对应回归用例。
5. 是否会改变稳定版当前语义。

### 3.4 推进版发布原则

- 新能力先在推进版落地。
- 验证通过后再同步稳定版。
- 大改动不直接进稳定版。
- 推进版失败不阻断稳定版运行。

## 4. 合入节奏

### 4.1 推荐节奏

1. 先在推进版完成开发。
2. 再做推进版内验证。
3. 验证通过后提交稳定版候选。
4. 稳定版跑回归。
5. 回归通过后正式发布。

### 4.2 合入边界

- 推进版可以快。
- 稳定版必须慢。
- 推进版可以承担试错。
- 稳定版只承担确认结果。

## 5. 版本角色建议

### 5.1 0.9.x

- 作为稳定测试版。
- 只做回归和小修。
- 维持当前可用主链。

### 5.2 0.10.x

- 作为推进开发版。
- 继续做架构收口和性能优化。
- 收敛因子、清洗、数据迁移主线。

### 5.3 1.0.0

- 作为正式稳定版。
- 主链闭环。
- 结果可验证。
- 对外交付。

## 6. 当前最优先事项

1. 稳定版回归基线固定。
2. 推进版继续清洗和回测优化。
3. 因子能力判断与 runtime 统一。
4. PostgreSQL 目标结构冻结。
5. 主数据和时序数据迁移。
6. 风险管理和交易执行链补齐。

## 7. 结论

双线策略的关键不是“同时做两套东西”，而是把职责分开：

- 稳定版负责稳。
- 推进版负责进。

只要这两个目标分开，项目就能在不打断测试的情况下持续推进。
