# 回测架构分离方案

## 问题分析
当前的回测功能存在策略回测和因子回测混合的问题：

### 1. 现有架构问题
- **FactorBacktestService**：虽然名为因子回测，但实际包含了策略回测的逻辑
- **BacktestEngine**：通用的策略回测引擎，但被因子回测服务调用
- **UI混淆**：用户界面没有明确区分因子回测和策略回测

### 2. 概念混淆
- **因子回测**：评估因子的预测能力，通过分组测试、IC/IR计算等
- **策略回测**：基于因子构建交易策略，测试策略的盈利能力

## 架构分离方案

### 1. 服务层分离

#### FactorBacktestService（因子回测服务）
**职责**：
- 因子分组（分位数、等值、自定义）
- IC/IR计算
- 分组绩效统计
- 因子有效性验证

**接口**：
```cpp
class FactorBacktestService {
public:
    // 因子分组回测
    FactorGroupResult runFactorGroupBacktest(const FactorGroupConfig& config);
    
    // IC/IR计算
    ICIRResult calculateICIR(const ICIRConfig& config);
    
    // 因子有效性分析
    FactorValidityResult analyzeFactorValidity(const FactorValidityConfig& config);
};
```

#### StrategyBacktestService（策略回测服务）
**职责**：
- 交易策略回测
- 仓位管理
- 风险控制
- 绩效指标计算

**接口**：
```cpp
class StrategyBacktestService {
public:
    // 策略回测
    StrategyBacktestResult runStrategyBacktest(const StrategyBacktestConfig& config);
    
    // 多策略对比
    std::vector<StrategyBacktestResult> runMultiStrategyBacktest(
        const std::vector<StrategyBacktestConfig>& configs);
    
    // 参数优化
    StrategyOptimizationResult optimizeStrategyParameters(
        const StrategyOptimizationConfig& config);
};
```

### 2. 控制器层分离

#### FactorBacktestController（因子回测控制器）
**职责**：
- 因子分组配置
- IC/IR计算控制
- 因子有效性分析

#### StrategyBacktestController（策略回测控制器）
**职责**：
- 策略配置
- 回测参数设置
- 绩效分析

### 3. UI层分离

#### FactorBacktestPage（因子回测页面）
**功能**：
- 因子选择
- 分组配置
- IC/IR分析
- 分组绩效图表

#### StrategyBacktestPage（策略回测页面）
**功能**：
- 策略选择
- 参数配置
- 回测执行
- 绩效分析图表

## 具体实现步骤

### 阶段一：服务层重构
1. 创建`StrategyBacktestService`类
2. 将策略相关逻辑从`FactorBacktestService`迁移
3. 保持`FactorBacktestService`专注于因子分析

### 阶段二：控制器层重构
1. 创建`StrategyBacktestController`类
2. 更新`FactorBacktestController`专注于因子功能
3. 确保接口清晰分离

### 阶段三：UI层重构
1. 创建`StrategyBacktestPage.qml`
2. 更新`BacktestPage.qml`重命名为`FactorBacktestPage.qml`
3. 明确区分两种回测的UI界面

## 数据流分离

### 因子回测数据流
```
用户选择因子 → 分组配置 → FactorBacktestService → 分组结果 → IC/IR计算 → 结果展示
```

### 策略回测数据流
```
用户选择策略 → 参数配置 → StrategyBacktestService → 回测执行 → 绩效分析 → 结果展示
```

## 迁移计划

### 短期（1-2周）
1. 创建`StrategyBacktestService`基础框架
2. 分离现有的策略回测逻辑
3. 更新CMake配置

### 中期（2-4周）
1. 创建`StrategyBacktestController`
2. 开发`StrategyBacktestPage` UI
3. 测试策略回测功能

### 长期（1-2月）
1. 完善两种回测的集成
2. 添加高级功能（参数优化、多策略对比等）
3. 性能优化和用户体验改进

## 预期收益

### 技术收益
1. **架构清晰**：明确的责任分离
2. **代码可维护性**：减少耦合，提高可测试性
3. **扩展性**：更容易添加新的回测类型

### 业务收益
1. **用户体验**：明确的界面区分，减少用户困惑
2. **功能完整性**：两种回测都能得到充分发展
3. **专业性**：符合量化金融的专业实践

## 风险控制

### 技术风险
1. **兼容性问题**：确保现有功能不受影响
2. **性能影响**：分离后可能增加系统复杂度

### 缓解措施
1. **逐步迁移**：分阶段实施，每阶段都有完整测试
2. **回滚计划**：保留原有代码，确保可以回滚
3. **充分测试**：每个阶段都有完整的单元测试和集成测试

## 总结
通过清晰的架构分离，可以解决当前策略回测和因子回测混合的问题，提高系统的专业性、可维护性和用户体验。
