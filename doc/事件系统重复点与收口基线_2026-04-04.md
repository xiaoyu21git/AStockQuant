# 事件系统重复点与收口基线

更新时间：2026-04-04

## 1. 结论

当前事件系统存在重复，主要集中在两层：

1. 事件基础设施层重复
2. 业务事件命名与语义承载重复

但并非所有相似事件都应合并。像 `market.tick` 与 `trading.market.tick`、`trading.order.updated` 与 `order.fill` 这类事件，当前承担的是不同语义，不应误判为重复。

## 2. 真正重复的部分

### 2.1 EventBus 与 EventSystem 双轨暴露

当前公开接口已经以 `EventBus` 为统一入口：

- `EventBus` 对外声明内部应隐藏 `EventSystem`
- 见 `src/engine/include/Event/EventBus.hpp`

但 `EventSystem` 仍然作为另一套完整公开接口存在：

- `src/engine/include/Event/EventSystem.hpp`

当前业务代码绝大多数直接走全局 `EventBus`：

- `src/app/src/AppBootstrap.cpp`
- `src/ui/bridge/src/StrategyService.cpp`
- `src/ui/bridge/src/MarketDataService.cpp`
- `src/ui/bridge/src/TradeExecutionService.cpp`
- `src/ui/bridge/src/PositionAccountService.cpp`
- `src/ui/bridge/src/RiskMonitorService.cpp`

结论：

- `EventSystem` 更像底层实现与历史接口残留
- `EventBus` 才是当前业务主入口
- 这属于架构级重复

建议基线：

- 业务侧只允许依赖 `EventBus`
- `EventSystem` 仅保留为 `EventBus` 内部实现，或明确标记为底层组件，不再鼓励业务代码直接使用

### 2.2 EventBusImpl 内部双队列/双订阅体系

`EventBusImpl` 里同时维护两套事件承载：

1. 原始 `Event` 体系
2. `EventFormat` 体系

证据：

- 原始队列初始化：`src/engine/src/Event/EventBusImpl.cpp:20`
- 原始通知：`src/engine/src/Event/EventBusImpl.cpp:66`
- EventFormat 队列入队：`src/engine/src/Event/EventBusImpl.cpp:257`
- EventFormat 订阅表：`src/engine/src/Event/EventBusImpl.cpp:311`

结论：

- 这是最核心的基础设施重复点
- 长期会导致两套统计、两套映射、两套调试路径并存

建议基线：

- 统一以 `EventFormat` 为主通道
- 原始 `Event` 仅保留兼容适配层

### 2.3 事件常量定义重复

同一事件名被定义在至少两套头文件中：

1. `EventTypes`：`src/engine/include/Event/EventFormat.hpp`
2. `EventTopic`：`src/engine/include/Event/topic/EventTopic.hpp`

例如：

- `market.tick`
- `order.status`
- `risk.alert`

结论：

- 这属于常量层重复
- 如果继续并行维护，后续极易发生命名漂移

建议基线：

- 保留 `EventTypes`
- `EventTopic` 改为薄别名层，或直接废弃

### 2.4 事件类型映射来源重复且已漂移

当前至少有三处维护事件类型映射：

1. `EventBusImpl` 注册映射：`src/engine/src/Event/EventBusImpl.cpp`
2. `EventBusFactory` 注册与公共映射：`src/engine/src/Event/EventBusFactory.cpp`
3. `EventSystem::convert_event_type` 字符串映射：`src/engine/src/Event/EventSystem.cpp`

而且命名已经不一致：

- `order.fill`
- `order.filled`
- `order_filled`

以及：

- `order.cancel`
- `order.cancelled`
- `order_cancelled`

结论：

- 这已经不是简单重复，而是映射体系分叉
- 后续任何新增事件都会继续放大维护风险

建议基线：

- 建立单一 canonical 注册表
- 其余位置只引用，不再自行扩充字符串映射

## 3. 业务事件层的重复/旁路

### 3.1 订单状态存在两套主事件名

当前订单状态相关主路径如下：

- 交易运行时发布：`trading.order.updated`
  - `src/ui/bridge/src/GmStrategySession.cpp:573`
  - `src/ui/bridge/src/GmStrategySession.cpp:817`
- 前台订单状态消费：`src/ui/bridge/src/PositionAccountService.cpp:280`

但同时还有另一套通用状态事件：

- `order.status`
  - `src/ui/bridge/src/TradeExecutionService.cpp:742`
  - `src/app/src/JujinMarketConnector.cpp:636`

当前未发现对应的主消费方直接订阅 `order.status`。

结论：

- `trading.order.updated` 是当前实盘链路主事件
- `order.status` 当前更像历史通用事件或旁路事件

建议基线：

- 实盘运行时状态统一使用 `trading.order.updated`
- `order.status` 标记为兼容/废弃候选

### 3.2 持仓与账户更新存在两套命名

运行时主路径：

- `trading.position.updated`
  - 发布：`src/ui/bridge/src/GmStrategySession.cpp:973`
  - 订阅：`src/ui/bridge/src/PositionAccountService.cpp:298`
- `trading.account.updated`
  - 发布：`src/ui/bridge/src/GmStrategySession.cpp:948`
  - 订阅：`src/ui/bridge/src/PositionAccountService.cpp:307`

同时 `PositionAccountService` 还会自行再发：

- `position.update`
  - `src/ui/bridge/src/PositionAccountService.cpp:631`
- `account.update`
  - `src/ui/bridge/src/PositionAccountService.cpp:660`

当前未见主链路对 `position.update` / `account.update` 的订阅。

结论：

- 这两类 generic 事件当前不是主业务链路
- 更像对外广播残留或未来扩展位

建议基线：

- 内部交易状态统一保留 `trading.position.updated` / `trading.account.updated`
- `position.update` / `account.update` 列入废弃候选

### 3.3 下单过程命名扩散

当前至少存在以下事件：

- `trading.order.submit.request`
  - `src/ui/bridge/src/TradeExecutionService.cpp:706`
- `trading.order.cancel.request`
  - `src/ui/bridge/src/JujinApi.cpp:263`
- `trading.order.updated`
  - `src/ui/bridge/src/GmStrategySession.cpp:573`

结论：

- 命令事件与状态事件目前没有形成统一前缀规范
- 继续扩展会越来越难区分“请求”“受理”“状态更新”

建议基线：

- 请求类统一放到命令域，例如：
  - `trading.order.submit.request`
  - `trading.order.cancel.request`
- 状态类统一放到状态域，例如：
  - `trading.order.updated`
- 成交增量保留：
  - `order.fill`

当前落地状态：

- `TradeExecutionService` 已改为发布 `trading.order.submit.request`
- `JujinApi` 已改为发布 `trading.order.updated`（`status=SUBMITTED`）/ `trading.order.cancel.request`
- `order.submitted` 与过渡期的 `trading.order.submitted` alias 已从 `EventTypeRegistry` 删除
- `order.submit.request` / `order.cancel.requested` alias 也已从 `EventTypeRegistry` 删除
- 后续新增或回填代码禁止再使用 `order.submit.request`、`order.submitted`、`order.cancel.requested` 这组旧命名

### 3.4 连接状态事件目前偏观测性

当前有：

- `broker.connected`
- `broker.disconnected`

来源：

- `src/ui/bridge/src/JujinApi.cpp:125`
- `src/ui/bridge/src/JujinApi.cpp:143`

当前未发现明确主消费方。

结论：

- 这类事件更像日志/观测事件
- 暂时不构成主链路重复，但需要明确是否继续保留

## 4. 不应合并的分层

### 4.1 `market.tick` 与 `trading.market.tick`

这两个名字相似，但当前承担不同语义：

- `market.tick` / `market.bar`
  - 通用行情域
  - `StrategyService` 直接消费
  - `src/ui/bridge/src/StrategyService.cpp:281`
  - `src/ui/bridge/src/StrategyService.cpp:286`
- `trading.market.tick` / `trading.market.bar`
  - 交易运行时域
  - `MarketDataService` 专门消费
  - `src/ui/bridge/src/MarketDataService.cpp:720`
  - `src/ui/bridge/src/MarketDataService.cpp:729`

结论：

- 这属于“通用行情域”与“交易运行时域”的区分
- 不建议简单合并

### 4.2 `trading.order.updated` 与 `order.fill`

这两个事件也不应合并：

- `trading.order.updated` 表示委托状态快照
- `order.fill` 表示成交增量事件

前台状态维护依赖两者协同：

- `src/ui/bridge/src/PositionAccountService.cpp:280`
- `src/ui/bridge/src/PositionAccountService.cpp:289`

结论：

- 两者是不同业务语义
- 应同时保留

### 4.3 `risk.approval` 与 `risk.reject`

这不是重复，而是一条风控审批流的两个分支：

- 发布端：`src/ui/bridge/src/RiskMonitorService.cpp`
- 订阅端：`src/ui/bridge/src/TradeExecutionService.cpp:402`

结论：

- 不需要合并
- 但可以补一个共用字段如 `decision_type`

## 5. 推荐的收口基线

### 5.1 基础设施层

- 对外统一入口：`EventBus`
- 对内实现：`EventSystem` 仅作为底层组件
- 统一主事件结构：`EventFormat`
- 原始 `Event` 仅保留兼容层

### 5.2 常量层

- 只保留一套 canonical 常量定义，建议用 `EventTypes`
- `EventTopic` 不再作为独立来源扩展字符串

### 5.3 交易域 canonical 事件

建议保留为主线的事件：

- `trading.market.tick`
- `trading.market.bar`
- `trading.order.updated`
- `trading.position.updated`
- `trading.account.updated`
- `trading.execution.report`
- `trading.session.error`

### 5.4 通用 cross-domain 事件

建议保留为跨模块语义事件：

- `market.tick`
- `market.bar`
- `strategy.signal`
- `risk.approval`
- `risk.reject`
- `order.fill`

### 5.5 建议废弃或降级为兼容事件

- `order.status`
- `position.update`
- `account.update`

其中命令型事件已迁移为：

- `trading.order.submit.request`
- `trading.order.updated`（承载 `SUBMITTED` 受理态）
- `trading.order.cancel.request`

## 6. 优先级建议

### P0

1. 收敛事件名映射来源，只保留单一 canonical 注册表
2. 明确 `EventBus` 为唯一业务入口，停止继续扩展 `EventSystem` 直连接口

### P1

1. 将交易主链统一到 `trading.*` 事件族
2. 对 `order.status` / `position.update` / `account.update` 做消费者盘点并标记废弃

### P2

1. 将命令类事件统一到 `trading.order.*.request`
2. 为连接类、诊断类事件补统一命名规范

## 7. 当前判断

当前事件系统不是“完全乱”，而是：

- 主业务链路已经出现了事实标准
- 但标准还没有被提升成唯一基线
- 历史常量、兼容事件、实现层双轨仍在并行存在

因此下一步不应该大面积重写，而应该先按本文件完成：

1. canonical 事件名冻结
2. 重复事件标记为兼容或废弃
3. 基础设施层只保留一条主路径

## 8. 补充规则

1. 不允许使用 QString 做类型判断，QString 仅允许用于调试输出。
2. QVariantMap 仅允许作为 QML 输入参数和返回到 QML 的输出载荷，桥接输出对象名统一为 StrategyManage。
