## C1 EvalRequest.priceProvider 指针生命周期

**歧义**：指针由谁持有？Pipeline 执行期间是否保证有效？

**裁定**：`PriceProviderFactory::createProvider` 返回 `unique_ptr<IPriceProvider>`，由 Facade 栈上持有；`EvalRequest` 携带**裸指针**（观察者语义），仅在同步 `run()` 调用栈内有效。管道不得将该指针缓存至 run() 返回之后；EvalSession 对 provider 的全部使用在 run() 栈帧内完成。所有权链：工厂 → Facade 栈 → 析构。

**依据**：CLAUDE.md 3.1（所有权用智能指针，观察者用裸指针/引用）；主文档 §5 EvalRequest 定义 `const IPriceProvider*`；§9 "EvalSession 持 shared_ptr 禁 .get() 长期持有"同类原则。

**实施影响**：Deps 中 priceProvider 为裸指针 const 成员；禁止出现在任何跨评估周期的缓存结构中。

## C2 probeFactorCrossSection 单股失败语义

**歧义**：`computeFactor(iid, date)` 对某只股票抛异常时，probe 继续下一只还是中断返回 false？

**裁定**：单只 iid 抛异常 → catch，该 iid 计入"无有限值"，**继续下一只**；probe 仅在**全截面无一 iid 产出有限值**时返回 false（→ Error(FactorSnapshotEmpty)）。部分成功返回 true。任何单股异常不中断 probe。

**依据**：主文档 §9 "probe 逐 iid 锚点日调 computeFactor，只返回'全截面是否有有限值'，无'顺带'副作用"；§1 原则②与 §8 异常矩阵既有二分——单股失败 WARN+continue，全链失败 Error 截断。

**实施影响**：probe 内部 per-iid try/catch + WARN 日志 `[Factor] probe 单股异常跳过 iid=...`。

## C3 PositionBook in-flight 豁免期

**歧义**："当日"是评估日还是提交日？周五 14:50 提交、周一簿记校验是否豁免？

**裁定（评审确认口径）**：豁免锚定**提交日**（订单所属评估的交易日），豁免条件 = 偏差可完全归因于**未确认成交的订单**：账本股数 − 券商快照股数 == Σ未确认订单股数（按符号）→ 豁免该部分；偏差超过该归因 → Error(BookKeepingMismatch)。周五 14:50 提交、周一簿记校验：券商快照尚未体现成交（gmsdk 回报未达）→ **仍豁免**；成交已在快照体现后，账本与快照自然对齐，豁免自然消失（转正式）。

**依据**：主文档 §9 "当日已提交未确认成交豁免，次日转正式"——评审确认"次日"指**成交确认后**，非固定一个交易日。

**实施影响**：PositionBook 维护待确认订单集合（提交日+符号+股数）；P5 比对时先按归因扣除待确认订单再判偏差；成交在券商快照体现后（账本与快照对齐）从待确认集合清除。

## C4 LiveViewPreparer 非交易日语义

**歧义**：`isTradingDay(endDate)` 返回 false 时，prepareRows 返回空行集合还是报错？

**裁定**：**no-op，不报错**——输入行集合原样返回（注入的合成行集合为空）。非交易日不存在"当日K线"，无需合成锚点行；下游视图由既有历史行构造，照常评估。评估日非交易日的场景在正常链路不可达（调度器交易判定门控 + 补偿窗口评估对象为上一交易日），此分支为防御性 no-op。

**依据**：主文档 §5 LiveViewPreparer 职责仅"当日合成行注入"；§1 原则②冗余接纳；§6 调度器交易判定。

**实施影响**：prepareRows 开头判交易日，false 时原样返回（零合成行）；不产生任何 Error。

## C5 补单窗口 TriggerPolicy 判定

**歧义**：补单窗口（次日 0:00-9:30）调用时，是否重新执行 TriggerPolicy 判定，还是沿用昨日判定结果仅补执行？

**裁定**：**重新计算**，以**被补单的交易日**（评估日 tradingDay 参数；补单窗口下 = 上一交易日）为基准。TriggerPolicy 是评估日的纯函数（DailyPolicy 交易日计数 / WeeklyPolicy 星期几 / MonthlyPolicy 月内日均仅依赖评估日与日历），补单窗口本质是一次独立评估机会，重算结果与昨日判定必然一致。不持久化、不复用"昨日判定结果"，零新增状态。

**依据**：主文档 §2 轴2 TriggerPolicy 定义；§6.2 补单窗口评估对象为上一交易日（tradingDay 参数即昨日）。

**实施影响**：管道 checkRebalance 阶段对 isCompensation **无特殊分支**——同一代码路径，评估日参数决定判定结果；零新增持久化。

## C6 TriggerPolicy 判定落点与调度器触发关系

**歧义**：主文档 §2"每交易日 14:50 都触发，是否调仓由 TriggerPolicy 判定"与 §6.1 管道 checkRebalance"非调仓日 Skipped"并存——调仓判定在调度器还是管道？若调度器按 policy 跳过触发，"持仓监控每日必跑"（§3）如何兑现？

**裁定（2026-08-14 用户确认，选项"调度器门控+恒触发接线"）**：
1. **调度器消费 isTriggerDay 门控是否调用 evalFn**；Facade 注入 `DailyTriggerPolicy`（每交易日恒触发，与现状逐项一致，§2"每交易日都触发"兑现）。
2. **interval 调仓判定继续留在引擎 checkRebalanceDay**（现状），P2 管道化时迁入管道 checkRebalance（§6.1）。DailyTriggerPolicy 的 intervalDays 参数为 P2 管道接线预留（§2 轴2"现 m_rebalanceInterval 语义"）。
3. 周/月 policy 本次不注入（§12.6 明确不做）。C5 语义自然兑现：policy 门控在 doEvaluate 内、以传入的 tradingDay（补单时=被补单交易日）为基准重算。

**实施影响**：P1 行为变化为零；DailyTriggerPolicy::isTriggerDay 恒 true；policy 未设置（nullptr）时调度器视为恒触发（防御）。

## C7 lastEvalDay 键迁移

**歧义**：P1 门禁要求持久化键含 period 维度（`lastEvalDay.<strategyId>.<period>`），旧键 `eodExecuted.<strategyId>`（P0 保持）如何过渡？升级日重启若落在 14:50 窗口内，失去去重可能重复评估下单（lastBasket 幂等 P2 才上线）。

**裁定（2026-08-14 用户确认，选项"直接换新键不迁移"）**：直接换新键，不读取旧键。旧 `eodExecuted` section 条目留在 app_state.json 中失效（后续维护时人工清理）。升级日运维须知：**避免在 14:50 评估窗口内升级重启**，否则当日可能重复评估（P2 lastBasket 幂等上线后此风险消除）。

**实施影响**：Cron/Interval 调度器持久化统一 `lastEvalDay.<strategyId>.<period后缀>`（后缀 "daily"/"1min"/"5min"，`BarPeriodNaming` 集中定义）；无迁移代码、无旧键兼容读取。

## C3 补充（P1 PositionBook 实现口径）

**在途部分成交**：券商快照部分体现成交时（0 ≤ |偏差| < |Σ在途| 且同向），已体现部分按提交序（FIFO）转正式、在途缩减至剩余偏差；全量体现（偏差=0）则全部转正式。均为 C3"成交在快照体现后转正式"的直接推论。

**在途订单持久化**：flush 载荷含在途订单（符号+股数+提交日），重启后豁免连续有效（周五提交周一未确认仍豁免）。已知限制：被拒/撤单的订单无状态回流，在途永挂 → 豁免长期掩盖真实偏差，需券商成交回报对接后消除（P2 接线时评审）。

**载荷不可解析**：键存在但载荷损坏 → 不采纳券商快照（键存在分支），账本按空处理 → P5 校验报 BookKeepingMismatch 人工介入（保守截断，符合 §8 恢复路径）。

## C8 管道日历能力注入方式（P2/P4 边界）

**歧义**：主文档 §7 迁移表 #1/#2 要求管道 checkRebalance 用 `calendar->previousTradingDay`，但 §5 Deps 列表含 `calendar`，而 §10 将 `ITradingCalendar/DbTradingCalendar` 落地排入 P4；P2 阶段管道如何获得日历能力？

**裁定（P2 用注入函数，P4 换日历类）**：P2 的 Pipeline Deps 注入 `PrevTradingDayFn = std::function<std::string(const std::string&)>`，Facade 接线为现 gmsdk `::get_previous_trading_date` 包装（行为零变化）；`countTradingDaysBetween` 迁入管道，改为基于 PrevTradingDayFn 的私有辅助。P4 落地 DbTradingCalendar 后，同一注入点换源为 `calendar->previousTradingDay`，Deps 增加 `calendar` 成员。管道任何阶段**恒零 gmsdk**（§4）。

**依据**：§4 "管道内零 gmsdk"；§10 顺序理由"P4 必须等 P2 验证通过（先有新承载再拆旧桥）"——日历类前移 P2 将把"实盘日历源替换"与"管道提取"两个风险叠加，违反分阶段风险隔离。

**实施影响**：P2 门禁核查点：管道源码中 grep `get_previous_trading_date` 零命中；P4 门禁核查点：Facade 接线点换 DbTradingCalendar。

## C9 preflight P4/P5 物理落点

**歧义**：§9 要求 preflight 顺序 P1→P2→P3→P4→P5，但 §11.2 日志断言 `preflight 通过` → `[Price] 源=...` 要求取价日志在"preflight 通过"之后；P4（价格空检查）若在 preflight 内执行则断言被破坏。三者（§9 顺序、§11.2 断言、门禁"Preflight 含 P5"）无法同时字面满足。

**裁定（2026-08-14 用户确认，选项"preflight=P1-P3+P5, P4 在取价阶段"）**：
1. `preflight()` 阶段函数含 **P1（视图空）、P2（锚点/因子）、P3（账户空）、P5（簿记校验）**——簿记校验不依赖价格，放取价前。
2. **P4（价格全空→Error(PriceDataEmpty)）判定落在 fetchPrices 阶段**——紧贴取价链，"tick 介入失败"的硬截断与 `[Price] 源=` 逐级诊断日志同处，`preflight 通过` 日志先于取价日志（§11.2 断言成立）。
3. 代价（已接受）：价格空+簿记偏差同时发生时先报 P5——簿记偏差需人工介入，优先暴露更安全。补单窗口日线已完整，P4 几乎不触发，落点对补单无实质影响。

**依据**：§11.2 验证方案日志断言顺序；门禁"Preflight 含 P5"字面；§8 恢复路径"簿记偏差→人工介入"优先级。

**实施影响**：管道阶段注释标明检查点编号（P1/P2/P3/P5 在 preflight，P4 在 fetchPrices）；EvalResult.failedStage 分别取 Preflight / FetchPrices。

## C10 盘中价格链移除 DB 兜底

**歧义**：P0 已落地盘中链 `Fallback{tickCache→liveData→db}`；用户裁定 DB 不参与盘中当日价格兜底。

**裁定（2026-08-14 用户直接裁定）**：**数据库的唯一职责是提供回看数据**（补单/历史）。14:50 评估时当日日K尚未入库（日终同步才写），DB 兜底是伪命题，且会把"tick 没进来"伪装成"有价格"。修正：
- 盘中链（Daily+Intraday）：`Fallback{tickCache → liveData}`（两级均为 tick 实时/聚合数据）
- 补单链（Daily+Compensation）：`Db 单级`（回看历史，不变）
- 盘中价格全空 = tick 介入失败 → P4 Error(PriceDataEmpty) 截断，无 DB 遮掩

**依据**：用户业务语义——正常评估以 tick 聚合当日 K 线（距收盘差 2 根 5 分钟 K 线，tick 对日线影响优先）；后续盘中择时成交（回踩买入）依赖同一条 tick 介入链。

**实施影响**：PriceProviderFactory 盘中链移除 Db 级；主文档 §2/§4/§5/§6.1/§8 中"tickCache→liveData→db"表述同步为"tickCache→liveData"，P4 附注源链同步。
