# 策略创建规则编排页线框与组件拆分方案

更新时间：2026-04-14

## 1. 目标

本方案用于把当前策略创建第二步从“参数配置 + 单阶段单模板绑定”升级为“策略画像 + 分阶段规则编排 + 规则建议侧栏”。

本次方案只定义页面结构、组件职责、状态模型和实施切片，不直接修改运行时规则执行器。

目标有四个：

1. 支持同一阶段配置多个规则，而不是继续限制为一个模板。
2. 支持按策略风格、持有周期、交易频率生成不同的默认规则骨架。
3. 支持把规则分成市场、准入、信号、仓位、调仓、执行、账户风控等阶段。
4. 支持把规则建议从“按关键词查模板”提升为“按当前阶段和当前组角色推荐模板”。

## 2. 当前页面现状

当前页面入口是 src/app/Qml/page/strategies/StrategyCreationPagePro.qml。

当前结构为三步：

1. 第一步：策略类型选择 + 基本信息。
2. 第二步：参数配置 + 规则模板建议。
3. 第三步：创建确认。

其中第二步核心组件为：

1. src/app/Qml/components/Strategy/Creation/StrategyParamConfig.qml
2. src/app/Qml/components/Strategy/Creation/RuleTemplateSuggestionPanel.qml
3. src/app/Qml/utils/StrategyCreationUtils.js

当前问题不在建议服务是否能返回多条结果，而在创建页状态模型仍然按 phase 存一个 binding。这样会导致：

1. 同一阶段只能保留一条规则模板。
2. 规则更像“替换当前阶段模板”，而不是“编排当前阶段规则组合”。
3. selectedStrategyType 主要只影响提示文案，没有真正参与规则骨架生成和建议约束。

### 3.2 窄屏布局

窄屏下建议退化为上下布局：

1. 顶部先展示策略画像。
2. 中间只展示当前选中的阶段卡。
3. 右侧建议栏折叠为底部抽屉。
4. 阶段切换通过顶部 tabs 或横向 chips 完成。

## 4. 页面结构调整建议

### 4.1 第一步保持不动

第一步仍保留当前策略类型选择和基本信息组件：

1. StrategyTypeSelector
2. StrategyBasicInfo

但要增加一个新概念：策略画像。

当前 selectedStrategyType 不删除，而是升级为画像的一个字段。后续画像至少包含：

1. strategyType
2. horizon
3. tradingFrequency
4. marketScope
5. executionStyle

### 4.2 第二步升级为规则编排页

第二步不再只叫“参数配置”，而应变成“参数与规则编排”。

建议结构：

1. 参数区保留在页面顶部，但高度压缩为摘要式。
2. 主区域切换为规则编排器。
3. 高级选项区域继续保留在底部折叠卡中。

参数区在这一版中不再承担规则选择职责。

### 4.3 第三步增加规则摘要

第三步的确认页除了策略概览和参数检查，还应增加“规则编排摘要”。

建议展示：

1. 每个阶段配置了几个规则组。
2. 每个阶段有多少条模板实例。
3. 哪些规则组是必须满足。
4. 哪些规则组是风险否决。

## 5. 新组件拆分

### 5.1 保留组件

以下组件保留，但职责会收敛：

1. StrategyTypeSelector
   仍用于策略类型选择，但后续应输出画像默认值。
2. StrategyBasicInfo
   继续承载名称、说明、标签、股票池等基础信息。
3. RuleTemplateSuggestionPanel
   继续作为建议侧栏基础，但要扩展查询条件和应用目标。

### 5.2 重构组件

1. StrategyParamConfig
   从“参数配置容器”重构成“参数摘要 + 规则编排容器”。

建议拆成：

1. StrategySetupShell.qml
   作为第二步外层容器，负责编排布局。
2. StrategyParameterSummaryCard.qml
   展示参数摘要、校验状态和跳转入口。
3. StrategyRuleComposer.qml
   规则编排主容器，维护 stage 和 group 状态。

### 5.3 新增组件

建议新增以下组件：

1. StrategyProfilePanel.qml
   用于编辑策略画像字段。

职责：
   1. 展示策略风格、持有周期、频率、市场范围、执行方式。
   2. 输出默认规则骨架请求。

2. RuleStageNavigator.qml
   用于阶段导航。

职责：
   1. 展示七个阶段的列表。
   2. 展示每个阶段的组数、规则数、校验状态。

3. RuleStageBoard.qml
   用于展示所有阶段卡或当前阶段卡。

职责：
   1. 按 stage 渲染多个 RuleStageCard。
   2. 响应当前选中阶段切换。

4. RuleStageCard.qml
   表示单个阶段卡。

职责：
   1. 展示阶段标题、说明、风险状态。
   2. 承载多个规则组。

5. RuleGroupCard.qml
   表示一个规则组。

职责：
   1. 展示组名、组角色、逻辑关系、最少命中数。
   2. 容纳多个规则实例。
   3. 支持添加、删除、排序、启用禁用。

6. RuleInstanceChip.qml
   表示一个规则模板实例。

职责：
   1. 展示模板名、标签、就绪状态。
   2. 支持参数覆盖、删除、移动到其他组。

7. RuleComposerSummaryBar.qml
   展示当前规则编排统计信息。

职责：
   1. 展示总组数、总规则数、待补全特征数。
   2. 展示当前策略是偏趋势、偏短线还是偏防守。

8. RuleTemplateDetailPanel.qml
   作为建议侧栏详情面板。

职责：
   1. 展示模板摘要、阶段、角色、周期、更新时间。
   2. 展示缺失特征和应用位置。

## 6. 规则编排状态模型

### 6.1 页面级状态

第二步建议新增一个顶层状态对象：

1. strategyProfile
2. ruleComposerState
3. selectedStageId
4. selectedGroupId
5. selectedSuggestionId

### 6.2 strategyProfile 结构

建议结构：

```text

  strategyType: "trend_following",
  horizon: "swing",
  tradingFrequency: "low_frequency",
  marketScope: "a_share",
  executionStyle: "close_confirmed"

```

建议结构：

```text
      groups: [
        {
          groupId: "market_gate_core",

              instanceId: "rule_001",

              templateName: "情绪退潮冻结模板",
              phase: "market",
              paramsOverride: {},
              weight: 0,
              enabled: true
            }
          ]
        }
      ]
    }
  ]
}
```

## 8. StrategyCreationUtils.js 调整建议

建议在 src/app/Qml/utils/StrategyCreationUtils.js 中新增以下方法：

1. buildDefaultStrategyProfile(strategyType)
   输入策略类型，生成默认画像。

2. buildDefaultRuleComposerSkeleton(strategyProfile)
   输入画像，生成阶段和规则组骨架。

3. getStageDefinitions()
   返回七个阶段的显示名称、说明和排序。

4. getRuleGroupRoleDefinitions()
   返回组角色的名称、颜色和说明。

5. summarizeRuleComposerState(ruleComposerState)
   生成第三步确认页摘要。

6. normalizeRuleComposerState(rawState)
   负责编辑场景和旧结构兼容。

## 9. 与现有字段的兼容策略

当前创建页会在 parameters 中写入：

1. rule_template_binding
2. rule_template_bindings

新方案不应立刻删除旧字段，而应采用兼容写入：

1. 新增 rule_profile 或 rule_composer_state 作为完整编排结构。
2. 继续保留 rule_template_bindings 作为旧链路兼容字段。
3. 选择一个主信号模板写入 rule_template_binding 作为旧接口回退字段。

兼容原则：

1. 老策略打开时，自动转换成单 stage 单 group 单 rule 的编排结构。
2. 新策略保存时，同时写入新结构和旧结构。
3. 等执行器和回测链路完全接入新结构后，再考虑收缩旧字段。

## 11. 组件通信建议

建议统一成以下事件流：

1. StrategyProfilePanel 修改画像。
2. StrategySetupShell 收到画像变化，询问是否重建默认骨架。
3. RuleStageNavigator 负责切换 selectedStageId。
4. RuleStageBoard 根据 selectedStageId 渲染当前阶段卡。
5. RuleGroupCard 发出 addRuleRequested(stageId, groupId)。
6. RuleTemplateSuggestionPanel 根据当前 stageId 和 groupRole 拉取推荐。
7. 用户点击应用后，把模板实例插入当前 group 的 rules。
8. RuleComposerSummaryBar 和第三步确认页同步展示摘要。

## 12. 实施切片

### 第一阶段：UI 骨架

目标：先把第二步从单面板升级为三栏式规则编排页面，不改后端执行逻辑。

建议改动：

1. 新增 StrategyProfilePanel.qml
2. 新增 RuleStageNavigator.qml
3. 新增 RuleStageBoard.qml
4. 新增 RuleStageCard.qml
5. 新增 RuleGroupCard.qml
6. 新增 RuleComposerSummaryBar.qml
7. 重构 StrategyParamConfig.qml 为编排容器

### 第二阶段：建议服务接入画像与组角色

目标：让建议真正按策略画像和规则组上下文推荐。

建议改动：

1. 扩展 RuleTemplateSuggestionPanel 查询参数。
2. 在建议服务链路中支持 stageId、groupRole、strategyProfile。
3. 在目录元数据中补充 horizon、strategy_style、role 等标签。

### 第三阶段：保存结构兼容

目标：把新编排结构写入策略数据，但不打断旧链路。

建议改动：

1. StrategyCreationUtils 增加 ruleComposerState 的构建和归一化方法。
2. 创建页保存时同时写入 rule_profile 和旧绑定字段。
3. 编辑页加载时先优先读取新结构，否则从旧绑定字段自动恢复。

### 第四阶段：执行器接入

目标：让同阶段多规则组合真正参与回测和运行时。

建议改动：

1. 回测链路支持 stage 内多组、多规则组合。
2. 运行时规则评估支持 must_pass、veto、score_boost 等组角色。
3. 回测结果和运行日志输出组级命中明细。

## 13. 最小可用版本建议

如果要尽快交付一个可演示版本，建议最小可用范围如下：

1. 只实现三类阶段：市场环境、入场确认、调仓退出。
2. 只实现三类组角色：must_pass、veto、score_boost。
3. 只支持添加、删除、排序，不先做复杂参数覆盖。
4. 建议侧栏先按 stageId + groupRole + 最近更新时间排序。
5. 保存时同时写入 rule_composer_state 和旧 rule_template_bindings。

这样可以先从当前 signal、rebalance、market 三块平滑演进，而不是一次扩到全部阶段。

## 14. 结论

当前创建页真正缺的不是更多模板，而是规则编排能力。

后续页面重构应遵循以下顺序：

1. 先把策略类型升级为策略画像。
2. 再把第二步升级为阶段编排器。
3. 再把建议侧栏升级为按组推荐。
4. 最后把执行器和回测链路接入同阶段多规则组合。

只要页面状态模型从“phase 对应一个模板”切换为“stage 对应多个 group，每个 group 对应多个 rule”，规则系统就能自然承载长线、短线、隔日 T、高频和波段等不同策略形态。
