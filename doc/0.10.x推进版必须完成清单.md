# 0.10.x 推进版必须完成清单

## 1. 版本目标

0.10.x 的定位不是“再加一堆新功能”，而是把当前已经跑通的主链继续收口，完成从“可用”到“可控、可验证、可迁移”的过渡。

这一版应优先解决三类问题：

- 因子回测与因子服务之间的重复逻辑。
- 数据清洗与回测链路中的性能热点。
- MySQL 到 PostgreSQL 的主库迁移准备。

## 2. 0.10.x 必须完成的功能

### 2.1 因子回测收口

必须完成：

- 因子支持判断统一到单一入口。
- 因子字段需求统一到 runtime 解析结果。
- 因子实例、因子参数、回测执行的真源统一。
- 取消运行时对 bridge 兼容逻辑的依赖。

验收标准：

- 同一因子在选择、预检、回测执行三处的判断结果一致。
- 不再出现“可选但不可跑”或“可跑但无字段”的分裂判断。
- 预检失败能够明确指出原因，而不是只给模糊错误。

### 2.2 数据清洗优化

必须完成：

- 清洗主流程保持可用。
- 清洗中的重复字段解析进一步收口。
- 清洗中的性能热点继续压缩。
- 清洗结果保存、加载和统计保持稳定。

验收标准：

- 清洗可在可接受时间内完成。
- 清洗结果不丢失主数据语义。
- 关键规则执行结果可追踪。

### 2.3 数据源与主库迁移准备

必须完成：

- PostgreSQL 目标 schema 冻结。
- 主数据表、时序表、结果表的职责边界明确。
- `factor_instance.full_config` 继续作为因子参数真源。
- `daily_bar`、`financial_indicator`、`symbol_info` 作为优先迁移对象。

验收标准：

- 能明确哪些表是主数据，哪些表是兼容层。
- 能明确哪些表还留在 MySQL，哪些表准备迁移到 PostgreSQL。
- 迁移脚本具备可回归、可对账的基础能力。

### 2.4 稳定版测试基线

必须完成：

- 保留 0.9.x 稳定测试线。
- 稳定版主链回归不漂移。
- 当前已可用的功能不因推进版开发而退化。

验收标准：

- 回归测试稳定可重复。
- 关键主链不受推进版影响。
- 日常测试可继续依赖稳定版。

## 3. 0.10.x 允许推进的功能

以下内容可以推进，但不能成为阻塞稳定版的条件：

- 风险管理链补齐。
- 交易执行链补齐。
- 组合构建链继续完善。
- 数据质量监控扩展。
- 因子运行快照、回测结果版本化等结构预留。

这些能力可以作为 0.10.x 的扩展任务，但只要影响主链稳定性，就应退回推进版继续收口，不要提前并入稳定版。

## 4. 0.10.x 不应做的事情

- 不应在稳定版继续引入大范围结构变化。
- 不应在多个服务之间继续复制同一套判断逻辑。
- 不应把未完成的兼容层当作长期主链。
- 不应为了赶版本而跳过回归验证。

## 5. 0.10.x 里程碑判断

当以下条件满足时，0.10.x 可以视为完成：

1. 因子回测支持判断统一。
2. 清洗性能热点完成一次收口。
3. PostgreSQL 目标结构冻结并通过文档确认。
4. 主数据迁移脚本具备执行条件。
5. 稳定测试版继续保持可用。

## 6. 结论

0.10.x 的核心任务是“收口和统一”。

如果这一版没有把因子链、清洗链和迁移准备收拢起来，就不算真正进入下一阶段。只有当主链可用、收口明确、迁移可控时，才适合继续往 1.0.0 走。
