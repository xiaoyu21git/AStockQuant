# 回测引擎重建设计规格说明书

更新时间：2026-05-26

## 1. 文档目的

本文用于正式冻结“回测引擎需要重建”这一判断背后的工程边界，避免后续继续在现有字符串、QVariantMap、QMap 语义上做增量堆叠。

本文只回答六件事：

1. 当前回测系统的根问题是什么。
2. 哪些问题属于边界层问题，哪些问题属于引擎主干问题。
3. 新回测引擎必须承担什么职责，不再承担什么职责。
4. 新回测引擎的主合同和层次如何定义。
5. 哪些旧实现可以保留适配，哪些必须删除。
6. 如何分阶段迁移，确保不把现有可用执行能力一起推翻。

## 2. 当前结论

当前系统的真正问题，不只是页面层或 bridge 层存在大量字符串，而是回测引擎所依赖的上游装配语义、本体语义和结果语义都没有被完整冻结成一套强类型合同。

当前仓库已经出现了一批正确方向的雏形：

1. [src/domain/backtest/include/BacktestRequest.h](../src/domain/backtest/include/BacktestRequest.h)
2. [src/domain/backtest/include/BacktestResultDto.h](../src/domain/backtest/include/BacktestResultDto.h)
3. [src/application/backtest/include/BacktestRequestFactory.h](../src/application/backtest/include/BacktestRequestFactory.h)
4. [src/application/backtest/include/BacktestEngineGateway.h](../src/application/backtest/include/BacktestEngineGateway.h)

但这些类型和接口还没有成为“全链唯一真源”。现状仍然是：

1. QML 页面保存大量散装状态。
2. bridge/controller 继续承担业务装配和兼容归一化。
3. service 层继续读写 QVariantMap / JSON / 字符串字段。
4. 结果回写链继续依赖 JS payload 拼装。
5. 引擎虽然开始接 typed request/result，但外围仍然把它当成“typed 壳 + map 真实语义”的混合系统来用。

因此，后续不应再把目标定义为“修一修当前策略回测”，而应定义为：

重建一套能够承载策略回测、因子执行预览、规则模板执行摘要、多频率策略分层和后续真实交易联动的统一回测引擎主干。

## 3. 当前系统的结构性问题

### 3.1 主问题

当前系统存在五类结构性问题：

| 问题类别 | 当前表现 | 后果 |
| :--- | :--- | :--- |
| 主合同不完整 | typed request/result 已出现，但还没有成为唯一入口和唯一出口 | 上层仍能绕过 typed 合同继续直传 map |
| 字符串承载业务语义 | execution kind、strategy subtype、factor overlay、股票池、结果字段仍大量靠字符串键表达 | 编译器无法保护真实语义 |
| 分层职责漂移 | QML、bridge、service、repository 都在做业务结构归一化 | 扩展时无法判断正确落点 |
| 研究与执行混用 | 因子研究、策略执行、结果展示、持久化快照经常混在一个对象里 | 新需求容易把旧语义污染得更严重 |
| 结果链不闭合 | 结果生成、结果展示、结果回写、结果恢复不是同一 typed 主链 | 回测可跑，但长期不可维护 |

### 3.2 已发现的具体症状

当前已经明确暴露过的症状包括：

1. 因子导入上下文和真实 backtestSymbolPool 一度没有正式持久化。
2. 策略回测执行分发曾依赖 strategy_type / subtype 字符串猜测，而不是显式 execution kind。
3. factor overlay 已经进入策略回测，但仍然主要影响选股，不具备完整的分层频率合同。
4. 股票池、规则模板、市场环境、执行参数、结果回写仍然在多个 map 和快照对象中并行出现。
5. 当前系统尚不具备“低频定池、中频精选、高频执行优化”的正式引擎分层能力。

## 4. 重建目标

新回测引擎必须满足下面四个总目标：

1. 让引擎本体只认强类型合同，不再认 QVariantMap / QMap / 字符串别名作为业务真源。
2. 让研究、执行、展示、持久化四类语义彻底拆开，各自只通过显式 DTO 连接。
3. 让策略回测、因子执行预览、规则模板执行摘要共享同一套执行主干，而不是各自再拼第二套语义。
4. 让未来的多频率、多层级、多入口策略系统可以在当前主干上继续扩展，而不是再次回到临时 map 结构。

## 5. 重建范围

### 5.1 必须重建

以下部分属于本次回测引擎重建的核心范围：

1. 回测请求主合同。
2. 回测结果主合同。
3. 策略装配到回测请求的工厂层。
4. 回测应用服务层。
5. 回测引擎网关层。
6. 执行运行时主流程。
7. 结果回写与恢复主链。
8. 展示 adapter 的单向投影层。

### 5.2 原则上保留

以下部分原则上不做爆炸式推翻，但必须适配新合同：

1. 行情数据提供器。
2. 因子数据提供器。
3. 现有撮合与绩效计算内核中可复用的计算逻辑。
4. 线程池和后台执行框架。
5. EventBus 与基础设施。

## 6. 新引擎的层次边界

新引擎必须按下面七层收口：

| 层级 | 职责 | 禁止行为 |
| :--- | :--- | :--- |
| 展示层 | 收集用户输入、显示结果 | 禁止保存真实业务语义；禁止构造散装 map 作为业务真源 |
| bridge 层 | 展示模型与 typed DTO 之间的边界适配 | 禁止做业务归一化；禁止吸收兼容逻辑 |
| 应用装配层 | 把 StrategyAggregate / Factor context 装配成 BacktestRequest | 禁止直接访问 QML 状态对象 |
| 应用服务层 | 校验请求、调度引擎、管理任务与缓存 | 禁止自行解释页面字段名 |
| 引擎网关层 | 隔离回测引擎实现细节，对外只暴露 execute/runBatch | 禁止把底层 engine::BacktestResult 直接外泄 |
| 执行运行时层 | 统一处理 universe、risk、execution、rule template、factor overlay | 禁止读取 QVariantMap / JSON 字段 |
| 持久化与展示投影层 | BacktestResultDto 写库、读库、投影展示 | 禁止回写业务真源到展示字段 |

## 7. 新引擎的核心主合同

### 7.1 唯一输入合同

新引擎唯一输入合同为 BacktestRequest 或同等 typed 对象。它至少必须包含下面九类信息：

1. strategyIdentity
2. strategySpec
3. universeSpec
4. marketEnvironmentSpec
5. costSpec
6. riskSpec
7. executionSpec
8. factorOverlaySpec
9. runtimeOptions + dateWindow

约束：

1. 引擎内部不得再从 strategy_type、sub_type、symbol_pool 这类字符串字段反推主语义。
2. 若上游仍有旧 map 结构，必须先进入单一 adapter 层，再转成 BacktestRequest。
3. 任何缺少关键字段的请求都必须直接失败，不允许默认猜测。

### 7.2 唯一输出合同

新引擎唯一输出合同为 BacktestResultDto 或同等 typed 对象。它至少必须包含：

1. runMetadata
2. configSnapshot
3. performanceSummary
4. tradeStatistics
5. riskMetrics
6. timeSeries
7. tradeRecords
8. universeResolutionSummary
9. ruleTemplateSummary
10. diagnostics

约束：

1. 展示层只能消费投影后的 display DTO，不允许再直接消费 engine 原始对象。
2. 结果回写链必须从 BacktestResultDto 写入，不再从 JS 拼装 payload 反向生成业务结果。
3. 历史记录恢复也必须从同一 typed result 主链恢复，而不是从展示快照反推。

## 8. 新引擎必须冻结的规则边界

### 8.1 研究与执行边界

1. 因子研究结果不等于策略执行结果。
2. 因子股票池不等于策略最终成交集合。
3. 因子层负责研究排序与候选范围，策略层负责规则、仓位、调仓、执行和风险。

### 8.2 股票池边界

1. universeSpec 必须明确区分 explicitSymbols、resolvedSymbols、backtestSymbolPool、liveSymbolPool 等对象的语义。
2. 高频执行层不得越过中低频已经确定的 backtestSymbolPool。
3. 引擎内部不得再混用 symbol_pool、symbolPool、backtestSymbolPool 多套真源。

### 8.3 执行边界

1. executionSpec 只定义执行制度与调仓制度，不定义研究信号。
2. factorOverlaySpec 只定义因子如何参与策略选股，不直接承担资金预算分配的新语义，除非单独引入 typed 资金配置合同。
3. 默认等权持仓和按因子预算持仓必须是两种显式 execution mode，禁止模糊混用。

### 8.4 结果边界

1. 结果展示字段不得回流为业务真源。
2. QML 的 latestBacktest / displayResult 只能作为展示态，不得再作为持久层恢复依据。
3. 规则模板摘要、风险诊断、覆盖率摘要都应作为 typed diagnostics/summary 输出，而不是临时拼字段。

## 9. 旧实现的处理原则

### 9.1 必须删除的模式

以下模式后续必须被明确绞杀：

1. 引擎直接读取 QVariantMap。
2. controller/service 内多处重复做字段别名兼容。
3. JS 侧拼出完整业务 payload，再交给 C++ 写库。
4. 结果回写依赖展示快照倒推业务字段。
5. 通过字符串 subtype 猜测执行分支。

### 9.2 允许临时保留的模式

以下模式允许阶段性保留，但必须集中在单点：

1. 旧 Strategy/QML 结构到 typed request 的 adapter。
2. 旧 StrategyBacktestResult 到 BacktestResultDto 的转换层。
3. 数据库历史旧字段到新 typed 模型的迁移 adapter。

约束：

1. 所有兼容读取都必须集中在单一 adapter 层。
2. 兼容层不得继续向新层传播旧字段名。

## 10. 建议的目标模块结构

建议后续按下面模块组织：

1. domain/backtest/model
   1. 放 BacktestRequest、BacktestResultDto、ExecutionSpec、RiskSpec、UniverseSpec 等核心类型。
2. application/backtest/assembler
   1. 放 RequestFactory、旧结构 adapter、参数校验器。
3. application/backtest/service
   1. 放 BacktestApplicationService、任务调度、缓存策略。
4. application/backtest/gateway
   1. 放 BacktestEngineGateway 及其实现。
5. domain/backtest/runtime
   1. 放统一执行运行时、rule template 执行、factor overlay 执行、risk gating。
6. infrastructure/backtest/persistence
   1. 放 result repository、history snapshot repository。
7. ui/bridge/backtest
   1. 放展示 adapter 与边界映射，不再放业务主装配。

## 11. 分阶段迁移路线

### 阶段一：冻结主合同

目标：

1. 冻结 BacktestRequest 和 BacktestResultDto 字段。
2. 冻结 StrategyAggregate 到 BacktestRequest 的唯一工厂入口。
3. 冻结展示投影只能从 BacktestResultDto 单向生成。

阶段结果：

1. 新旧实现并行，但 typed 合同成为唯一新真源。

### 阶段二：桥接层瘦身

目标：

1. StrategyBacktestController 不再承担业务归一化。
2. StrategyService 不再拼装回测业务结构。
3. JS 结果 payload 缩减为展示交互辅助，不再承担正式回写语义。

阶段结果：

1. 上层 map 逻辑被压缩到单点 adapter。

### 阶段三：执行运行时替换

目标：

1. 统一 execution runtime 主流程。
2. 把 factor overlay、rule template、risk gating、universe resolution 放进同一 runtime 合同。
3. 让 preview、strategy backtest、factor-to-strategy preview 共用同一运行时骨架。

阶段结果：

1. 引擎主干不再依赖旧策略页面语义。

### 阶段四：回写与恢复链收口

目标：

1. 回测结果只从 BacktestResultDto 写库。
2. 策略历史恢复只从 typed result/history 恢复。
3. 删除旧展示快照反推业务字段的路径。

阶段结果：

1. 结果链正式闭合。

## 12. 验收标准

回测引擎重建完成后，至少必须满足下面标准：

1. 引擎内部主链不再出现 QVariantMap 业务真源读取。
2. execution kind、market environment、universe、factor overlay、risk、result summary 都有 typed 合同。
3. 策略回测和执行预览共用同一 request/result 主干。
4. 结果回写链不再依赖 JS 拼装 payload 作为真源。
5. 缺失关键元信息时直接失败，不再靠字符串回退继续运行。
6. 新增一种执行模式或一种频率分层能力时，不需要跨 QML、bridge、service、repository 四层同时补字符串键。

## 13. 最终结论

后续不应继续把回测系统理解为“当前策略回测页面 + 若干 service 的局部修补对象”，而应明确把它定义为一套统一的回测引擎平台。

正确方向不是简单删除所有旧代码，而是：

1. 先冻结新的 typed 主合同。
2. 再把 bridge、service、repository 周围的 map/string 语义逐层拔掉。
3. 最后把现有执行内核中有价值的部分吸收到新引擎主干里。

只有这样，后续更大的上层建筑，例如多频率策略、策略族、组合约束、执行制度档案、规则模板分层和真实交易联动，才有稳定底座可承载。
