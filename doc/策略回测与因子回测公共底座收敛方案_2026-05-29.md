# 策略回测与因子回测公共底座收敛方案

## 1. 文档目的

本文档用于替代“继续在策略回测链路上局部补细节”的推进方式，先给出一份可执行的收敛方案，再按阶段逐步把当前实现推向正确架构。

本文档只回答四个问题：

1. 当前策略回测与因子回测各自拥有什么能力。
2. 哪些能力应该复用，哪些能力不应该复用。
3. 正确目标架构应该是什么，而不是什么。
4. 后续代码应该按什么顺序收敛，避免继续产生第二套底座。

本文档不是口号性意见，而是基于当前源码事实和既有设计文档给出的修正方案。

## 2. 当前事实判断

### 2.1 现有冻结设计文档的方向并不完全正确

现有 [通用可扩展策略回测引擎——架构设计文档_2026-05-26.md](通用可扩展策略回测引擎——架构设计文档_2026-05-26.md) 把策略回测引擎描述成一套独立 typed engine，并将 `IMarketDataCache` 视为策略引擎外部依赖。

这个方向有一半是对的：

1. 策略决策、规则检查、执行模拟、组合优化，确实应保持独立 typed engine。
2. 这些行为层不应回退到旧的因子回测服务链。

但这个方向也有一半是不完整的：

1. 当前仓库里最接近“公共回测数据底座”的能力，实际上已经主要沉在因子回测链中。
2. 如果策略回测继续围绕 `HistoricalMarketDataCache` 自己长出一套市场上下文、逐日股票池、HistoricalView 语义，那么仓库会长期并存两套底座。

因此，现有冻结设计文档需要补一份“底座收敛修正”，否则会在实现层持续诱导出第二套公共能力。

### 2.2 当前源码里已经出现两套市场上下文底座

当前策略回测主链：

1. `StrategyBacktestRuntimeHost`
2. `HistoricalMarketDataCache`
3. `StrategyBacktestEngine`

当前因子回测主链：

1. `FactorBacktestController`
2. `FactorBacktestExecutor`
3. `prepareCachedExecutionMarketContext`
4. `HistoricalView` / `ArrowMarketData` / `symbolsByDate`

两边当前都在处理以下同类问题：

1. 缓存集行过滤与标准化。
2. 交易日序列提取。
3. 某日可交易 symbol 集合。
4. HistoricalView 或等价历史视图。
5. 因子运行时对逐日 symbol 集合的消费。

这已经不是“上层差异实现”，而是“公共底座出现双实现”。

### 2.3 当前更成熟的底座不在策略回测链，而在因子回测链

从当前源码事实看，因子回测链已经具备以下能力：

1. `prepareCachedExecutionMarketContext` 已能构建 tradeDates。
2. 已能构建 `symbolsByDate`。
3. 已能构建 `allowedSymbolsByDate`。
4. 已能在 Arrow 与 row-based 视图之间切换。
5. `HistoricalView` 已经成为大量因子运行时的唯一数据读取入口。
6. 多个因子已经明确禁止数据库回退，要求引擎提供 HistoricalView。

相比之下，策略回测当前的 `HistoricalMarketDataCache` 仍停留在：

1. 按 `TradingDayIndex + SymbolId` 拉取单日 KLine。
2. 用 `sliceForDay` 组装当天 bar 集。
3. 用 `FactorSnapshotProvider` 单独拉取因子快照。

这说明：

1. 策略回测 typed engine 的行为层是新的。
2. 但其数据准备底座并不比因子回测更成熟。
3. 若继续扩写 `HistoricalMarketDataCache`，本质上是在重复发明因子回测已经拥有的大块能力。

## 3. 架构判断

### 3.1 正确目标不是“策略回测直接调用整个因子回测执行器”

虽然策略回测应该复用因子回测的大部分功能，但这不等于让策略回测直接建立在 `FactorBacktestExecutor` 整个类之上。

原因如下：

1. `FactorBacktestExecutor` 内部混有因子研究专属职责，例如 IC、IR、分组收益、future return、研究绩效汇总。
2. 这些研究职责不属于策略回测执行底座。
3. 如果策略回测直接嵌套 `FactorBacktestExecutor`，会把研究路径和执行路径再次混层。

因此，正确做法不是“策略引擎复用整个因子回测执行器”，而是：

1. 识别并抽出因子回测里已经成熟的公共底座。
2. 让策略回测和因子回测都建立在这套公共底座之上。

### 3.2 正确目标是“单一公共回测数据底座 + 两个上层执行器”

建议目标架构如下：

1. 公共回测数据底座
2. 因子研究执行器
3. 策略执行回测引擎

其中：

1. 公共底座负责缓存集标准化、交易日索引、逐日可交易 symbol、HistoricalView、Arrow/row 视图、按日股票池收缩、公共字段读取合同。
2. 因子研究执行器只负责因子计算、IC/IR、分组、研究指标。
3. 策略执行回测引擎只负责规则、分层、执行、持仓、订单、权益与结果合同。

即：

1. 公共底座只能有一份。
2. 上层执行器可以有两个。

### 3.3 当前应复用与不应复用的边界

应复用的内容：

1. 缓存集行标准化与行过滤。
2. 交易日索引构建。
3. `symbolsByDate` 和 `allowedSymbolsByDate`。
4. HistoricalView 抽象。
5. Arrow 和 row-based 数据视图。
6. 缓存集按日可交易 universe 解析。
7. 数据字段存在性、价格序列、截面数据的统一读取语义。

不应复用的内容：

1. 因子回测的 IC、IR、group return、research metrics。
2. 因子研究任务调度与 batch executor 组织方式。
3. 策略回测的规则检查、执行模拟、组合优化、调仓逻辑。
4. 策略回测自己的 typed result contract。

这条边界是本文档最重要的判断。

## 4. 当前代码收敛方向判断

### 4.1 当前已经做过的局部修正只能视为临时止血

最近已经做过两类局部修正：

1. 将缓存集可回测 symbol 提取逻辑抽到 `FactorBacktestCachedBarUtils.h`，策略与因子共同复用。
2. 在 `HistoricalMarketDataCache` 中对缓存集模式引入按日收缩的临时行为，避免后续交易日少一只股票就整天失败。

这些修正是必要的，但只能视为止血，不应继续扩展成长期方案。

原因：

1. 这仍然发生在策略链本地。
2. `HistoricalMarketDataCache` 仍然不知道 tradeDates、HistoricalView、跨日 symbol 视图，只是开始承担这些语义的局部碎片。
3. 如果继续沿这条线补，会把“过渡层”补成“第二套底座”。

### 4.2 从现在开始，策略链上不应再继续扩写新的底座语义

从本文档生效开始，以下方向禁止继续作为主要推进路径：

1. 继续在 `HistoricalMarketDataCache` 里补更多缓存集逐日语义。
2. 继续在策略回测 runtime 里自行生长 HistoricalView 等价结构。
3. 继续把因子快照准备、逐日股票池、数据字段视图分别在策略侧再做一份 typed 包装。

允许继续做的只有两类事情：

1. 正确性止血修复。
2. 为后续底座抽取做最小桥接改造。

## 5. 收敛后的目标分层

建议新增一个“公共回测数据底座层”，位置可以是新的 domain 子模块，也可以是从 factor_system 中拆出的纯底座静态库。

该层只承载下列职责：

1. `CachedMarketIndex`
2. `ExecutionMarketContext` 中与研究无关的公共部分
3. `HistoricalView`
4. `CachedRowHistoricalView`
5. `DirectCachedHistoricalView`
6. Arrow / row 数据统一视图适配
7. `tradeDates`
8. `symbolsByDate`
9. `allowedSymbolsByDate`
10. 缓存集可回测 universe 提取
11. 公共行过滤与标准化 helper

策略回测上层只应保留：

1. `BacktestRequest`
2. `StrategyBacktestEngine`
3. `LayerExecutionPipeline`
4. `IRuleChecker`
5. `IExecutionSimulator`
6. `IPortfolioOptimizer`
7. `IExecutionPolicyStrategy`
8. 策略结果与诊断装配

因子回测上层只应保留：

1. `FactorBacktestExecutor` 的研究计算部分
2. 因子批量执行与研究汇总
3. 因子研究合同与展示结果

## 6. 分阶段迁移方案

### 阶段 0：冻结细节漂移

目标：停止继续在策略链上长新底座。

要求：

1. `HistoricalMarketDataCache` 的现有修复只保留正确性意义，不再继续扩写新语义。
2. 新增需求先落文档，不再以“先补细节再回头整理”的方式推进。
3. 所有后续改动必须显式标注属于哪一阶段。

### 阶段 1：抽取公共回测数据底座

目标：从因子回测链中抽出真正应被复用的公共能力。

工作项：

1. 将 `CachedMarketIndex`、`HistoricalView`、逐日 symbol 视图相关结构从 `FactorBacktestExecutor` 拆出。
2. 把 `CachedRowHistoricalView`、`DirectCachedHistoricalView` 从 executor 内部类迁出。
3. 为公共底座建立最小 typed 接口，不暴露因子研究语义。
4. 保留现有行为，不改变因子回测结果合同。

阶段完成条件：

1. `FactorBacktestExecutor` 不再自己定义公共底座结构。
2. 公共底座可以独立编译、独立测试。

### 阶段 2：先让因子回测完全站到新底座上

目标：先在原生拥有者一侧完成切换，确保公共底座定义正确。

工作项：

1. `FactorBacktestExecutor` 全量改为消费新的公共底座模块。
2. 因子回测当前 HistoricalView 路径行为保持不变。
3. 以现有因子回归测试验证抽取未改语义。

阶段完成条件：

1. 因子回测链不再拥有底座私有实现。
2. 历史视图、逐日股票池、缓存索引只保留一份真源。

### 阶段 3：让策略回测改为消费公共底座

目标：把策略回测从“单日 KLine slice 缓存器”迁到“公共历史视图底座 + 策略行为层”。

工作项：

1. 定义策略侧使用的公共市场上下文接口。
2. 将 `HistoricalMarketDataCache` 收缩为底座适配器或删除。
3. 让策略引擎的 `IMarketDataCache` 只描述策略行为层真正需要的数据切片，不再自行承担底座构建。
4. 因子快照准备尽量对齐公共底座视图，不再单独走另一套 universe 语义。

阶段完成条件：

1. 策略回测不再拥有独立的缓存集逐日股票池真源。
2. `HistoricalMarketDataCache` 若保留，也只承担适配职责，不再长底座逻辑。

### 阶段 4：删除重复实现和过渡逻辑

目标：去掉所有临时桥接和双口径。

工作项：

1. 删除策略侧已被公共底座替代的缓存集解析逻辑。
2. 删除 executor 内已被迁出的历史视图内嵌实现。
3. 清理只为过渡存在的 helper 和临时标记字段。

阶段完成条件：

1. 仓库中只存在一套回测数据底座。
2. 因子回测与策略回测只在上层执行语义不同。

## 7. 本方案对既有文档的修正结论

本文档对既有设计文档做如下修正：

1. 保留“策略回测 typed engine 独立”的结论。
2. 修正“策略回测数据底座可以独立实现”的隐含推进方向。
3. 明确：策略回测应复用因子回测已验证过的大部分公共数据能力，但不应直接复用整个因子研究执行器。

换句话说：

1. 要复用的是底座，不是把研究器硬套成执行器。
2. 要分离的是上层行为，不是再分裂一份公共数据语义。

## 8. 风险与反例

### 8.1 反例一：继续补 `HistoricalMarketDataCache`

如果继续在策略侧补如下能力：

1. tradeDates
2. symbolsByDate
3. HistoricalView
4. 缓存字段可用性

那么最终只会得到“策略版 FactorBacktestExecutor 底座”，这与收敛目标相反。

### 8.2 反例二：让策略直接调用 `FactorBacktestExecutor`

如果让策略回测直接建立在 `FactorBacktestExecutor` 上：

1. 会把因子研究指标、future return、group backtest 逻辑混入策略执行域。
2. 会破坏当前 typed 策略引擎的职责边界。

这同样不是正确方向。

## 9. 下一步执行建议

在本文档确认后，下一步不再继续补策略侧运行细节，而是只做下面两件事：

1. 先形成“公共回测数据底座”的类型草图和模块边界文档。
2. 再开始阶段 1 的结构抽取。

在阶段 1 完成前，策略回测只允许做阻断式正确性修复，不再扩写新的底座能力。
