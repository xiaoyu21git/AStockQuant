# 版本规划与双线发布策略

## 1. 目的

当前工程已经进入“主链可用、继续收口”的阶段。为了避免测试环境被持续改动影响，同时让研发能够继续推进未完成能力，建议采用双线版本策略：

- 稳定版负责回归测试、日常验证和对外可用。
- 推进版负责架构收口、性能优化、数据迁移和功能补齐。

这不是简单的分支划分，而是把“稳定可测”和“持续演进”拆成两条明确职责不同的版本线。

## 2. 当前阶段判断

根据现有进度文档和代码状态，工程当前更接近以下阶段：

- 核心主链已跑通。
- 数据管理、策略回测、事件系统、因子基础链路已可用。
- 因子系统、数据清洗、数据库迁移、风险与交易执行仍在收口过程中。
- 整体不适合直接定义为 1.0 成熟版，但已经不再是原型阶段。

因此当前更适合的定位是：

- 0.9.x：稳定收口期。
- 0.10.x：推进演进期。
- 1.0.0：稳定交付期。

## 3. 双线版本定义

### 3.1 稳定版

稳定版只承担“当前可用功能”的稳定运行和回归验证。

允许：

- 阻断性缺陷修复。
- 回归问题修正。
- 小范围性能修补。
- 不改变接口语义的安全修复。

禁止：

- 数据结构大改。
- 运行链重构。
- 依赖关系重排。
- 为新功能引入大范围兼容层。

用途：

- 日常测试。
- 演示验证。
- 回归基线。
- 临时稳定交付。

### 3.2 推进版

推进版承担继续开发和架构演进任务。

允许：

- 因子回测统一。
- 数据清洗性能优化。
- PostgreSQL 迁移。
- 风险管理链补齐。
- 交易执行链补齐。
- 结果域、审计域、迁移域设计。

用途：

- 新能力开发。
- 架构收口。
- 数据真源统一。
- 性能优化。
- 新版本预研。

## 4. 合入规则

1. 所有新功能先进入推进版。
2. 推进版经过验证后，再择机合入稳定版。
3. 稳定版只接收已验证修复，不接收未消化的大改动。
4. 稳定版出现问题时，优先做回归修复，不在稳定线上继续扩功能。
5. 推进版如果引入大范围改动，应保持独立验证，不影响稳定版节奏。

## 5. 版本编号建议

建议按以下节奏命名：

- 0.9.x：稳定测试版。
- 0.10.x：推进开发版。
- 1.0.0：正式稳定版。

### 5.1 0.9.x 的职责

- 保持可运行。
- 保持可回归。
- 保持可演示。
- 作为测试基线。

### 5.2 0.10.x 的职责

- 继续推进清洗和回测优化。
- 统一因子 runtime 和字段需求。
- 收口数据服务与因子服务之间的重复逻辑。
- 推进数据库迁移和 schema 冻结。

### 5.3 1.0.0 的职责

- 数据管理、因子分析、策略回测三条主链稳定闭环。
- 核心功能经过回归验证。
- 具备相对稳定的交付属性。

## 6. 推荐里程碑

### 6.1 近期目标

- 固化稳定版回归基线。
- 保持当前主链可用。
- 继续修正清洗和回测热点。
- 不在稳定版继续引入新结构。

### 6.2 中期目标

- 完成因子回测和清洗链的统一。
- 冻结 PostgreSQL 目标结构。
- 开始主数据迁移和对账。
- 将结果域纳入正式设计。

### 6.3 长期目标

- 完成风险管理和交易执行链。
- 建立可追溯的数据质量体系。
- 形成稳定产品版本 1.0 及后续演进版本。

## 7. 建议的执行方式

### 7.1 稳定版执行方式

- 只修 bug。
- 只做小修小补。
- 每次改动都走回归验证。
- 以“不破坏现有主链”为硬约束。

### 7.2 推进版执行方式

- 按模块推进。
- 以目标闭环为主，不追求一次性全完成。
- 每完成一个收口点就做一次验证。
- 通过后再合入稳定版。

## 8. 当前最合适的推进顺序

1. 稳定版保持可用并锁定回归基线。
2. 推进版继续清洗和回测性能优化。
3. 统一因子能力判断、字段需求和 runtime。
4. 冻结 PostgreSQL 目标 schema。
5. 迁移主数据和时序数据。
6. 补齐风险管理和交易执行链。

## 9. 结论

当前工程最适合采用“稳定版 + 推进版”双线策略。

- 稳定版保障测试和验证不被打断。
- 推进版保障研发持续推进。
- 两条线各自承担不同职责，避免互相拖累。

这套策略比单线滚动更适合当前阶段，也更符合项目现在“主链已通、继续收口”的状态。
