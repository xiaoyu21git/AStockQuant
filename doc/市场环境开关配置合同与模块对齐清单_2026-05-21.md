# 市场环境开关配置合同与模块对齐清单

> 说明：本文里关于旧策略回测配置链的表述需要按当前代码现状理解。旧 `StrategyBacktestService` 已删除，当前策略回测相关锚点应以 `BacktestRequest`、`StrategySnapshotTypes`、`BacktestRequestFactory` 和运行时规则链为准。

## 1. 目标

本文承接 [doc/市场环境开关与因子策略影响总纲_2026-05-21.md](./市场环境开关与因子策略影响总纲_2026-05-21.md)，回答更具体的问题：

1. 市场环境开关应该落在哪些配置合同里。
2. 因子回测、策略回测、运行时规则三条链各自需要新增什么字段。
3. 后续模块级对齐时，应该先改哪几个入口。

本文只定义配置合同和模块落点，不展开到具体代码实现细节。

## 2. 当前锚点

当前工程里，市场环境相关信息是分散存在的：

1. 因子回测链目前通过 `backtestRuntimeParams` 透传运行参数，再在控制器里组装 `factor::BacktestConfig`，但没有正式的市场环境字段，见 [src/ui/bridge/src/FactorBacktestController.cpp](../src/ui/bridge/src/FactorBacktestController.cpp) 和 [src/domain/factor/include/FactorBacktestExecutor.h](../src/domain/factor/include/FactorBacktestExecutor.h)。
2. 策略回测 typed 主链当前已经把配置拆成 `strategySpec`、`universeSpec`、`costSpec`、`riskSpec`、`executionSpec`、`dataSourceSpec` 等结构，但还没有统一的 `marketEnvironmentProfile` 顶层字段，见 [src/domain/backtest/include/BacktestRequest.h](../src/domain/backtest/include/BacktestRequest.h) 和 [src/domain/strategy/include/StrategySnapshotTypes.h](../src/domain/strategy/include/StrategySnapshotTypes.h)。
3. 运行时规则链里已经出现了 `marketEnvironmentGate`，但现在它更接近“门禁结果字段”，不是“环境配置真源”，见 [src/ui/bridge/include/StrategyRuntimeRuleEvaluator.h](../src/ui/bridge/include/StrategyRuntimeRuleEvaluator.h) 和 [src/ui/bridge/src/StrategyRuntimeRuleEvaluator.cpp](../src/ui/bridge/src/StrategyRuntimeRuleEvaluator.cpp#L194)。

结论很明确：

当前系统有市场环境相关判断，但没有统一市场环境合同。

## 3. 合同原则

后续实现必须遵守下面四条原则：

1. C++ 内部只允许枚举和结构化类型，不允许用字符串表示市场环境。
2. QML 可以显示市场环境标签字符串，但那只是展示层映射，不是运行时真源。
3. 第一阶段只允许一个总开关 `marketEnvironmentProfile` 作为用户输入，不允许页面上散落多个隐含制度开关。
4. 各模块的具体执行语义必须从该开关解析得到，不允许每个模块各自猜测。

## 4. 建议的核心类型

### 4.1 顶层开关

建议新增统一枚举：

```text
enum class MarketEnvironmentProfile {
    GENERIC_EQUITY = 0,
    CN_A_SHARE = 1,
    HK_EQUITY = 2,
    US_EQUITY = 3,
};
```

这个枚举是唯一的用户级市场环境输入。

### 4.2 解析后的执行语义

建议由上面的枚举解析出一份内部只读语义结构：

```text
ResolvedMarketEnvironment
    - executionLagTradingDays
    - allowSameDaySellAfterBuy
    - shortSellingMode
    - returnAttributionMode
    - executionPriceModel
    - priceLimitMode
    - tradabilityRuleProfile
    - benchmarkProfile
    - calendarProfile
    - costProfile
```

约束：

1. 用户先选 `MarketEnvironmentProfile`。
2. 系统再解析出 `ResolvedMarketEnvironment`。
3. 第一阶段不开放页面级零散 override。

这样可以避免一开始就把市场制度拆成一堆用户自由组合的布尔开关，导致合同失控。

## 5. 因子回测链的配置合同

### 5.1 顶层配置

建议在 `factor::BacktestConfig` 中新增：

1. `marketEnvironmentProfile`

放置位置建议：

- 与 `forwardDays`、`rebalanceDays`、`transactionCost`、`slippageRate` 同级。

原因：

- 它和这些字段一起决定回测执行语义，属于回测运行配置，而不是因子定义本身。

### 5.2 解析后的内部语义

`FactorBacktestExecutor` 内部不应继续直接散用 `forwardDays + 默认 A 股理解` 这类隐含逻辑，而应在执行前先拿到：

1. `ResolvedMarketEnvironment`
2. 由它派生出的 `signalDate / executionDate / returnStartDate` 规则

### 5.3 桥接层入口

当前因子回测页面和控制器是通过 `backtestRuntimeParams` 传递运行参数，见 [src/ui/bridge/src/FactorBacktestController.cpp](../src/ui/bridge/src/FactorBacktestController.cpp#L1095) 和 [src/app/Qml/components/FactorWorkbench/Backtest/FactorBacktestPage.qml](../src/app/Qml/components/FactorWorkbench/Backtest/FactorBacktestPage.qml)。

后续建议：

1. `backtestRuntimeParams` 新增 `marketEnvironmentProfile` 整数字段。
2. `FactorBacktestController` 只负责读取该整数字段并写入 `BacktestConfig`。
3. 页面只维护枚举值，不自行维护 A 股 T+1、是否允许卖空等细分布尔项。

## 6. 策略回测链的配置合同

### 6.1 顶层配置

建议在 `StrategyBacktestConfig` 中新增：

1. `marketEnvironmentProfile`

它应与 `commissionRate`、`slippageRate`、`taxRate`、`enableShortSelling`、`rebalanceFrequency` 同级，但后续这些字段的默认值和可用范围应由市场环境解析得到。

### 6.2 四类快照的归属建议

当前策略回测结果里已经有四类快照：

1. `ruleProfileSnapshot`
2. `executionPolicySnapshot`
3. `backtestAssumptionsSnapshot`
4. `strategyScopeContextSnapshot`

建议后续按下面方式放置市场环境相关字段：

#### `strategyScopeContextSnapshot`

放用户选择的顶层环境：

1. `marketEnvironmentProfile`

职责：

- 表示“当前策略/回测是在什么市场环境里解释”。

#### `executionPolicySnapshot`

放由环境解析出的执行制度字段：

1. `executionLagTradingDays`
2. `allowSameDaySellAfterBuy`
3. `shortSellingMode`
4. `executionPriceModel`
5. `priceLimitMode`

职责：

- 表示执行时到底如何成交、何时允许退出、是否允许做空。

#### `backtestAssumptionsSnapshot`

放由环境解析出的研究/回测假设：

1. `returnAttributionMode`
2. `benchmarkProfile`
3. `riskFreeRateProfile`
4. `costProfile`
5. `calendarProfile`

职责：

- 表示收益归因、基准和年化假设，而不是订单执行细节。

#### `ruleProfileSnapshot`

不建议把市场环境本身塞进这里。

原因：

- `ruleProfile` 更适合放组合/风控/限制规则，而不是制度真源。

## 7. 运行时规则链的配置合同

### 7.1 MarketContext

当前 `StrategyRuntimeRuleEvaluator::MarketContext` 里只有市场时段和运行时会话信息，见 [src/ui/bridge/include/StrategyRuntimeRuleEvaluator.h](../src/ui/bridge/include/StrategyRuntimeRuleEvaluator.h)。

建议后续新增：

1. `marketEnvironmentProfile`
2. `resolvedMarketEnvironmentSnapshot`

职责：

- 让运行时门禁知道自己在什么制度环境下工作。

### 7.2 Gate 输出

当前输出里已有 `marketEnvironmentGate`，但它表示的是 `pending / blocked / live / shadow` 这类结果，不够表达配置本身。

建议后续区分：

1. `marketEnvironmentProfile`：当前环境配置值。
2. `marketEnvironmentGate`：当前环境门禁结果。
3. `marketEnvironmentReason`：门禁失败原因。

不要再让一个字段同时表示“环境是什么”和“门禁结果如何”。

## 8. 结果合同建议

后续结果合同至少要显式暴露下面几项：

1. `marketEnvironmentProfile`
2. `signalDateSemantics`
3. `executionDateSemantics`
4. `returnAttributionMode`

这里有一条硬约束：

- C++ 结果结构里保存枚举值或结构化字段。
- 如果 QML 需要显示中文标签，由桥接层单独映射展示字符串。

不要让结果合同继续只展示 `forwardDays`、`rebalanceDays`，却不告诉用户这套结果是在什么市场制度下解释出来的。

## 9. 缓存与测试合同建议

市场环境一旦进入正式配置合同，下面两类内容必须同步对齐：

1. 回测缓存键
2. 回归测试矩阵

### 9.1 缓存键

因子回测缓存、benchmark 缓存、策略回测缓存都应把 `marketEnvironmentProfile` 纳入签名。

必要时还应加入：

1. `executionPriceModel`
2. `returnAttributionMode`
3. `environmentContractVersion`

原因很简单：

- 同一因子、同一时间区间、同一 `forwardDays`，在 A 股和美股环境下不应复用同一结果。

### 9.2 测试矩阵

至少要新增四类测试：

1. 因子回测在不同 `marketEnvironmentProfile` 下的收益起点差异。
2. 策略回测在不同 `marketEnvironmentProfile` 下的执行限制差异。
3. 运行时规则在不同 `marketEnvironmentProfile` 下的门禁差异。
4. 缓存键在不同 `marketEnvironmentProfile` 下不会错误复用。

## 10. QML 和桥接层建议

### 10.1 页面输入

因子回测页、策略回测页、风险配置页后续都应接入统一市场环境选择器。

页面层约束：

1. 只传递 `marketEnvironmentProfile` 整数值。
2. 页面只负责显示 label，不负责解释制度细节。
3. 页面不自行维护一套 A 股特判逻辑。

### 10.2 桥接职责

桥接层只负责两件事：

1. 把页面的枚举值写入配置合同。
2. 把配置合同中的枚举值映射成展示标签返回给 QML。

桥接层不应该再成为市场制度兜底逻辑聚集地。

## 11. 模块级落地顺序

建议按下面顺序推进：

1. 先在因子回测配置和策略回测配置里加入 `marketEnvironmentProfile`。
2. 再引入 `ResolvedMarketEnvironment`，统一执行语义解析。
3. 然后把运行时规则链改成读取同一环境配置。
4. 最后统一结果合同、缓存键和测试矩阵。

这个顺序的好处是：

- 先把配置真源固定。
- 再让执行链和展示链逐步服从这个真源。

## 12. 结论

后续“支持 A 股和其他市场环境”的关键，不是给页面多加一个下拉框，而是把市场环境开关变成正式配置合同。

第一阶段最小闭环应当只有一个用户输入：

1. `marketEnvironmentProfile`

然后由系统内部解析出执行、研究、风控和展示所需的全部语义。

只有这样，后续模块级对齐才不会再次退化成“页面一个字段、回测一个默认值、规则链另写一套判断”的碎片状态。
