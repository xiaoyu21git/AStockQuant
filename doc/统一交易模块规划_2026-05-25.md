# 统一交易模块规划

## 1. 目标

本文用于回答一个具体问题：

1. 策略回测和因子回测的交易能力，是否可以收敛成一个统一模块。
2. 统一模块是否可以通过模式切换同时服务于回测和实盘。
3. 风险控制是否应该直接内嵌到交易模块内部。

结论先行：

1. 可以统一，但统一对象应是交易执行内核，不是把所有页面、参数、研究逻辑和实盘逻辑硬并成一个大模块。
2. 可以通过回测模式和实盘模式复用同一套订单意图、撮合语义、仓位状态、成本模型和结果合同。
3. 风控不应以“业务归属”被吞进交易模块；应作为交易内核中的规则链和风控画像注入点存在，执行时被强制使用，但参数所有权仍保持独立。

换句话说，推荐的不是“一个巨型交易模块”，而是：

1. 一个统一交易执行内核
2. 一个回测执行适配层
3. 一个实盘执行适配层
4. 一条统一风险规则链
5. 两套不同的参数装配入口

## 2. 现状判断

从当前工程结构看，已经具备部分统一基础，但还没有完全统一。

### 2.1 已经统一的部分

1. 策略回测侧已经有结构化回测请求合同，`BacktestRequest` 明确拆出 `costSpec`、`riskSpec`、`executionSpec`、`dataSourceSpec`、`runtimeOptions`。
2. 策略回测侧已经有相对清晰的应用服务边界，`BacktestApplicationService` 和 `BacktestRequestFactory` 说明系统已经接受“回测入口结构化”这件事。
3. 现有职责文档已经明确要求：策略定义、回测会话、风控运行三层分开，禁止互相代写和混读。

### 2.2 还未统一的部分

1. 因子回测核心仍偏研究执行器形态，重点是因子值、分组收益、IC、未来收益窗口，不是订单级交易内核。
2. 策略回测已经进入“策略信号 -> 仓位/交易 -> 绩效结果”的链路；因子回测更多是“因子观测 -> 调仓假设 -> 横截面收益归因”的链路。
3. 实盘交易链路目前围绕 GM/Jujin 生命周期、订单状态回报、Execution report、订单补查等真实运行时事实展开，这与回测的同步演算语义不同。

### 2.3 已有约束不能被破坏

当前仓库已有明确约束，后续统一设计必须遵守：

1. 回测页只维护回测会话参数，不能重新拥有策略定义参数。
2. 风控页维护的是运行期风控，不应反向拥有回测假设。
3. 因子页里的 `forwardDays`、`rebalanceDays`、`benchmarkSymbol`、`commissionRate`、`slippageRate` 被定义为研究运行参数，属于回测会话层，不属于风控层。
4. 实盘交易运行时遵循单会话、单运行实例、回调为真相来源，EventBus 只是桥，不是交易事实源。

因此，统一交易模块不能以“把所有参数都收口到交易模块内部”为代价破坏分层。

## 3. 对提议的判断

针对“交易功能全部做成一个模块，回测使用回测模式，实盘使用实盘模式，并把风险直接嵌入交易模块内部，只开放部分参数给回测使用”的提议，判断如下。

### 3.1 可接受的部分

以下方向是对的：

1. 统一订单语义、成交语义、持仓语义、账户语义。
2. 用模式切换区分回测执行器和实盘执行器。
3. 回测和实盘共用一套交易意图合同、订单计划合同、成交结果合同和风险规则接口。
4. 策略回测与因子回测共用同一套调仓和执行假设表达。

### 3.2 不能直接照搬的部分

以下做法不建议直接采用：

1. 把风险“作为业务归属”完全塞进交易模块，然后对外只暴露少数回测参数。
2. 让统一交易模块自己拥有回测参数、策略参数、风险参数三类字段。
3. 让因子回测为了复用交易模块，被迫伪装成普通策略回测。

原因很直接：

1. 这会重新制造当前项目刚刚在清理的职责混层问题。
2. 风控在回测和实盘中的语义不完全相同，不能只靠一个“隐藏参数集合”处理。
3. 因子回测很多场景是研究型组合构建，不一定需要实盘级订单状态机的全部细节。

## 4. 推荐的统一方案

推荐统一的是“交易执行域模型”和“执行管线”，而不是把所有业务场景强行压成一个类。

### 4.1 目标架构

建议分为五层：

1. 交易意图层
2. 交易计划层
3. 执行内核层
4. 模式适配层
5. 风险规则链层

对应说明如下。

#### 4.1.1 交易意图层

职责：接收来自策略回测、因子回测、实盘策略运行时的统一交易意图。

统一输入建议：

1. 目标持仓
2. 调仓原因
3. 信号时间
4. 生效时间
5. 资金约束
6. 执行约束
7. 风险画像引用

此层不关心底层是回测还是实盘，只表达“想达到什么仓位变化”。

#### 4.1.2 交易计划层

职责：把目标持仓变化转换为统一订单计划。

输出建议包括：

1. 买卖方向
2. 目标数量或目标权重
3. 计划批次
4. 顺序依赖
5. 价格模型
6. 成本模型
7. 调仓窗口

该层是策略回测和因子回测真正应该共享的核心之一。

#### 4.1.3 执行内核层

职责：执行订单计划，维护统一仓位状态、现金状态、成交状态、账户权益状态。

统一内核至少要拥有：

1. PositionLedger
2. CashLedger
3. OrderBook
4. FillBook
5. PortfolioState
6. ExecutionResultBuilder

这里才是“一个可以复用的交易模块”的核心。

#### 4.1.4 模式适配层

此层按执行环境分成两类：

1. 回测适配器
2. 实盘适配器

回测适配器职责：

1. 从历史 bar/tick/daily bar 提供价格与成交假设
2. 根据撮合模型生成 fill
3. 按交易日历推进状态
4. 生成回测绩效和归因结果

实盘适配器职责：

1. 向券商或 GM/Jujin 提交真实委托
2. 接收 order update / execution report
3. 做真实订单补查与状态合并
4. 按真实账户事实修正仓位和资金

两者共享内核，但不共享数据源和事实来源。

#### 4.1.5 风险规则链层

风险应嵌入执行管线，但不应吞掉风险的参数所有权。

推荐做法：

1. 交易模块强制依赖 `RiskProfile`
2. 所有下单、改单、撤单、批次推进都必须经过 `RiskRuleChain`
3. 回测模式与实盘模式都使用统一规则接口
4. 规则启用范围、阈值、动作级别由外部画像配置注入

也就是说，风险是执行前置门禁和执行中断器，不是一个随处散落的工具函数集合。

## 5. 风险应该怎么嵌

### 5.1 可以嵌入的部分

可以嵌入交易执行模块内部的，是风险执行机制：

1. 下单前检查
2. 持仓超限检查
3. 组合敞口检查
4. 熔断检查
5. 批次推进阻断
6. 滑点容忍度校验
7. 单日亏损终止

这些应该是内核固定流程的一部分。

### 5.2 不应该嵌入的部分

不应该嵌入交易模块内部的，是风险参数的业务归属：

1. 风控页仍然是风控参数编辑入口。
2. 回测页仍然只暴露研究需要的回测参数。
3. 策略页仍然拥有策略定义参数。
4. 交易模块不应成为这些参数的最终编辑归属地。

因此更准确的表述应该是：

1. 风险执行机制内嵌到交易管线。
2. 风险参数画像从外部装配进入交易模块。
3. 不同模式按权限暴露不同参数视图。

## 6. 策略回测与因子回测如何共用

这里要区分“共用执行层”和“共用业务入口”。

### 6.1 可以共用的部分

策略回测与因子回测可以共用：

1. 调仓日历
2. 调仓频率表达
3. 成本模型
4. 滑点模型
5. 目标持仓到订单计划的转换
6. 仓位账本
7. 权益曲线计算
8. 风险规则链接口
9. 结果快照基础结构

### 6.2 不应强行共用的部分

不建议强行共用：

1. 因子研究特有的 IC、RankIC、分组收益、因子暴露诊断。
2. 普通策略回测特有的规则模板事件、离散买卖点逻辑。
3. 实盘运行时特有的订单补查、回报修正、客户端委托号映射。

建议做法是：

1. 因子回测在上游生成目标组合或目标权重。
2. 然后把“目标组合调仓任务”交给统一交易内核做回测执行。
3. 因子研究指标继续保留在因子研究层，不塞进交易内核。

这比“因子回测完全改造成普通策略回测”更稳。

## 7. 建议的模块划分

建议未来拆成以下模块。

### 7.1 TradingCore

唯一职责：统一交易执行内核。

内容包括：

1. 订单意图模型
2. 订单计划模型
3. 仓位账本
4. 现金账本
5. 成交记录
6. 权益曲线
7. 执行结果快照

### 7.2 TradingModeBacktest

唯一职责：为 TradingCore 提供回测环境。

内容包括：

1. 历史行情读取
2. 撮合模型
3. 交易日推进
4. 成本模拟
5. 回测专用结果汇总

### 7.3 TradingModeLive

唯一职责：为 TradingCore 提供实盘环境。

内容包括：

1. 券商适配
2. GM/Jujin 订单桥接
3. 回报订阅
4. 补查与对账
5. 真实账户状态同步

### 7.4 TradingRisk

唯一职责：定义统一风险规则链和风险画像。

内容包括：

1. RiskProfile
2. RiskRule
3. RiskRuleChain
4. RiskDecision
5. RiskBreachEvent

### 7.5 TradingAdapters

唯一职责：承接不同业务入口。

建议至少有：

1. StrategyBacktestTradingAdapter
2. FactorBacktestTradingAdapter
3. LiveStrategyTradingAdapter

这样做可以保证业务入口各自保留自己的前置语义，但最终落入统一执行内核。

## 8. 参数暴露策略

你提出“只开放部分参数给回测使用”，这个方向本身是对的，但应按视图裁剪，不应按模块私藏。

### 8.1 回测模式暴露

回测模式对外建议暴露：

1. 初始资金
2. 佣金率
3. 滑点率
4. 调仓频率
5. 成交价格模型
6. 基准
7. 股票池过滤
8. 研究型风险阈值，例如单票权重上限、组合权重上限、最大回撤停止条件

### 8.2 实盘模式暴露

实盘模式对外建议暴露：

1. 账户绑定
2. 券商连接
3. 下单权限
4. 单笔委托上限
5. 日内成交额限制
6. 熔断阈值
7. 实时滑点容忍度
8. 批次执行控制
9. 人工检查点

### 8.3 内部统一画像

虽然外部展示不同，但内部最好统一成：

1. BacktestExecutionProfile
2. LiveExecutionProfile
3. RiskProfile
4. CostProfile
5. MarketExecutionProfile

然后由模式装配器把这些 profile 注入 TradingCore。

## 9. 迁移路线

不建议一步到位重写。推荐分四期推进。

### 9.1 第一期：统一合同，不动底层执行

目标：先统一输入输出合同。

工作内容：

1. 定义统一 TradeIntent、TargetPortfolio、OrderPlan、ExecutionResult、RiskProfile。
2. 为策略回测和因子回测各写一个 Adapter，把现有输入装配到统一合同。
3. 先不替换现有回测执行器，只做双写或镜像演算验证。

交付标准：

1. 两种回测都能产出统一执行计划快照。
2. 风险画像可以通过统一接口注入。

### 9.2 第二期：抽出统一回测交易内核

目标：让策略回测先切到 TradingCore Backtest 模式。

工作内容：

1. 把当前策略回测里的仓位、现金、成交、权益计算抽到 TradingCore。
2. 旧 `StrategyBacktestService` 已删除，第二期应直接让新的策略回测 bridge/controller 对接 typed application service 和统一内核。
3. 回归验证现有结果合同和页面展示不退化。

交付标准：

1. 标准策略回测可完全跑通。
2. 绩效指标与旧实现差异可审计。

### 9.3 第三期：因子回测接入统一调仓执行

目标：让因子回测共用统一调仓和持仓演算。

工作内容：

1. 因子回测上游先输出目标组合。
2. 统一由 TradingCore Backtest 模式执行调仓。
3. 因子研究指标继续在研究层计算，和交易执行结果并列输出。

交付标准：

1. 因子回测能复用统一成本、滑点、仓位和权益逻辑。
2. IC/分组收益等研究指标不受损。

### 9.4 第四期：实盘接入统一执行内核

目标：将真实订单桥接收敛到统一内核之下。

工作内容：

1. 抽象 LiveBrokerAdapter。
2. GM/Jujin 作为其中一个实现。
3. 统一 recent orders、fills、positions、equity 的状态写入口。
4. 将现有执行前规则链接到统一 RiskRuleChain。

交付标准：

1. 回测和实盘共享同一套订单状态模型。
2. 风控规则在回测和实盘中能共用接口但保留不同配置。

## 10. 关键设计原则

后续落地时建议强制遵守以下原则：

1. 一个语义只有一个拥有者，禁止交易模块回收所有参数归属。
2. 统一的是执行内核，不是研究指标和实盘桥接细节。
3. 风险是统一规则链，不是到处读配置的 if 分支。
4. 回测模式和实盘模式共享状态机与合同，不共享事实来源。
5. 因子回测先输出目标组合，再交给交易内核，不要反向把因子研究层改成普通策略层。
6. 页面只暴露本层参数，不能因为统一模块出现就重新跨层编辑。

## 11. 建议的最终口径

如果要对团队给出一句明确建议，推荐这样表述：

1. 可以做成一个统一交易执行内核。
2. 回测和实盘通过不同模式适配器复用它。
3. 风险控制要内嵌进执行管线，但风险参数归属不能并入交易模块。
4. 策略回测和因子回测共用调仓执行、成本、仓位和权益计算，不强行共用研究指标层。

这条路线既能提升复用度，又不会把当前已经清理出来的职责边界重新打乱。
