# 策略回测引擎实现约束

日期：2026-05-26

## 1. 目的

本文档用于补充并收紧新策略回测引擎的实现约束。

结论只有一条：

现在可以开始创建新的策略回测引擎类，但实现必须以强类型、面向对象、无字符串业务语义、无散装 map 容器语义为硬前提。

若本约束与现有冻结设计稿中的示例声明冲突，以本约束为准；冲突示例必须视为待修正文档示例，而不是实现依据。

## 3. 类型系统硬约束

### 3.1 禁止项

新策略回测引擎主干中，以下类型和表达方式不得作为业务语义载体出现在公开合同、跨模块接口、领域模型和运行时边界上：

1. `std::string`
2. `QString`
3. `char*`
4. `std::string_view`
5. `QMap`
6. `QVariantMap`
7. `QHash`
8. `std::map`
9. `std::unordered_map`
10. 以 `pair`、`tuple`、匿名容器直接承载业务字段组合
11. 通过字符串 key、字符串 id、字符串 reason 传递领域语义

说明：

1. 字符串只允许存在于 QML 展示态、日志展示态、错误呈现态。
2. 引擎领域层、应用层、网关层、运行时层不得把字符串当成业务真源。
3. `QVariantMap` / `QVariantList` 只允许停留在 UI 层展示输入输出边界，UI 层以外任何模块都不得继续持有、返回或传播这两类类型。
4. 任何需要跨边界表达的业务概念都必须有命名类型。
5. 新策略回测引擎内部禁止出现字符串字面量；若确有展示、日志或错误呈现需要，必须停留在桥接层或其他受控边界，不得进入引擎主干源码。

### 3.2 允许项

下列内容允许存在，但只能作为实现细节或基础数值，而不能代替领域类型：

1. 私有实现中的顺序容器。
2. 列式数值缓冲区。
3. 局部循环计数器。
4. 不承载歧义语义的基础数值类型。

限制条件：

1. 它们不能直接暴露到公开接口。
2. 它们不能替代命名领域对象。
3. 它们不能成为跨层通信合同。

### 3.3 命名类型规则

以下业务语义必须使用自定义类型：

1. 标识类：`StrategyId`、`RuleTemplateId`、`FactorId`、`UniverseId`、`LayerId`、`OrderId`、`RunId`
2. 枚举类：`DecisionType`、`LayerType`、`ExecutionMode`、`OrderSide`、`RuleDecisionCode`
3. 值对象：`CandidateCount`、`ScoreThreshold`、`Weight`、`CashAmount`、`ShareQuantity`、`TradingDayIndex`
4. 集合对象：`FactorIdList`、`CandidateScoreList`、`TargetWeightList`、`LayerDecisionList`、`PositionSnapshotList`
5. 诊断对象：`RuleDecision`、`EngineAssumption`、`ValidationIssue`

### 3.4 类型替换清单

旧示例或临时设计中若出现以下表达，必须按下面方式收口：

1. `std::string ruleTemplateId` -> `RuleTemplateId ruleTemplateId`
2. `std::vector<std::string> factorIds` -> `FactorIdList factorIds`
3. `std::string reason` -> `RuleDecision decision`
4. `std::map<Symbol, double> scores` -> `CandidateScoreList scores`
5. `std::map<Symbol, double> weights` -> `TargetWeightList targetWeights`
6. `Map<Symbol, double>` 持仓表示 -> `PositionBook`
7. 裸 `int` 层标识 -> `LayerId`
8. 裸 `int` 候选数量 -> `CandidateCount`
9. 压平交易方向字符串 `"BUY"/"SELL"` -> 显式 `TradeSide side + TradePositionEffect positionEffect`

补充冻结规则：

1. 回测交易记录不得再使用 `direction` 一类压平字段承载成交语义。
2. 成交语义必须至少拆成 `side` 和 `positionEffect` 两个字段。
3. `Buy/Open`、`Buy/Close`、`Sell/Open`、`Sell/Close` 是四种不同语义，结果合同不得再合并。
4. 展示层若需要 `BUY`、`SELL`、`OPEN`、`CLOSE` 文本，必须由边界序列化生成，不得反向定义领域合同。

## 4. 面向对象设计约束

### 4.1 类职责必须单一

新引擎必须使用明确职责的类组织，不允许把整个回测流程塞进一个巨型过程函数。

至少应拆成以下角色：

1. `StrategyBacktestEngine`：唯一对外执行入口。
2. `BacktestRequestValidator`：请求完整性和边界校验。
3. `BacktestRuntimeSession`：一次回测运行的状态对象。
4. `LayerExecutionPipeline`：单层执行管道。
5. `PortfolioAllocator`：仓位目标分配。
6. `ExecutionCoordinator`：订单生成与成交回报整合。
7. `ResultAssembler`：结果装配。
8. `DiagnosticsRecorder`：诊断采集。

### 4.2 禁止 C 风格写法

以下模式在新引擎中一律禁止：

1. 以裸结构体加大批自由函数组成主流程。
2. 以 `switch + 字符串` 分发业务语义。
3. 使用输出参数回填多段状态。
4. 使用全局变量或静态可变状态保存运行上下文。
5. 一个函数同时承担校验、执行、持久化、展示拼装多重职责。

### 4.3 值对象要求

数据载体可以是值对象，但不能是无约束的 C 风格数据包。

要求如下：

1. 值对象必须有命名语义。
2. 值对象必须具备自己的不变量检查能力。
3. 值对象字段不得继续泄露字符串业务语义。
4. 跨层合同必须优先使用值对象和领域对象，而不是匿名基础类型组合。

### 4.4 必须显式使用设计模式与策略接口

新策略回测引擎不得仅靠“大类 + 若干工具函数”拼出流程，必须通过明确的设计模式组织可替换行为。

必须遵守以下规则：

1. 可替换行为必须通过显式策略接口建模，不允许把差异行为硬编码进主循环。
2. 至少以下能力必须具备独立策略接口或同等级别的可替换抽象：分层筛选、规则检查、执行模拟、仓位分配、结果分析。
3. 主引擎只承担流程编排职责，不承担所有具体算法实现。
4. 不允许通过 `if/else` 或 `switch` 在主流程内堆叠多套执行算法分支来代替策略模式。
5. 若使用其他模式辅助组织，如模板方法、门面、组合器、工厂，只允许服务于职责收敛，不得重新引入字符串分发和动态 map 语义。

## 5. 引擎边界约束

### 5.1 唯一输入输出保持不变

新引擎仍保持：

1. 唯一输入为 `BacktestRequest` 或其严格等价的强类型对象。
2. 唯一输出为 `BacktestResultDto` 或其严格等价的强类型对象。

### 5.2 引擎内部不得吸收外围噪音

以下能力不得重新进入引擎主干：

1. QML 页面字段名解释。
2. JSON 或 JS payload 归一化。
3. QVariantMap/QMap 兼容读取。
4. 历史别名字段回退。
5. 结果展示态反推业务语义。

### 5.3 失败策略

引擎必须直接失败，不允许兜底猜测：

1. 缺少关键元信息直接失败。
2. 类型不匹配直接失败。
3. 候选池域不一致直接失败。
4. 时间边界不一致直接失败。
5. 规则结果不完整直接失败。

## 6. 第一批类设计约束

第一批可落地类建议按下面骨架冻结：

1. `IStrategyBacktestEngine`
2. `StrategyBacktestEngine`
3. `BacktestRuntimeSession`
4. `BacktestRequestValidator`
5. `LayerExecutionPipeline`
6. `IRuleChecker`
7. `IExecutionSimulator`
8. `IPortfolioOptimizer`
9. `IMarketDataCache`
10. `ResultAssembler`
11. `DiagnosticsRecorder`
12. `ILayerSelectionStrategy`
13. `IExecutionPolicyStrategy`
14. `IAsyncBacktestScheduler`

要求：

1. 公开接口参数和返回值全部使用命名类型。
2. 依赖通过构造注入。
3. 不允许在引擎类里直接 new 具体基础设施实现。
4. 不允许把 UI、数据库、展示层对象带入引擎类定义。
5. 策略接口的职责边界必须互不重叠，禁止同一语义在多个策略接口重复解释。

## 7. 当前是否可以开工

可以。

原因只有三条：

1. 旧 `StrategyBacktestService` 已删除。
2. 旧共享 `BacktestEngine` 已从策略回测主链移出。
3. 当前仓库已经具备 `BacktestRequest`、`BacktestResultDto`、`BacktestEngineGateway` 这些 typed 锚点，可作为新引擎类的落点。

但开工前提也只有一条：

实现必须优先满足本约束文档，不得再把冻结稿里残留的字符串或 map 示例照搬进代码。

## 8. 最终性能目标

新策略回测引擎的最终目标必须额外满足以下硬约束：

1. 面向全市场、5 年数据量的标准回测任务，必须在 30 分钟内完成。
2. 执行上述规模任务时，不得导致 CPU 和内存异常暴涨，不得出现失控式资源占用。
3. 性能目标不是优化建议，而是最终验收条件；任何实现若无法满足该目标，即使功能正确，也不能视为完成。
4. 后续所有架构、数据访问、缓存、并行、因子计算与市场数据装载方案，都必须优先服从这一最终性能目标。

为避免语义歧义，本文对“不得导致 CPU 和内存异常暴涨”的解释固定如下：

1. 不允许通过重复全市场扫描、重复全量物化、重复横截面重算、无界缓存增长来换取功能通过。
2. 不允许把短窗口单标的请求放大成全市场全窗口计算主路径。
3. 不允许让峰值内存、线程数或 CPU 占用失去可预测上界。
4. 必须优先采用可控、可分块、可流式、可收敛的实现方式，避免 OOM、长时间打满 CPU、以及因为中间结果堆积导致的吞吐崩塌。

### 8.1 达成该目标的实现路径也必须固定

为满足“全市场 5 年 30 分钟内完成且 CPU/内存不异常暴涨”的最终目标，后续实现必须继续收敛到以下单一路径：

1. 市场数据装载必须以 typed 批量接口为主路径，按交易日切片或按日期窗口批量装载指定 symbol 集合，不允许退回到 `symbol/day` 逐条 SQL 拉取。
2. `HistoricalMarketDataCache` 必须优先做同交易日、同 universe 的批量预取，并把缺失值缓存为显式结果，避免同一交易日对同一 symbol 重复打数据库。
3. 因子快照装载必须继续朝“同交易日、同 symbol 集合、同 warmup 窗口复用一次底层数据，再批量产出多个 factor 结果”的方向收敛，不允许每个 factor、每个 symbol、每个交易日各自重复装载一遍历史窗口。
4. 因子运行时不得把单标的、短窗口请求放大成全市场全窗口横截面重算；当请求已经给出 symbol 集合时，底层数据查询、historical view 构造和 factor 计算都必须服从该集合边界。
5. 全市场执行必须采用有上界的分块策略，按交易日块、symbol 块或明确的运行分片推进，不允许一次性全量物化 5 年全市场原始行情、全部因子中间结果和全部横截面缓存。
6. 所有缓存都必须具备明确 key、生命周期和容量边界；禁止无界增长的进程级缓存，禁止为了命中率保留不可回收的全市场中间对象。
7. 并行执行必须采用固定上界的 worker 数和清晰的调度边界；不得通过无限加线程、无限排队任务或无节制 future 堆积来换吞吐。

### 8.2 最终验收必须包含真实数据基线

1. 最终验收不能只看单元测试和小样本回归，必须包含真实数据库、真实因子服务、真实全市场 5 年数据量下的端到端基线测试。
2. 验收结果至少必须记录总耗时、峰值内存、CPU 占用趋势、批量 SQL 次数、factor 数据装载次数和主要阶段耗时分布。
3. 若基线结果显示主要耗时来自重复市场数据装载、重复 warmup 查询、重复 historical view 构造或重复 factor 重算，则必须继续收敛实现，不得以“功能已经正确”为由结束。

## 9. 最终结论

新策略回测引擎从现在开始可以正式创建类骨架。

创建时必须把“强类型、禁字符串业务语义、禁 map 字典业务语义、纯面向对象、职责分层、失败即终止”作为硬约束，而不是建议项。

后续若实现代码与本文冲突，应修改代码，不修改约束口径。

## 10. 当前规则器落地边界

当前版本的 `IRuleChecker` 落地必须继续遵守以下边界：

1. 规则检查器只能消费 typed `StrategyContext`、`RuleProfileSnapshot`、`RuleTemplateBinding`、`RuleComposerState` 等强类型对象。
2. 规则检查器不得在引擎主干内解析 `templateId`、`filePath` 或任何字符串 DSL，不得根据字符串内容分发业务语义。
3. 当仓库内尚不存在强类型模板语义注册表时，规则检查器允许只实现基于 `RuleProfileSnapshot` 的 typed 门禁，并把 `RuleTemplateBinding`/`RuleComposerState` 仅作为阶段激活信息使用。
4. 规则摘要必须来自 `IRuleChecker` 的强类型统计结果，至少写回 `boundTemplateCount`、`matchedTemplateCount`、`blockedTemplateCount`。
5. 在主循环尚未接通 `Hold`/`Exit` 决策路径之前，已接通的 `Entry` 路径必须先成为真实规则门禁，不允许继续使用“发现绑定即一刀切失败”的占位实现。

## 11. 目录与分层硬约束

### 11.1 新引擎必须独立目录承载

新策略回测引擎不得继续散落在已有 bridge、controller 或旧共享回测目录中拼装实现。

必须遵守以下规则：

1. 新策略回测引擎主干必须放入独立文件夹。
2. 该文件夹只承载策略回测引擎自身的 typed 模型、运行时对象、接口和实现。
3. UI bridge、QML 页面、数据库适配、展示投影不得与引擎主干文件混放。
4. 若需要目录建议，优先采用 `src/domain/backtest/strategy_engine/` 或同等语义清晰的独立目录，而不是继续堆在现有杂糅目录下。
5. 新目录建立后，桥接层只能依赖引擎公开 typed 合同，不得反向把 UI 结构渗入引擎目录。

### 11.2 Qt 只能停留在桥接层

Qt 相关代码只能存在于 UI 展示边界和桥接层，不得进入新策略回测引擎主干。

硬约束如下：

1. 新策略回测引擎目录内禁止包含任何 Qt 头文件。
2. 新策略回测引擎目录内禁止出现 `QString`、`QVariant`、`QVariantMap`、`QList`、`QVector`、`QDateTime`、`QObject`、信号槽宏及任何其他 Qt 类型。
3. bridge 层负责把 Qt/QML 输入一次性转换成 typed C++ 对象，再交给引擎。
4. bridge 层负责把引擎 typed 输出投影成 Qt/QML 展示对象。
5. 不允许以“先用 Qt 类型占位，后续再替换”为理由突破这条边界。
6. 即使是不依赖 Qt 的普通字符串字面量，也不得进入新策略回测引擎主干；引擎内部语义必须由枚举、值对象、类型字段和显式诊断对象承载。

## 12. 代码风格与实现方式约束

### 12.1 只允许现代 C++ 实现

新策略回测引擎必须使用现代 C++ 方式实现，不允许退回 C 风格组织。

必须遵守以下规则：

1. 公开合同优先使用命名类、值对象、枚举类、接口类。
2. 资源管理优先使用 RAII、构造注入和明确生命周期对象。
3. 禁止把主流程写成“大量自由函数 + 裸数据包”的 C 风格组合。
4. 禁止以裸数组、裸指针输出参数、全局可变状态作为主流程组织方式。
5. 禁止函数堆砌式实现，即把校验、装配、执行、诊断、结果拼装塞进一串超长过程函数。
6. 禁止在引擎内部通过字符串字面量做阶段识别、原因编码、策略分发、诊断分类或默认值声明。

### 12.2 类设计必须以文档为真源

任何新类和新模块都必须先从文档定义职责，再进入代码实现。

必须遵守以下规则：

1. 先对齐 [doc/通用可扩展策略回测引擎——架构设计文档_2026-05-26.md](./通用可扩展策略回测引擎——架构设计文档_2026-05-26.md) 的组件职责与边界。

## 13. 实施顺序与编码前核对流程

### 13.1 实施顺序固定

新策略回测引擎的落地顺序必须固定如下：

1. 先确定目录边界与模块分层。
2. 先定义接口、枚举、值对象、请求结果合同和运行时状态类型。
3. 先定义策略接口、异步调度边界和主流程编排骨架。
4. 再建立类骨架、依赖注入关系和模块职责边界。
5. 完成以上骨架后，才允许填充具体执行逻辑。
6. 不允许跳过类型定义和边界设计，直接进入实现细节堆砌。

### 13.4 主流程必须支持异步线程

新策略回测引擎的主流程设计必须支持异步线程执行，但异步能力必须通过清晰边界进入，而不是污染核心计算内核。

必须遵守以下规则：

1. 单次回测计算内核可以保持同步 `execute(request)` 语义，但外层主流程必须提供异步调度能力。
2. 异步线程能力必须通过显式调度接口建模，例如任务调度器、运行句柄、进度快照、取消令牌等 typed 对象。
3. 引擎实例不得依赖全局可变状态，必须可安全并发运行多个独立实例。
4. 异步任务状态、进度、取消、完成结果必须使用强类型对象表达，不允许回退到字符串状态码或散装 map。
5. 线程池、后台执行框架和任务调度属于主流程能力，可以复用现有基础设施，但不得把 Qt 线程对象或 UI 生命周期对象带入引擎主干。

### 13.2 每次写新代码前必须做文档对齐

每次新增或修改策略回测引擎代码前，必须先完成下面的核对动作：

1. 核对本约束文档是否允许该类型、目录、依赖和边界。
2. 核对架构设计文档中的职责划分是否与本次改动一致。
3. 核对冻结版规则与边界文档中的输入输出、规则消费和硬边界是否被破坏。
4. 若当前代码锚点与文档冲突，先修正文档或明确冲突归属，再继续写代码。
5. 不允许在未完成上述核对前直接提交新实现。

### 13.3 与文档不一致时的处理原则

1. 若代码与文档冲突，默认先判断代码是否违规，而不是优先怀疑文档失效。
2. 若确需修改文档，必须先更新文档约束，再落地对应代码。
3. 任何新增规则都必须写回本约束文档或其明确指定的上位规则文档，不允许只停留在口头约定。
