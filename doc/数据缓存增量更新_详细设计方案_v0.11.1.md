## 1. 背景与目标

### 1.1 问题

当前历史数据缓存管线（PG → Fetch → Clean → Arrow Cache）每次都是全量重建。PostMarketSyncService 已实现增量下载（只拉当日数据写 PG），但下游清洗缓存需要全量重跑，每次耗时数十分钟。

### 1.2 目标

在已有 Arrow 缓存文件基础上，仅处理增量数据（新交易日），实现分钟级缓存更新。

### 1.3 范围

仅影响历史数据缓存链路（回测用），不动实时交易链路（策略引擎直接从 PG 查询）。

## 2. 当前架构

```
GMSDK → PostMarketSyncService(✅增量) → PostgreSQL
                                            │
                              全量查询 ❌     │
                                            ▼
                               DataFetchController
                                            │
                              全量清洗 ❌     ▼
                               CleaningEngine (14条规则)
                                            │
                              全量写入 ❌     ▼
                               DataCache (Arrow IPC .arrow)
                                            │
                                            ▼
                               ArrowMarketDataView → 回测引擎
```

## 3. 设计决策

| 决策 | 结论 |
|------|------|
| Arrow 写入方式 | 读全量旧 batches + 合并新 batches → 写临时文件 → 原子 rename（方案 A） |
| 清洗模式 | 复用 `cleanSortedBatch` 分批能力，回溯窗口用 `isFirst=true` 构建状态，新数据延续状态，`onKeep` 中按 `trade_date` 过滤丢弃回溯部分 |
| CleaningEngine 改动 | **零改动**。现有 `cleanSortedBatch` 接口已足够，合并和过滤逻辑在调用方实现 |
| 去重预加载 | 不需要。PG 有 UNIQUE 约束保证跨查询无重复，m_seen 从回溯窗口自然构建即可 |
| 复权因子 | 缓存层不处理。由 PostMarketSyncService 检测因子变化并全量重拉该股票 |
| 回溯窗口 | 动态计算 = max(maxForwardFillDays, maxLookbackDays, 60) + 10 天安全边际，默认 ~70 天 |
| 触发时机 | 用户手动触发（UI 按钮 "更新缓存"），不自动绑定 PostMarketSyncService |

## 4. 数据流设计

### 4.1 增量更新流程

```
1. 检测增量范围
   ├─ 从 DataCache::getDataSetInfo 获取 endDate
   ├─ 查询 PG: SELECT MAX(trade_date) FROM mkt.daily_bar
   ├─ 如果 endDate >= maxDate → 无需更新
   └─ 增量范围 = [endDate - lookbackWindow, maxDate]

2. 加载上下文
   ├─ DataCache::loadDataSetRange(dataSetId, sinceDate)
   └─ 从 PG 查询增量范围内的新数据

3. 合并清洗
   ├─ context + newData → 合并为 LightRow 向量
   ├─ 按 (symbol, trade_date) 排序
   └─ CleaningEngine::cleanSortedBatch(batch, true, true, onKeep)
       └─ onKeep 中：只保留 trade_date > endDate 的行

4. 增量写入
   └─ DataCache::appendDataSetFile(dataSetId, newRows, ...)
       ├─ 读取全部旧 RecordBatch → 写临时文件
       ├─ 写入新 RecordBatch → 写临时文件
       ├─ Close + fsync
       └─ rename(data.arrow.tmp → data.arrow)
```

### 4.2 清洗状态传递示意

```
回溯窗口 (第1批)              新数据 (第2..N批)
┌──────────────────┐       ┌──────────────────┐
│ isFirst=true      │       │ isFirst=false     │
│ → 状态从零构建    │ ────→ │ → 状态自然延续    │
│ → onKeep: 丢弃    │       │ → onKeep: 写入    │
└──────────────────┘       └──────────────────┘

例如: SuspensionFillRule 在回溯窗口中看到 2024-01-05 的有效价，
     到新数据 2024-01-06 (停牌) 时，自动向前填充。
```

## 5. 接口设计

### 5.1 DataCache（阶段 1）

```cpp
// 增量追加：读取现有 .arrow 的全部 RecordBatches，
// 与新数据合并后写入临时文件，最后原子 rename
// 返回追加后的总行数，失败返回 -1
int appendDataSetFile(int dataId, const std::vector<J>& newRows,
    const std::vector<std::string>& fieldNames,
    const std::unordered_set<std::string>& numericFields);

// 加载缓存中 trade_date 在 [sinceDate, endDate] 范围内的所有行（完整列）
// 实现：先扫描 trade_date 列找 maxDate → 计算实际范围 → 加载完整行
std::vector<J> loadDataSetRange(int dataId, const std::string& sinceDate);

// 获取数据集中最大的 trade_date（从 DataSetInfo.endDate 获取，无需重复扫描）
std::string getMaxTradeDate(int dataId);
```

### 5.2 DataCleaningServiceRefactored（阶段 3）

```cpp
// 增量更新已清洗的数据集
// 对比 PG 中最新的 trade_date 与缓存中的 endDate，
// 仅清洗增量部分并追加到缓存
void incrementalUpdateDataSet(int dataSetId, const QVariantMap& rules);
```

信号：
- `incrementalUpdateStarted(int dataSetId)`
- `incrementalUpdateProgress(int dataSetId, int pct, QString stage)`
- `incrementalUpdateFinished(int dataSetId, int newRows, QString message)`

### 5.3 CleanedDataController（阶段 4）

```cpp
// 对选中的数据集执行增量更新
Q_INVOKABLE void updateDataset(int dataSetId);

// 检查数据集是否有可用更新
Q_INVOKABLE bool hasUpdateAvailable(int dataSetId);
```

信号：
- `updateStarted(int dataSetId)`
- `updateFinished(int dataSetId, bool success, QString message)`

## 7. 异常处理矩阵

| 异常场景 | 处理策略 |
|----------|----------|
| 缓存文件不存在 | 降级为全量清洗（调用现有 `cleanDataFromDataSet`） |
| Arrow Schema 不匹配 | 检测后降级为全量重建 |
| 写入中崩溃 | `.arrow.tmp` 残留，下次写入前清理；旧 `.arrow` 完好 |
| 写入中磁盘空间不足 | 清理 `.arrow.tmp`，向 UI 返回明确错误，不降级为全量重建 |
| PG 连接失败 | 返回错误消息给 UI，不清洗 |
| 增量范围为空（已是最新）| 返回 "已是最新" 消息 |
| 回溯窗口覆盖不到某股票 | SuspensionFill/MissingValueFill 安全降级（视为首日，不填充） |
| 新上市股票（缓存中不存在）| 上下文没有该 symbol → 规则自然处理（无历史状态，正常通过） |

## 8. 验证方案

### 8.1 单元/集成测试

1. **DataCache 原子写入测试**：
   - 创建测试数据集 → `appendDataSetFile` 追加数据 → 验证 `loadDataSetFile` 返回完整数据
   - 模拟写入中途崩溃 → 验证旧文件完整，无 `.tmp` 残留

2. **增量清洗模式测试**：
   - 准备上下文数据（包含停牌日）+ 新数据
   - 调用增量清洗 → 验证停牌填充正确
   - 验证回溯部分被正确丢弃

3. **端到端测试**：
   - 创建清洗缓存（全量）
   - PG 插入新的交易日数据
   - 调用增量更新
   - 验证：新数据追加到缓存，旧数据不变，endDate 更新

### 8.2 手工验证

1. 编译通过（`cmake --build .`）
2. 启动应用 → 回测页面 → 选择一个已清洗的数据集
3. 点击 "更新缓存" → 观察 progress 信号
4. 验证更新后的数据集在回测中可用，数据范围扩展到最新交易日
