# 规则系统现状分析与设计方案

更新时间：2026-04-09

## 1. 目标与结论

### 1.1 交易规则系统总纲

如果把本项目的规则系统重新聚焦到“交易规则”而不是“软件规则”，那么它的定义应该是：

交易规则系统的主要目的，是把交易策略从信号生成推进到可执行的交易纪律，明确规定何时可交易、交易什么、何时开平仓、买卖多少、如何调仓，以及在风险恶化时如何收缩或停止交易。

这意味着规则系统首先服务于交易决策，而不是首先服务于软件模块划分。软件层的职责，是把交易规则参数化、执行化、审计化；交易层的职责，才是定义真正的行为边界。

基于这个定位，交易规则系统建议固定为以下四个顶层目标：

1. 约束交易边界：回答什么时候允许交易，什么时候只能观察、减仓或停止交易。
2. 统一交易决策：回答什么标的可以做、何时开仓、何时平仓、何时调仓。
3. 控制交易规模：回答单票、组合、账户三个层级应该持有多少仓位，如何分批执行。
4. 保证风险收缩：回答当市场、持仓或账户风险恶化时，系统如何降频、减仓、清仓、冻结。

### 1.2 交易规则系统的分层

建议以后所有规则都按交易生命周期组织，而不是按现有软件服务散放。统一分成七层：

1. 市场环境规则：今天是否允许参与市场，允许做到什么程度。
2. 标的准入规则：哪些标的可以进入候选池。
3. 信号与评分规则：哪些标的值得关注、产生开平仓候选信号。
4. 仓位与组合规则：单票、行业、组合、账户应分配多少风险预算。
5. 调仓决策规则：当前是开仓、加仓、减仓、退出，还是保持不动。
6. 执行编排规则：订单如何排序、拆分、节流、推进。
7. 账户级风险规则：何时只允许减仓、何时暂停交易、何时强制清仓。

这七层是交易规则的业务结构。后续 C++/QML 的服务设计应该去承载它，而不是反过来决定它。

### 1.3 交易规则的标准结构

从方法论上，单条规则建议至少包含以下八个要素：

1. 规则目标：这条规则要解决什么交易问题。
2. 作用层级：市场、标的、持仓、组合、账户中的哪一层。
3. 生效阶段：选股前、开仓前、持仓中、调仓时、下单时、异常处理中哪个阶段。
4. 判断对象：指数、行业、个股、持仓、组合或账户。
5. 触发条件：指标、事件、状态如何组合成触发条件。
6. 阈值参数：周期、比例、金额、次数、冷却时间等量化边界。
7. 输出动作：放行、拒绝、限制、改写、评分、状态切换。
8. 优先级与失效条件：与其他规则冲突时谁优先，什么情况下解除当前规则影响。

这比“条件满足就买卖”更完整，因为真实交易里很多规则不是直接发单，而是先限制、改写或冻结下一步行为。

### 1.4 交易规则的标准输出类型

为了避免把所有规则都做成简单的是/否判断，建议把规则输出统一成六类：

1. Pass：放行，允许进入下一阶段。
2. Block：阻断，当前行为不允许继续。
3. Limit：限制，允许继续但附加边界，例如限额、限批、限仓。
4. Rewrite：改写，把原始动作改成更保守的动作，例如全仓改试探仓。
5. Score：评分，用于候选标的排序或市场状态量化。
6. StateSwitch：状态切换，例如进入只减仓模式、冷却期或风控冻结。

这样设计后，交易规则系统才能真正表达“可以，但只能这样做”，而不是只有“允许/拒绝”两种粗粒度结果。

### 1.5 交易规则的标准运行顺序

建议把整个交易规则系统固定成以下运行顺序：

1. 先跑市场环境规则：判断今天是否可交易、允许的风险级别是什么。
2. 再跑标的准入规则：筛掉停牌、流动性不足、事件窗口不适合参与的标的。
3. 再跑评分与信号规则：形成候选信号，而不是立即形成最终订单。
4. 再跑仓位与组合规则：把候选信号约束到单票、行业、组合、账户的风险预算内。
5. 再跑调仓决策规则：决定最终是开仓、加仓、减仓、退出还是保持不动。
6. 再跑执行编排规则：决定先卖后买、分批数量、批次节奏、等待成交逻辑。
7. 最后始终由账户级风险规则做最终仲裁：必要时覆盖前序所有交易意图。

这个顺序的意义是，交易系统不能先下单再风控，也不能先有执行方案再补做组合约束。必须先定边界，再出动作。

### 1.6 交易规则的仲裁原则

当多条规则冲突时，建议固定采用下面的仲裁顺序：

1. 账户级风险规则最高：例如熔断、最大回撤、日内亏损、强制停机。
2. 组合级约束规则次高：例如总仓位、行业暴露、最大持仓数。
3. 持仓退出规则高于新开仓规则：先处理风险退出，再考虑新增暴露。
4. 市场环境规则高于个股机会规则：市场不允许时，单票再好也不能做。
5. 执行优化规则最低：执行规则只能优化路径，不能推翻上层风险边界。

可以压缩成一句话：

风险约束高于收益机会，退出决策高于进入决策，系统状态高于局部信号。

### 1.7 当前项目的建设方向

基于以上总纲，当前项目的交易规则系统建设方向建议固定为三阶段：

1. 先收敛“何时允许交易”和“何时禁止交易”：把启动期、只读态、绑定策略、持仓快照、交易时段、熔断等边界固定下来。
2. 再收敛“何时开平仓”和“买卖多少”：把信号审批、仓位管理、组合约束统一到一条交易决策链里。
3. 最后收敛“如何执行计划”：把一次性全发改成分批、节流、等待成交反馈推进的执行编排系统。

这三阶段里，前两阶段解决“做不做”和“做多少”，第三阶段解决“怎么做”。对当前项目来说，第三阶段正是最关键的缺口。

### 1.8 七层交易规则清单

为了让这个总纲后续可以直接展开为规则库，建议先固定一版“七层规则清单”。这不是具体策略参数，而是通用交易系统应该具备的规则目录。

#### 第一层：市场环境规则

这一层回答的问题是：今天、当前这个市场环境下，系统是否允许承担新的市场风险。

建议至少包含以下规则：

1. 交易时段规则：仅在允许的交易时段内开新仓、加仓、调仓。
2. 指数趋势规则：大盘或基准指数不满足趋势条件时，禁止新开仓。
3. 市场波动规则：市场波动率过高时，只允许观察或减仓。
4. 流动性环境规则：市场整体成交额或成交活跃度低于阈值时降低风险预算。
5. 事件窗口规则：重大会议、财报密集期、宏观事件窗口中降低或暂停主动交易。
6. 市场状态切换规则：在正常、谨慎、冻结三种状态间切换。

标准输出建议为：

1. AllowNewExposure
2. ReduceExposureBudget
3. FreezeNewExposure
4. ExitRiskOnly

#### 第二层：标的准入规则

这一层回答的问题是：哪些标的根本不应该进入交易候选集。

建议至少包含以下规则：

1. 基础可交易规则：停牌、退市整理、异常状态标的直接排除。
2. 风险标签规则：ST、*ST、财务异常、监管高风险标的排除。
3. 流动性准入规则：成交额、换手率、盘口深度不达标的标的排除。
4. 价格行为规则：连续一字板、临近涨跌停、跳空过大标的排除或限权。
5. 事件避让规则：财报前后、解禁窗口、重大公告窗口的标的限制参与。
6. 交易池规则：只允许来自指定 universe、指数成分、白名单或策略股票池的标的参与。

标准输出建议为：

1. Eligible
2. Ineligible
3. EligibleWithPenalty

#### 第三层：评分与信号规则

这一层回答的问题是：在可交易标的中，哪些值得关注，哪些产生开平仓候选信号。

建议至少包含以下规则：

1. 趋势评分规则：均线、突破、趋势斜率、相对强弱等。
2. 估值评分规则：PE、PB、EV/EBITDA、分位数等。
3. 质量评分规则：ROE、现金流、负债、盈利稳定性等。
4. 动量评分规则：过去 N 日收益、行业相对强弱、跨期动量。
5. 波动过滤规则：波动过大标的虽然有信号，但降低评分或直接拒绝。
6. 入场信号规则：满足某组条件后生成候选买入信号。
7. 出场信号规则：满足某组条件后生成候选卖出或减仓信号。

标准输出建议为：

1. Score
2. CandidateEntry
3. CandidateAdd
4. CandidateReduce
5. CandidateExit

这里要特别强调：这一层生成的是候选动作，不应该直接等价于真实下单动作。

#### 第四层：仓位与组合规则

这一层回答的问题是：即使某个标的有信号，也应该给它分配多少风险预算。

建议至少包含以下规则：

1. 单票仓位上限规则：单只标的不超过总资产或净值的某个比例。
2. 组合总仓位规则：全组合市场暴露不超过账户预算。
3. 最大持仓数规则：同一时间最多持有多少只标的。
4. 行业暴露规则：单一行业、单一主题不超过组合上限。
5. 风格暴露规则：成长、价值、小盘等风格暴露不能过度失衡。
6. 相关性规则：高度相关标的不能重复占用同一风险预算。
7. 仓位计算规则：固定比例、波动率、风险平价、凯利近似等。
8. 现金缓冲规则：始终保留一定现金，不将账户推到满风险状态。

标准输出建议为：

1. TargetWeight
2. MaxAllowedWeight
3. MaxAllowedNotional
4. RiskBudgetAdjustment

#### 第五层：调仓决策规则

这一层回答的问题是：当前到底应该做什么交易动作。

建议至少包含以下规则：

1. 开仓规则：满足环境、准入、评分、仓位条件后，允许新建仓位。
2. 加仓规则：已有持仓在何种情况下允许继续加仓。
3. 减仓规则：何时收缩仓位而不完全退出。
4. 平仓规则：何时彻底退出该标的。
5. 调仓频率规则：按日、周、月或偏离阈值触发调仓。
6. 偏离触发规则：目标权重与当前权重偏离不足阈值时不调仓。
7. 盈亏联动规则：盈利后分批止盈，亏损后分批收缩。
8. 冷却规则：刚止损或刚卖出后，进入一段时间的禁止重入期。

标准输出建议为：

1. Open
2. Add
3. Reduce
4. Exit
5. Hold
6. Cooldown

#### 第六层：执行编排规则

这一层回答的问题是：已经决定要交易之后，应该如何把交易动作安全地变成真实订单。

建议至少包含以下规则：

1. 先卖后买规则：先释放风险和现金，再扩张新仓。
2. 分批执行规则：将大订单拆成多批，避免瞬时冲击。
3. 单批金额规则：每一批次最大金额受限。
4. 单批笔数规则：每个执行轮次最多发出若干笔订单。
5. 流动性适配规则：成交额不足的标的自动放慢节奏或降低批量。
6. 价格偏离规则：价格偏离参考价过大时，本批不执行或重报价。
7. 成交推进规则：上一批未确认前，不允许进入下一批。
8. 冲突订单规则：同标的已有未完成单时，禁止重复下达相反或冲突订单。
9. 异常暂停规则：连续拒单、异常滑点、成交长时间停滞时暂停整轮执行。
10. 人工接管规则：在特定风险级别或异常级别下，必须进入人工确认点。

标准输出建议为：

1. ExecutionBatch
2. DeferredExecution
3. RetryLater
4. PauseExecution
5. RequireManualCheckpoint

这一层是当前项目最缺的部分，也是组合交易从“计划生成”走向“安全执行”的关键。

#### 第七层：账户级风险规则

这一层回答的问题是：从整个账户层面看，系统现在是否必须强制收缩风险，甚至停止交易。

建议至少包含以下规则：

1. 单日亏损规则：当日亏损达到阈值后停止新开仓。
2. 最大回撤规则：账户回撤达到阈值后降低仓位或强制退出。
3. 熔断规则：分级触发预警、减仓、清仓、停止交易。
4. 连续亏损规则：连续若干次亏损后进入冷却期。
5. 风险预算使用率规则：风险预算占用过高时，禁止新增仓位。
6. 杠杆与融资规则：杠杆使用率达到阈值时，限制所有扩张行为。
7. 异常会话规则：交易会话、回报链、持仓同步异常时，禁止新增风险暴露。

标准输出建议为：

1. Warn
2. RestrictNewExposure
3. ReduceExposure
4. ForceExit
5. HaltTrading

### 1.9 规则系统的最小闭环

如果要让这套通用交易规则体系先落地成一个最小可用版本，建议第一阶段只实现以下闭环：

1. 市场环境是否允许开新仓。
2. 标的是否允许进入候选池。
3. 候选信号是否满足开仓/减仓/退出条件。
4. 单票、组合、账户三个层级是否还有风险预算。
5. 最终动作是否需要分批执行。
6. 当账户风险恶化时是否必须停止新增交易。

这六个问题一旦串起来，系统就已经不是“有规则片段”，而是“有交易纪律闭环”。后续再继续补行业暴露、相关性、状态切换、人工接管等高级规则，会更稳。

### 1.10 第一阶段核心交易规则集

如果当前项目要先落地一版真正可运行的交易规则系统，不建议一开始把七层规则全部做满，而应该先固定一组“第一阶段核心交易规则集”。

这组规则的原则是：

1. 优先解决会直接导致错误交易或失控交易的问题。
2. 优先解决组合计划从“能算”到“能安全执行”的问题。
3. 优先选择已经有部分实现基础、可以较快收敛的规则。

建议第一阶段只先落下面十二条规则。

#### A. 市场环境层

**R001 交易时段开仓规则**

目标：非交易时段禁止新增敞口。

规则表达：

1. 如果当前不在允许的交易时段内，则禁止 Open 和 Add。
2. Reduce 和 Exit 可以保留为允许或延迟执行，由执行层决定。

理由：这是当前系统已经部分具备的能力，且是最基本的交易边界。

**R002 市场状态门禁规则**

目标：把系统的交易状态固定成“正常 / 谨慎 / 冻结”。

规则表达：

1. 正常状态允许 Open、Add、Reduce、Exit。
2. 谨慎状态允许 Reduce、Exit，Open 需要更高阈值或更低仓位。
3. 冻结状态仅允许 Reduce、Exit，禁止新增敞口。

理由：这是把大量离散判断收口成状态机的关键第一步。

#### B. 标的准入层

**R003 基础可交易准入规则**

目标：把不该参与的标的在最前面挡掉。

规则表达：

1. 停牌、退市整理、交易异常标的直接排除。
2. 不在策略股票池或允许 universe 中的标的直接排除。

理由：这是所有后续规则的前置条件，否则后面风控再多都只是补洞。

**R004 流动性准入规则**

目标：避免把计划生成到流动性明显不足的标的上。

规则表达：

1. 若成交额、换手率或盘口深度低于阈值，则该标的不允许 Open 和 Add。
2. 对已有持仓的 Reduce 和 Exit 不做同等强限制。

理由：这条规则与执行质量直接相关，应尽早进入第一阶段。

#### C. 信号与决策层

**R005 候选信号合法化规则**

目标：把“候选信号”与“最终下单动作”分开。

规则表达：

1. 信号层只生成 CandidateEntry、CandidateAdd、CandidateReduce、CandidateExit。
2. 候选信号在通过仓位、组合、账户风险约束前，不允许直接转成真实订单。

理由：这是当前系统从“信号即委托”升级到“信号 -> 决策 -> 执行”的关键分界线。

**R006 冷却期规则**

目标：避免止损后立刻重入、反复打脸。

规则表达：

1. 标的触发 Exit 后，在设定冷却期内禁止再次 Open。
2. 冷却期结束前，如果策略再次给出入场候选信号，只保留观察，不生成真实交易动作。

理由：这是一条交易纪律规则，成本低、收益高，适合第一阶段落地。

#### D. 仓位与组合层

**R007 单票仓位上限规则**

目标：限制个股集中度。

规则表达：

1. 任意标的的目标权重或目标市值不得超过单票上限。
2. 超过部分不允许进入执行计划。

理由：这条规则当前已有风险审批基础，最容易收敛。

**R008 组合总仓位规则**

目标：限制全组合市场暴露。

规则表达：

1. 所有目标买入叠加后，不得突破组合总仓位上限。
2. 超出部分按优先级或评分截断。

理由：它是组合层最核心的总闸门。

**R009 最大持仓数规则**

目标：控制组合复杂度和分散度。

规则表达：

1. 候选持仓数超过上限时，按评分或优先级保留前 N 个。
2. 后续候选标的即便满足信号条件，也不能突破最大持仓数。

理由：这是当前页面和分析层已有概念、但实时执行尚未落地的重要缺口。

#### E. 执行编排层

**R010 先卖后买规则**

目标：防止调仓时先扩张再回收，导致瞬时风险暴露放大。

规则表达：

1. 调仓计划中所有 Reduce/Exit 优先于 Open/Add。
2. 如果卖出资金尚未释放或回报尚未确认，则后续买入批次不得推进。

理由：这是组合执行器的第一条硬规则，优先级极高。

**R011 分批执行规则**

目标：防止一次性提交大量委托造成瞬时大持仓与冲击成本。

规则表达：

1. 调仓计划必须拆成若干执行批次。
2. 每一批次受单批金额、单批笔数、单标的节流约束。
3. 上一批次未达到推进条件时，下一批次不能启动。

理由：这正对当前你最关心的“瞬间大量持仓/大量委托”问题。

**R012 冲突订单与异常暂停规则**

目标：避免同标的重复下单、异常状态下继续推进执行。

规则表达：

1. 同标的存在未完成订单时，禁止发出冲突方向的新订单。
2. 连续拒单、长时间未成交、滑点显著恶化时，暂停整个执行轮次。
3. 暂停后进入人工接管或等待恢复状态。

理由：没有这条规则，分批执行器仍然可能在异常情况下失控。

#### F. 账户级风险层

**R013 账户回撤分级规则**

目标：把账户风险收缩做成统一的分级状态，而不是零散判断。

规则表达：

1. 一级风险：禁止新增高风险敞口，发出预警。
2. 二级风险：只允许 Reduce 和 Exit，并自动启动减仓动作。
3. 三级风险：强制清仓，当日停止交易。

理由：当前已有熔断逻辑基础，应作为第一阶段核心规则固化，而不是继续散落在服务里。

### 1.11 第一阶段规则的标准执行顺序

为了避免实现时再次回到“到处 if 判断”的状态，第一阶段规则建议固定用下面的顺序执行：

1. 先判断账户级风险状态。
2. 再判断市场环境状态。
3. 再做标的准入校验。
4. 再接收候选信号。
5. 再做仓位与组合约束。
6. 最后进入调仓与执行编排。

可以压缩成一句话：

先看账户还能不能做，再看市场该不该做，再看标的能不能做，再看计划该怎么做。

### 1.12 第一阶段落地后的预期结果

如果这组规则先落完，系统应至少达到以下效果：

1. 启动期不会因为时序问题直接进入错误交易。
2. 自动信号不会直接绕过组合和仓位约束进入下单。
3. 调仓计划不会一次性全部提交为委托。
4. 执行过程中遇到异常时能够暂停，而不是持续扩大风险。
5. 账户风险恶化时，系统行为会从“继续交易”切换为“限制交易、减仓、清仓”。

达到这一步，才可以进入第二阶段，继续补行业暴露、主题暴露、相关性、评分体系、动态仓位和更细的执行策略。

### 1.14 第一阶段代码映射结论

从代码现状看，第一阶段并不是从零开始。已经能直接复用的基础主要集中在以下三个服务：

1. RiskMonitorService：已经承载了大部分预交易审批、持仓快照门禁、交易时段门禁、单票/总仓位限制和熔断判断。
2. TradeExecutionService：已经承载了订单标准化、PENDING_RISK 过渡、风险审批衔接、broker readiness 检查和 recent order 状态维护。
3. PortfolioAnalysisService：已经承载了目标持仓快照与调仓计划生成。

当前真正的缺口，不在“有没有风控参数”，而在“有没有执行编排层”。也就是说：

1. 预交易审批基础已经有了。
2. 组合目标和调仓计划基础已经有了。
3. 但计划如何安全执行，当前几乎没有独立规则层。

因此第一阶段最值得优先补的，不是继续加更多风险指标，而是：

1. 把 RiskMonitorService 和 TradeExecutionService 里已有规则抽成统一 Rule 对象。
2. 给 maxPositions、流动性准入、冷却期补成完整交易规则。
3. 新增执行编排层，至少先实现：先卖后买、分批执行、冲突订单拦截、异常暂停。

### 1.15 第一阶段实施优先级建议

如果按“风险收益比”排序，建议用下面的顺序推进第一阶段：

1. 先抽象现有预交易规则：R001、R005、R007、R008、R013。
2. 再补交易边界缺口：R002、R003、R004、R006、R009。
3. 最后补执行编排缺口：R010、R011、R012。

理由很简单：

1. 预交易规则已经有基础，最容易先收敛成统一规则系统。
2. 交易边界规则补齐后，系统才不会在启动、选股和重入时继续漏风险。
3. 执行编排规则虽然最难，但它直接决定组合执行是否安全，是第一阶段必须完成的收尾部分。

### 1.16 参数型规则提取问题

除了前面列出的显式运行时规则，当前项目还有一个更隐蔽但同样重要的问题：

大量本应属于“交易规则系统”的内容，今天是以“策略参数”的形式散落在创建页、回测页、组合页、回测控制器和运行时桥接里。

这会带来四个直接问题：

1. 语义混乱：同一个字段有时代表策略逻辑，有时代表风控规则，有时代表执行约束。
2. 存储分散：同一类字段会同时出现在 parameters、backtest_runtime、advanced_options.optimization_config、strategyParams、appliedRiskConfig 中。
3. 读写重复：QML 和 C++ 两边都在做别名归并和兜底，字段越多越容易分叉。
4. 规则失真：本来应由统一规则系统控制的行为，被降格成“某次回测的参数快照”或“某个策略对象的附属字段”。

从当前代码看，这个问题已经非常明显，主要混入点包括：

1. [src/app/Qml/utils/StrategyCreationUtils.js](src/app/Qml/utils/StrategyCreationUtils.js) 把 positionSize、stopLoss、takeProfit、rebalanceDays 作为“通用策略参数”。
2. [src/app/Qml/page/backtest/StrategyBacktestPage.qml](src/app/Qml/page/backtest/StrategyBacktestPage.qml) 会从 parameters、backtest_settings、advanced_options、backtest_runtime 中抽取同一批风险/执行字段。
3. [src/ui/bridge/src/StrategyBacktestController.cpp](src/ui/bridge/src/StrategyBacktestController.cpp) 会把 stopLossPercent、takeProfitPercent、maxTotalExposure、maxPositionPercent、orderSizeLimit、turnoverLimit、breaker 等重新写回 strategyParams。
4. [src/ui/bridge/src/FactorBacktestController.cpp](src/ui/bridge/src/FactorBacktestController.cpp) 也会把 stopLossPercent、takeProfitPercent、maxDrawdownLimit 作为回测配置的一部分输出。
5. [src/app/Qml/page/PortfolioBuilderPage.qml](src/app/Qml/page/PortfolioBuilderPage.qml) 会把 positionSizingMethod、maxPositionPercent、maxTotalExposure、rebalanceDays、maxPositions、minWeightPercent、maxWeightPercent 同时写入 parameters、backtest_runtime、advanced_options.optimization_config。
6. [src/app/Qml/page/risk/RiskConfigurationPage.qml](src/app/Qml/page/risk/RiskConfigurationPage.qml) 又把这些字段作为全局风险规则来展示和保存。

这说明当前同一批字段已经横跨三层语义：

1. 策略逻辑参数。
2. 规则系统参数。
3. 回测/执行上下文参数。

后续必须把这三层拆开。

### 1.17 参数分类重构原则

建议以后把当前混在 strategy.parameters 里的字段，统一拆到下面四类，而不是继续都叫“参数”。

#### A. 应保留在 StrategyParams 的字段

这些字段属于策略自己的 alpha 逻辑、信号逻辑或模型逻辑，不应被抽成全局规则。

典型例子：

1. fastPeriod / slowPeriod
2. bollPeriod / bollStd / reversionThreshold
3. momentumPeriod
4. spreadThreshold / entryZScore / exitZScore
5. featureWindow / predictionDays / trainingDays / confidenceThreshold
6. factorTypes

这些字段回答的是“策略怎么看市场”，而不是“系统是否允许这样交易”。

#### B. 应提取到 RuleProfile 的字段

这些字段本质上属于交易纪律、风控边界、仓位边界、账户边界，应由规则系统统一管理。

典型字段：

1. stopLossPercent / stop_loss / stopLoss
2. takeProfitPercent / take_profit / takeProfit
3. maxDrawdownLimit / max_drawdown_limit
4. maxPositionPercent / maxSinglePositionRatio / positionPercent
5. maxTotalExposure / maxPositionRatio
6. maxPositions
7. maxIndustryExposure
8. maxThemeExposure
9. maxCorrelation
10. level1Breaker / level2Breaker / level3Breaker
11. autoStopEnabled
12. varWarningPercent

这些字段回答的是“允许承担多少风险、何时收缩风险、何时停止交易”。

#### C. 应提取到 ExecutionPolicy 的字段

这些字段更接近执行约束或交易实施方式，不宜继续附着在策略参数里。

典型字段：

1. orderSizeLimit
2. turnoverLimit
3. slippageLimit
4. rebalanceDays / rebalanceFrequency / rebalancingPeriod
5. positionSizingMethod
6. minWeightPercent / maxWeightPercent
7. position_size / positionSize

这些字段回答的是“怎么下、怎么调、怎么分配”，不是策略本身的因子或模型逻辑。

#### D. 应保留在 BacktestAssumptions 或 StrategyScopeContext 的字段

这两类字段不是规则本身，但当前也经常和规则混在一起。

BacktestAssumptions 典型字段：

1. commissionRate / commission / transactionCost
2. slippageRate / slippage / slippageCost
3. initialCapital
4. startDate / endDate
5. dataSourceMode

StrategyScopeContext 典型字段：

1. symbol_pool / symbolPool
2. linked_stock_pool_symbols
3. universeType / universeId / indexSymbol
4. selectedSymbols

这些字段分别回答的是：

1. 回测用什么假设。
2. 策略作用于什么范围。

它们不应该再和风险规则字段共用同一存储语义。

### 1.19 需要特别拆义的混合参数

当前有三类字段不能直接“搬家”，而必须先拆语义。

#### top_n / maxPositions

当前这组字段至少承担了两种不同含义：

1. 选股层含义：从候选池里选前 N 个。
2. 组合层含义：最多同时持有 N 个标的。

这两个不是一回事。后续应拆成：

1. selectionCount：策略筛选输出数量。
2. maxHoldings：组合最终允许持有数量。

#### position_size / positionSize / maxPositionPercent

当前这组字段也混了两种含义：

1. 单次开仓目标仓位。
2. 单票持仓上限。

后续应拆成：

1. entryTargetWeight：单次建仓目标权重。
2. maxSinglePositionWeight：单票持仓上限。

#### rebalanceDays / rebalanceFrequency

当前这组字段至少混了两种含义：

1. 策略重算/重新选股周期。
2. 实际交易执行的调仓周期。

后续应拆成：

1. signalRefreshDays：策略信号更新周期。
2. executionRebalanceDays：交易执行调仓周期。

3. 执行层应该怎么把交易落地。
4. 回测时用什么仿真假设。

### 1.21 参数提取的兼容迁移原则

考虑到当前代码已经大量依赖旧字段，参数提取不能一次性硬切，建议采用三步迁移：

1. 先读取兼容：规则系统优先读取新结构，同时兼容旧参数别名。
2. 再写入双轨：保存策略时同时写新结构和旧字段镜像，保证旧页面和旧控制器不立刻失效。
3. 最后收敛清理：当 RuleProfile / ExecutionPolicy 全链路稳定后，逐步移除旧字段回写。

在迁移期间，最重要的是保证一件事：

策略参数不再继续新增规则字段。

也就是说，从现在开始，新加的风险规则、执行规则、组合规则，都不应该再写回 strategy.parameters 的平铺字段里，而应该优先进入 RuleProfile 或 ExecutionPolicy。

### 1.25 对当前代码改造的直接含义

一旦采用上面的结构，后续代码层面就应遵循下面这条硬约束：

1. StrategyCreationUtils 不再继续新增风险规则和平铺执行规则字段。
2. StrategyBacktestPage 读取参数时先读 RuleProfile / ExecutionPolicy / BacktestAssumptions，再兼容旧字段。
3. StrategyBacktestController 和 FactorBacktestController 输出结果时，规则相关字段优先落到 ruleProfileSnapshot / executionPolicySnapshot，而不是继续塞回 strategyParams。
4. PortfolioBuilderPage 保存组合策略时，优化配置进入 ExecutionPolicy，组合约束进入 RuleProfile，symbol_pool 保持在 StrategyScopeContext。
5. RiskConfigurationPage 未来应直接编辑 RuleProfile，而不是间接编辑 strategy.parameters 的镜像字段。

这样改完之后，系统才能真正实现：

1. 策略有自己的逻辑参数。
2. 规则系统有自己的纪律参数。
3. 执行系统有自己的执行策略参数。
4. 回测系统有自己的仿真假设参数。

这四类参数分开之后，后续无论是做规则引擎、执行编排还是策略编辑器，语义才会稳定下来。

### 1.26 第一轮代码级重构目标

第一轮代码级重构不追求一次性把旧字段全部清掉，而是先建立下面这个新基线：

1. 所有页面和控制器都先学会“优先读新结构，兼容读旧字段”。
2. 所有新写入逻辑都优先写新结构，旧字段只做兼容镜像。
3. 规则解析逻辑不再散落在每个页面和控制器里，而是先收口到统一解析层。

这一轮重构的目标不是功能大改，而是把当前代码从“字段平铺 + 多处兜底”过渡到“结构化配置 + 统一适配”。

### 1.27 统一读写约定

从第一轮重构开始，所有相关模块都应遵循同一套读写顺序。

#### 读取优先级

统一采用下面的读取顺序：

1. 先读新结构：RuleProfile、ExecutionPolicy、BacktestAssumptions、StrategyScopeContext。
2. 再读当前已经结构化但语义未完全分离的旧容器：advanced_options.optimization_config、backtest_runtime、backtest_settings。
3. 最后再读 strategy.parameters 里的旧平铺字段和别名字段。

可以压缩成一句话：

新结构优先，旧容器兜底，平铺字段最后兼容。

#### 写入优先级

统一采用下面的写入顺序：

1. 优先写新结构。
2. 如果当前链路仍有旧控制器依赖，则同步写兼容镜像字段。
3. 禁止新增新的平铺规则字段。

也就是说，从这轮开始，即便为了兼容还要回写旧字段，旧字段也只能是镜像，不能再是主数据源。

### 1.28 统一适配层设计

为了避免每个页面和控制器都继续自己写一套 firstDefinedValue/alias merge 逻辑，建议先增加一层统一适配器。

#### QML 侧适配器

### 1.32 第一轮重构完成的判定标准

这一轮完成，不要求旧字段彻底消失，但至少要满足下面四个结果：

1. 页面和控制器读取规则字段时，新结构是第一优先级。
2. 页面和控制器内部不再各自维护一大串重复 alias 解析逻辑。
3. 新建和保存策略时，已经能稳定写出 rule_profile、execution_policy、backtest_assumptions、strategy_scope_context。
4. 当前运行时行为不因迁移而回退，旧页面和旧结果展示仍能正常工作。

达到这一步之后，第二轮才适合开始真正抽 Rule Engine 和 Execution Engine，因为那时配置来源已经稳定，不会再被参数语义混乱反复拖住。

当前项目里已经存在一批真实生效的交易规则，但这些规则分散在多个服务中，尚未形成统一的“规则系统”。现状不是“没有规则”，而是存在以下四类并存状态：

1. 已在运行时真正执行的规则。
2. 已有配置项，但只在回测或组合分析中生效的规则。
3. 页面上可配置、监控上可展示，但运行时没有硬约束的规则。
4. 业务上必须存在、但当前尚未实现的规则。

本设计文档的核心结论如下：

1. 当前真正的运行时规则核心在 RiskMonitorService 和 TradeExecutionService，而不是设置页。
2. RiskConfigService 当前更像“参数归一化与持久化服务”，不是规则引擎。
3. PortfolioAnalysisService 当前只负责“生成调仓计划”，还不具备“按规则安全执行计划”的能力。
4. RiskConfigurationPage 里展示的部分规则仍然属于“分析/展示层规则”，并未全部进入实时执行链。
5. 下一步应该把现有逻辑收敛为统一的 Rule Engine + Rule Chain + Rule Audit 三层结构，并补齐组合执行、批次控制、启动期保护、恢复单过滤等关键缺口。

## 3. 当前已经存在并真实生效的规则

### 3.1 连接与启动层规则

当前已经具备以下启动前置规则：

1. 交易连接默认 disabled=false 但 readOnly=true 作为安全基线，配置归一化由 TradingConnectionConfigService 负责。
2. 绑定策略时会生成业务 strategyId 与 runtimeStrategyId 的映射，避免业务策略和 GM runtime 策略身份混淆。
3. 开启真实交易前不再只要求 enabled=true 和 readOnly=false，还要求 liveUnlockConfirmed=true，避免保存配置后直接附着到 live runtime。
4. TradingConnectionConfigService 已经把启动门禁收敛成结构化 StartupGate 输出，统一返回 ready、ruleId、reasonCode、checks、checkedAt 等字段。
5. StrategyLibraryPage 从策略卡片启动时，会先完成交易绑定，再消费 StartupGate 和 live bridge readiness；SystemSettingsPage、StrategyLibraryPage、PortfolioBuilderPage 已共用同一套 StartupGate 文案解释。
6. TradeExecutionService 在 broker readiness 中已改为复用 StartupGate，而不是重复维护一份启动检查逻辑。
7. 启动恢复时，远端未完成订单快照已按当前绑定业务策略 / runtime strategy 过滤，不再把其他策略的遗留订单直接恢复进当前会话。

这部分规则已经构成了“系统是否允许进入交易态”的第一道门。

### 3.2 风险配置归一化规则

RiskConfigService 已经实现了别名归一化，这一点很重要，因为它意味着当前参数名虽然散，但写入后已能统一收敛。已经存在的别名组包括：

1. maxTotalExposure / maxPositionRatio
2. maxPositionPercent / maxSinglePositionRatio / positionPercent / position_size / positionSize
3. maxDrawdownLimit / max_drawdown_limit
4. stopLossPercent / stop_loss / stopLoss
5. takeProfitPercent / take_profit / takeProfit
6. positionSizingMethod / position_sizing_method
7. minWeightPercent / min_weight_percent
8. maxWeightPercent / max_weight_percent
9. rebalanceDays / rebalance_days / rebalancingPeriod / rebalanceFrequency
10. commissionRate / commission / transactionCost
11. slippageRate / slippage / slippageCost / slippageLimit

这一层已经具备“参数标准化”的雏形，但它只解决“值怎么存”，没有解决“规则怎么执行”。

### 3.3 信号审批规则

RiskMonitorService::reviewTradeSignal 已经形成一套较完整的预交易审批链。当前真实生效的规则包括：

#### 基础字段规则

1. strategyId、symbol、side 缺失时直接拒绝。
2. 非价格可选动作时，price 必须大于 0。
3. 自动策略信号如果没有明确 quantity 或 cashAmount，会被拒绝，不允许默认按风控额度自动推股数。
4. signal strength 小于等于 0 时拒绝。

#### 策略绑定与身份规则

1. 实盘模式下如果当前连接没有绑定任何业务策略，则拒绝委托。
2. 实盘模式下如果信号所属 strategyId 不在当前绑定列表中，则拒绝委托。
3. 策略服务未初始化或策略未找到，则拒绝委托。
4. 策略状态不是 ACTIVE/TESTING，则拒绝委托。

#### 启动期与交易时段规则

1. 持仓快照未加载完成时，禁止依赖持仓语义执行加仓或卖出。
2. 非交易时段禁止新增敞口。
3. 启动期 legacy market-driven 自动信号链已被整体关闭，不再允许市场 tick/bar 直接推导买卖。

#### 仓位与资产约束规则

1. 卖出时如果没有可卖持仓则拒绝。
2. 卖出数量大于可卖数量则拒绝。
3. 单笔委托金额超过 orderSizeLimit 时拒绝。
4. 日累计成交额加本笔超过 turnoverLimit 时拒绝。
5. 预计单票持仓占比超过 maxPositionPercent 时拒绝。
6. 预计组合总仓位超过 maxTotalExposure 时拒绝。

#### 价格与市场质量规则

1. 当 slippageLimit/slippageRate 配置存在时，委托价相对参考价偏离过大则拒绝。

#### 风险状态联动规则

1. 当前标的已触发止损线时，禁止继续加仓。
2. 当前标的已触发止盈线时，禁止继续加仓。
3. 当前账户回撤超过一级/二级/三级熔断线时，禁止继续加仓。
4. 当前账户回撤超过 maxDrawdownLimit 时，禁止继续加仓。
5. 当 level3 trading halt 已经触发时，当日停止交易。

这部分已经构成系统里最接近“规则引擎”的逻辑主体，但实现仍然是硬编码在单个服务里。

### 3.4 熔断自动动作规则

RiskMonitorService::evaluateBreakerActions 当前已具备自动执行型规则：

1. 仅在 enabled=true 且 readOnly=false 的前提下允许熔断自动动作。
2. 仅在账户总资产有效时评估熔断。
3. 熔断等级小于 2 时不执行自动动作，只保留约束语义。
4. 仅在交易时段内允许熔断自动动作。
5. 持仓首帧快照未完成时不允许熔断自动下单。
6. 二级熔断默认减仓 50%。
7. 三级熔断默认清仓并激活当日交易停止状态。
8. 熔断动作通过 submitBridgeOrder 重新走统一的委托与风控链。

这是当前系统里唯一真正带有“自动处置”能力的规则集合。

### 3.5 执行层规则

TradeExecutionService 当前已经实现以下执行侧规则：

1. 对 symbol、side、price、quantity、board lot 做参数合法性检查。
2. 对 stock/margin_buy/margin_sell 模式强制一手对齐。
3. 手工桥接委托先进入 PENDING_RISK，再调用 RiskMonitorService 审批。
4. 审批通过后才允许进入 submitBrokerOrder。
5. broker 不可用时可回退为 local pending order，但仍保留同一条事件链。
6. 若 runtime 返回延迟确认错误，会保留 PENDING 状态，而不是直接视为失败。
7. readOnly=true 时 evaluateBrokerReadiness 直接拒绝实盘提交。

### 3.6 组合调仓计划规则

PortfolioAnalysisService::buildPortfolioExecutionPlan 当前已经实现“计划生成规则”，包括：

1. 持仓快照未完成时拒绝生成调仓计划。
2. 目标持仓快照生成失败时拒绝生成计划。
3. 总资产无效时拒绝换算目标股数。
4. 对每个目标标的根据 targetWeight 和 lastPrice 计算目标数量。
5. 目标增仓不足一手时跳过。
6. 目标减仓时如果无可卖数量则跳过。
7. 现有持仓不在目标组合中时生成退出单。
8. 当前已对调仓委托应用先卖后买排序，并输出显式批次预览，作为执行编排层的最小基线。

这说明系统已经有“从组合目标到订单列表”的第一步，但目前只是生成 orders 预览，没有后续执行编排。

## 5. 当前缺失的关键规则

### 5.1 启动期规则剩余缺口

1. RecoveryOrderFilterRule、ExplicitLiveUnlockRule、StartupGateChain 已经落地，但目前仍主要收口在 TradingConnectionConfigService / TradeExecutionService 内，尚未抽成独立的 StartupRuleChain 和统一 Rule Audit。
2. StartupGate 当前重点覆盖连接可交易性门禁，尚未把 InitialSnapshotReadyRule、StartupNoExposureIncreaseRule、StartupSessionWindowRule 一并并入同一条启动安全链。
3. 启动相关页面虽然已经能展示结构化的 ruleId、reasonCode、checks，但这些结果还没有进入统一的规则命中统计和历史审计面板。

### 5.2 组合层规则缺口

1. maxPositions 没有进入 live 调仓审批。
2. 行业暴露、主题暴露、风格暴露没有进入 live 风控。
3. 持仓相关性规则没有进入候选持仓筛选和执行审批。
4. 目标权重信号没有“权重 -> 数量 -> 批次”的标准转换器。
5. 调仓周期 rebalanceDays 没有实际调度器。

### 5.3 执行编排规则剩余缺口

1. PortfolioAnalysisService 和 TradeExecutionService 之间还缺少统一的 ExecutionSchedulingRuleChain / ExecutionBatch 数据结构，当前 order list 仍停留在预览层。
2. 没有统一的 Execution Policy 作为批次、节流、推进、暂停的正式配置来源。
3. 没有“先减仓后加仓”的强制策略，也没有净现金释放后再推进买入批次的仲裁逻辑。
4. 当前仅在预览层支持批量委托节流拆分，单批金额、单批笔数、单批暴露增量仍未正式进入 live 执行链。
5. 当前已利用 recentOrders / runtime 回报状态实现 PendingOrderConflictRule 的 live 前置拦截基线，并在带 batchId / previousBatchId 上下文的委托上实现了 PartialFillAdvanceRule 的“前序批次必须全部成交”提交前门禁；同时在带 executionScopeId / pauseOnAbnormalReject 的批次委托上补了 RetryOrPauseRule 的“异常拒单后暂停后续批次”基线，并支持按 executionScopeId 显式解除暂停、在 TradingPage 原位重试当前批次；带 requiresManualCheckpoint 的批次也已能通过 ManualCheckpointRule 的显式人工确认门禁继续推进；但还没有继续补上统一恢复链和异常升级链。
6. 没有按市场类型区分股票、期货、期权的执行批处理策略。
7. 没有价格偏离时自动重报价或取消重试规则。

### 5.4 审计与解释缺口

1. StartupGate 已经输出结构化 ruleId、stageCode、reasonCode 和 checks，但预交易、执行、恢复等其他规则结果大多仍只有 reason 文本。
2. TradeExecutionService 当前已补 recentRuleHits 级别的委托规则命中历史基线，TradingPage 也能独立展示最近命中；但跨启动门禁、预交易、执行、恢复全阶段的统一规则命中日志和统计仍未完成。
3. 启动门禁相关页面已经能回答“是哪条 StartupGate 规则阻断”；交易页当前也已能在委托回报、toast 和执行日志中直接显示 ruleId、reasonCode 以及相关批次信息，用于回答“这笔单是被哪条执行规则拒绝的”。但更完整的阶段审计、参数快照和历史统计仍未统一沉淀。

## 6. 建议的规则系统分层设计

建议把规则系统收敛为五层：

### 6.1 Rule Catalog

职责：定义系统里有哪些规则、规则参数名、默认值、适用资产、适用阶段、是否阻断、是否可重写。

建议数据模型：

```cpp
enum class RuleStage {
    Startup,
    StrategyBinding,
    SignalNormalization,
    PreTradeRisk,
    PortfolioPlanning,
    ExecutionScheduling,
    BrokerSubmission,
    RuntimeRecovery,
    PostTradeAudit
};

enum class RuleDecisionType {
    Pass,
    Warn,
    Block,
    Rewrite,
    Schedule,
    Halt
};

struct RuleDecision {
    QString ruleId;
    RuleStage stage;
    RuleDecisionType type;
    QString reason;
    QVariantMap patches;
    QVariantMap metrics;
};

struct RuleContext {
    QVariantMap tradingConfiguration;
    QVariantMap riskConfiguration;
    QVariantMap strategy;
    QVariantMap accountSnapshot;
    QVariantList positions;
    QVariantMap signal;
    QVariantMap marketSnapshot;
    QVariantMap executionPlan;
    QVariantMap runtimeState;
};
```

### 6.2 Rule Chain

职责：把同一阶段的规则按固定顺序串起来执行，每一条规则只负责一件事情。

建议拆成以下链：

1. StartupRuleChain
2. BindingRuleChain
3. SignalRuleChain
4. PortfolioPlanRuleChain
5. ExecutionScheduleRuleChain
6. BrokerSubmissionRuleChain
7. RuntimeRecoveryRuleChain
8. AuditRuleChain

### 6.3 Rule Engine

职责：为每种业务场景装配对应链路，并返回结构化结果。

建议提供统一入口：

```cpp
class TradingRuleEngine {
public:

    RuleEvaluationResult evaluateSignal(const RuleContext& context);
    RuleEvaluationResult evaluatePortfolioPlan(const RuleContext& context);
    RuleEvaluationResult evaluateExecutionBatch(const RuleContext& context);

```

### 6.4 Rule Audit

职责：记录规则命中、参数快照、决策结果和后续动作。

建议落地内容：

1. ruleId
2. stage
3. decisionType
4. reason
5. strategyId
6. runtimeStrategyId
7. orderId/clientOrderId
8. symbol
9. snapshot version
10. risk config hash

### 6.5 Policy 与 Rule 分离

建议将“参数”与“逻辑”分离：

1. RiskConfigService 继续负责参数存取与归一化。
2. Rule Engine 只消费标准化配置，不直接管理持久化。
3. ExecutionPolicy 作为组合执行专用策略，不与基础风控混在同一对象里。

## 9. UI 角色重构建议

### 9.1 SystemSettingsPage 的定位

SystemSettingsPage 应只负责“连接与系统门禁”，不应承担完整规则系统入口。它应该只保留：

1. token
2. 账户环境
3. 绑定业务策略
4. runtimeStrategyId/gmStrategyId
5. readOnly/live unlock
6. 运行时订阅标的

不要把组合规则、执行策略、批次策略继续堆进这里。

### 9.2 RiskConfigurationPage 的定位

RiskConfigurationPage 应只负责“全局默认风险规则 + 实时监控 + 审计查看”，不应再混入大量仅展示但不执行的规则而不给状态标识。

建议为每个规则项显示以下状态之一：

1. 实时生效
2. 仅回测生效
3. 仅组合规划生效
4. 仅监控展示
5. 尚未实现

### 9.3 PortfolioBuilderPage 的定位

PortfolioBuilderPage 应负责三件事：

1. 目标组合生成
2. 调仓计划生成
3. 执行策略配置

需要新增一个明确的 Execution Policy 面板，而不是只展示 orders 预览。

## 10. 建议的实施路线

### 阶段一：收敛现有规则

目标：不改变业务行为，只把散落逻辑收拢成规则对象。

建议工作：

1. 提取 RuleContext。
2. 提取 RuleDecision。
3. 把 RiskMonitorService::reviewTradeSignal 内硬编码规则拆成独立 rule classes。
4. 为每条规则增加 ruleId 和统一审计输出。

### 阶段二：补齐启动与恢复规则

目标：解决当前最危险的启动期问题。

当前进展：

1. RecoveryOrderFilterRule 已落地：启动恢复的未完成订单会按当前绑定业务策略和 runtime strategy 过滤。
2. ExplicitLiveUnlockRule 已落地：enabled=true 且 readOnly=false 已不再足够，必须显式确认 liveUnlockConfirmed。

2. 把 InitialSnapshotReadyRule、StartupNoExposureIncreaseRule、StartupSessionWindowRule 并入统一启动安全链，而不是继续分散在其他服务里。
3. 把启动门禁的结构化结果沉淀到统一的历史审计和命中统计视图。

1. RecoveryOrderFilterRule
2. ExplicitLiveUnlockRule

本阶段剩余工作：

2. 把 SellBeforeBuyRule、BatchNotionalLimitRule、BatchCountLimitRule 从当前预览层能力继续推进到 live 执行，把分批、节流、暴露增量控制正式接入回报驱动链。

## 11. 最终建议

从工程优先级看，规则系统不应该先从“再加几个参数”开始，而应该先做三件事：

1. 把现有硬编码审批逻辑抽成统一 Rule Engine。
2. 把组合计划补到执行编排层，避免“人工确认 = 一次性全部下单”。
3. 把页面中的规则项按“实时生效/仅回测/仅展示/未实现”明确标记，停止语义混淆。

如果按风险优先级排序，最值得先做的不是新增更多风控阈值，而是：

1. 启动期显式实盘解锁。
2. 未完成订单恢复过滤。
3. 批次化组合执行器。
4. 规则命中审计。

这四项完成之后，现有系统才算从“有一些规则”进入“有完整规则系统”的状态。

## 12. 规则库详细设计

前面的章节更多是在回答“当前系统有哪些规则入口、哪些规则已经落地、哪些规则还缺失”。

但如果目标是后续做“可配置规则系统”，仅知道入口和缺口还不够，还必须先回答另外三个问题：

1. 到底有哪些规则类型可以进入规则库。
2. 这些规则类型之间应该如何组合。
3. 规则配置的最小表达单元应该长什么样。

这一节的目标不是再列一份门禁链，而是定义一套可以长期演化的规则库语言，让使用者先熟悉“规则材料库”，再逐步拼出自己的交易规则。

### 12.1 为什么要先做规则库

如果一开始就直接做“策略配置页”，很容易把规则系统做成一堆表单字段和几个 if/else 开关。那样的问题是：

1. 使用者不知道系统到底支持哪些规则形态。
2. 新增规则时总要改页面、改存储、改执行代码。
3. 规则之间无法统一组合，只能靠页面硬编码拼接。
4. 后续很难沉淀出自己的规则语言。

所以更稳的路径不是先做页面，而是先把规则库定义清楚：

1. 先有规则原子类型。
2. 再有规则组合方式。
3. 再有标准输出动作。
4. 最后才是页面去编辑这些规则。

可以把它理解成：

1. 规则库负责提供“积木”。
2. 规则配置负责定义“怎么搭”。
3. 页面编辑器只是“搭积木的界面”。

### 12.2 规则库的四层结构

建议把规则库拆成四层，而不是把所有条件都揉成一个大 JSON。

#### 第一层：规则原子

规则原子是最小判断单元，负责回答一个很小的问题，例如：

1. 当前价格是否突破前高。
2. 当前成交量是否超过均量的 1.5 倍。
3. 当前涨幅是否低于 9.9%。
4. 当前观察时长是否超过 120 分钟。
5. 当前标的是否仍然在龙头列表里。

这一层不关心交易动作，只关心真假、数值、状态。

#### 第二层：规则组

规则组负责把多个规则原子按逻辑关系组织起来，例如：

1. 突破买入组 = 价格突破 AND 成交量放大 AND 非涨停。
2. 放弃关注组 = 超时未突破 OR 量能萎缩 OR 被新龙头替代。
3. 强趋势候选组 = 中期趋势向上 AND 行业排名前 20% AND 波动率不过高。

这一层开始产生“业务语义”。

#### 第三层：阶段规则

阶段规则负责把规则组挂到交易生命周期的某个阶段，例如：

1. 观察阶段规则。
2. 候选阶段规则。
3. 入场阶段规则。
4. 加仓阶段规则。
5. 减仓阶段规则。
6. 退出阶段规则。
7. 放弃关注阶段规则。

同样的规则组，在不同阶段可能产生不同动作。

#### 第四层：规则剧本

规则剧本是完整策略的规则编排，负责回答：

1. 先做哪些筛选。
2. 再做哪些候选评分。
3. 何时从观察切到候选。
4. 何时从候选切到入场。
5. 何时从持仓切到退出。

也就是说，真正可运行的策略不是一条规则，而是一套阶段化规则剧本。

### 12.3 规则原子的标准分类

建议把规则原子固定成下面十二大类。这样做的好处是，后续新增规则时，优先判断它属于哪一类，而不是再随手发明一种新结构。

#### A. 比较型规则

最基础，也最常见。

含义：

1. 左值和右值做数值比较。
2. 常见操作符为 `>`、`>=`、`<`、`<=`、`==`、`!=`。

典型例子：

1. 当前涨幅 > 5%。
2. 成交额 / 均值 > 1.5。
3. 当前价 > 前高。
4. 当前回撤 >= 8%。

适用场景：

1. 突破。
2. 放量。
3. 涨跌幅。
4. 仓位上限。
5. 风险阈值。

#### B. 区间型规则

含义：

1. 判断一个值是否落在某个区间。
2. 可以表达“必须在范围内”或“必须不在范围内”。

典型例子：

1. 换手率在 3% 到 12% 之间。
2. 波动率不在极低和极高区间。
3. 回撤在 5% 到 10% 之间时进入警戒区。

适用场景：

1. 风险分层。
2. 活跃度筛选。
3. 温度带判断。

#### C. 集合型规则

含义：

1. 判断某个值是否属于一个集合。
2. 适合白名单、黑名单、股票池、行业池、概念池。

典型例子：

1. 标的属于自定义股票池。
2. 标的不属于 ST 黑名单。
3. 行业属于重点方向列表。
4. 当前事件标签属于可交易事件集合。

适用场景：

1. 股票池。
2. 风险标签。
3. 行业主题约束。

#### D. 枚举状态型规则

含义：

1. 判断当前状态是否等于某个枚举值。
2. 适合表达阶段、市场状态、持仓状态、规则状态。

典型例子：

1. 市场状态 == frozen。
2. 标的状态 == watchlist。
3. 当前仓位状态 == partial_take_profit。
4. 运行模式 == simulation。

适用场景：

1. 状态机。
2. 策略阶段切换。
3. 风控模式切换。

#### E. 事件型规则

含义：

1. 由离散事件触发，而不是由连续数值触发。
2. 事件可以来自行情、公告、板块轮动、成交回报、外部信号。

典型例子：

1. 被新龙头替代。
2. 财报公告已发布。
3. 涨停炸板事件发生。
4. 出现第一次大单抢筹事件。

适用场景：

1. 龙头切换。
2. 情绪转折。
3. 公告驱动。
4. 执行异常处理。

#### F. 计时型规则

含义：

1. 判断某状态持续了多久。
2. 可以是绝对时间，也可以是 bar 数、交易日数、分钟数。

典型例子：

1. 进入观察池后超过 120 分钟仍未突破。
2. 卖出后冷却 3 个交易日。
3. 连续涨停状态超过 2 天。
4. 挂单超过 30 秒未成交。

适用场景：

1. 观察期。
2. 冷却期。
3. 持仓超时。
4. 执行超时。

#### G. 计数型规则

含义：

1. 判断某事件或条件在窗口内发生了多少次。
2. 适合连续出现、累计出现、命中次数限制。

典型例子：

1. 最近 10 天涨停次数 >= 3。
2. 连续两次试探突破失败。
3. 一天内拒单次数 >= 2。
4. 连续 3 笔亏损后停手。

适用场景：

1. 形态强化。
2. 异常控制。
3. 连续亏损保护。

#### H. 序列型规则

含义：

1. 不仅关心事件是否出现，还关心出现顺序。
2. 是做形态规则和行为剧本时非常重要的一类。

典型例子：

1. 先放量，再突破，再回踩不破。
2. 先跌停打开，再弱转强上板。
3. 先减仓批次成交，再允许买入批次启动。
4. 先出现预警，再出现加速放量，最后确认入场。

适用场景：

1. K 线形态。
2. 龙头接力。
3. 执行推进。

#### I. 交叉型规则

含义：

1. 判断两个时间序列是否发生交叉。
2. 常见于均线、指标、资金流、价量关系。

典型例子：

1. 5 日线上穿 20 日线。
2. 价格上穿平台上沿。
3. 成交量均线下穿活跃阈值。

适用场景：

1. 趋势确认。
2. 反转确认。
3. 风险触发。

#### J. 排名型规则

含义：

1. 判断某标的在某集合中的相对位置。
2. 非常适合“龙头、强弱、行业领先、因子排序”这类语义。

典型例子：

1. 板块涨幅排名前 3。
2. 个股相对强弱位于行业前 10%。
3. 因子评分位于候选池前 20%。

适用场景：

1. 龙头识别。
2. 候选筛选。
3. 组合排序。

#### K. 评分型规则

含义：

1. 不直接输出真假，而是输出分值。
2. 适合趋势、质量、情绪、风险多个维度加权。

典型例子：

1. 趋势分 = 突破 + 均线斜率 + 相对强弱。
2. 关注分 = 龙头属性 + 放量程度 + 市场热度。
3. 风险分 = 波动率 + 回撤 + 相关性。

适用场景：

1. 候选排序。
2. 多维打分。
3. 仓位动态调节。

#### L. 状态迁移型规则

含义：

1. 条件满足后，不是直接买卖，而是切换对象状态。
2. 这是“可配置规则系统”里最容易被忽略、但最重要的一类。

典型例子：

1. 从 `watchlist` 切到 `candidate_entry`。
2. 从 `candidate_entry` 切到 `ready_to_buy`。
3. 从 `holding` 切到 `cooldown`。
4. 从 `normal` 切到 `cautious`。

适用场景：

1. 策略流程控制。
2. 账户状态机。
3. 执行流程编排。

### 12.4 规则输出动作的标准库

如果规则库只是输出真假，后面很快会不够用。建议固定一版动作库。

#### 基础动作

1. `pass`：放行。
2. `block`：阻断。
3. `warn`：提示但不阻断。
4. `score`：输出分数。

#### 交易动作

1. `watch`：加入观察。
2. `unwatch`：取消关注。
3. `candidate_entry`：进入候选买点。
4. `candidate_exit`：进入候选卖点。
5. `open`：开仓意图。
6. `add`：加仓意图。
7. `reduce`：减仓意图。
8. `exit`：退出意图。

#### 改写动作

1. `rewrite_position`：改写目标仓位。
2. `rewrite_price_mode`：改写委托方式。
3. `rewrite_priority`：改写执行优先级。
4. `rewrite_batch`：改写执行批次。

#### 状态动作

1. `state_switch`：切换状态。
2. `cooldown`：进入冷却期。
3. `freeze`：冻结新开仓。
4. `halt`：停止交易。

#### 标记动作

1. `tag`：打标签，例如 `leader`、`weak_leader`、`replacement_risk`。
2. `note`：记录说明。
3. `audit`：记录命中信息。

这意味着同一套规则库不仅能回答“要不要买”，还能回答：

1. 现在属于什么阶段。
2. 是否继续关注。
3. 如果可以买，应该怎么买。
4. 如果不能买，是暂时不能还是彻底放弃。

### 12.5 规则组合方式

你给的 `AND` / `OR` 只是第一层。真正可用的规则组合至少要支持下面八类。

#### A. 布尔组合

1. `AND`
2. `OR`
3. `NOT`
4. `XOR`

用途：

1. 最基础的条件树。
2. 适合入场、放弃、过滤条件。

#### B. 多数决组合

形式：

1. `N_OF_M`
2. `AT_LEAST`
3. `AT_MOST`

典型例子：

1. 5 个强势条件里满足 3 个即可入候选。
2. 3 个放弃条件里出现任意 2 个就取消关注。

用途：

1. 避免条件过硬导致完全没有样本。
2. 适合模糊判断和多维评分前置。

#### C. 顺序组合

形式：

1. `SEQUENCE`
2. `STEP_CHAIN`

典型例子：

1. 先放量，再突破，再回踩确认。
2. 先进入观察，再转候选，再触发买点。

用途：

1. 龙头接力。
2. 波段突破。
3. 执行推进。

#### D. 时间窗组合

形式：

1. `WITHIN_WINDOW`
2. `SUSTAIN_FOR`
3. `EXPIRE_AFTER`

典型例子：

1. 价格突破后 30 分钟内必须持续站稳。
2. 观察超过 120 分钟仍未突破则放弃。
3. 候选信号超过 2 个交易日失效。

用途：

1. 观察期。
2. 突破确认。
3. 失效管理。

#### E. 计数窗组合

形式：

1. `COUNT_IN_WINDOW`
2. `CONSECUTIVE`

典型例子：

1. 连续 2 次缩量回踩都不破位。
2. 最近 5 个 bar 中至少 3 个 bar 放量。

#### F. 评分聚合组合

形式：

1. `WEIGHTED_SUM`
2. `MAX_SCORE`
3. `MIN_SCORE`
4. `AVERAGE_SCORE`

典型例子：

1. 突破分、量能分、板块分、龙头分汇总为总关注分。
2. 风险分高于阈值才允许开仓。

#### G. 状态机组合

形式：

1. `FROM_STATE -> TO_STATE`
2. `ALLOWED_TRANSITIONS`

典型例子：

1. `watchlist -> candidate_entry -> ready_to_buy -> holding -> cooldown`
2. `leader -> replaced -> abandoned`

#### H. 优先级覆盖组合

形式：

1. `priority`
2. `override`
3. `first_match`
4. `highest_severity`

典型例子：

1. 放弃关注规则优先级高于入场规则。
2. 风险冻结状态高于所有买入规则。
3. 退出规则高于加仓规则。

### 12.7 面向策略使用者的规则类型视图

如果目标是让人“先熟悉规则库”，建议不要只按技术类型展示，还要按使用者视角再投影一遍。

建议在规则库界面或文档里同时提供以下六个视图：

1. 按交易阶段看：观察、候选、入场、加仓、减仓、退出、放弃。
2. 按规则类型看：比较、事件、计时、序列、评分、状态。
3. 按交易风格看：突破、低吸、趋势、龙头、波段、组合。
4. 按对象层级看：市场、板块、标的、持仓、组合、账户。
5. 按动作看：关注、打分、阻断、开仓、退出、切状态。
6. 按复杂度看：基础规则、组合规则、状态机规则、执行规则。

这样做的好处是，使用者即使还不会写规则，也能先通过目录熟悉“系统里原来支持这些规则材料”。

### 12.8 推荐的 DSL 结构

规则 DSL 不建议一开始就做得太自由。建议先固定成五层。

#### 第一层：规则集

```json
{
    "rule_set_id": "dragon_breakout_v1",
    "name": "龙头突破规则集",
    "version": 1,
    "phases": []
}
```

#### 第二层：阶段

```json
{
    "phase": "candidate_entry",
    "logic": "FIRST_MATCH",
    "rule_groups": []
}
```

#### 第三层：规则组

```json
{
    "group_id": "breakout_entry_group",
    "name": "突破买入条件",
    "logic": "AND",
    "priority": 90,
    "sub_rules": []
}
```

#### 第四层：规则原子

```json
{
    "rule_id": "price_break_prev_high",
    "name": "价格突破前高",
    "type": "comparison",
    "left": {"field": "price.last"},
    "operator": ">",
    "right": {"field": "price.prev_high"}
}
```

#### 第五层：动作

```json
{
    "on_match": {
        "action": "candidate_entry",
        "payload": {
            "entry_style": "breakout",
            "score_bonus": 12
        }
    },
    "on_fail": {
        "action": "pass"
    }
}
```

### 12.9 建议支持的规则原子字段模板

建议固定每条规则原子至少包含下面这些字段：

```json
{
    "rule_id": "unique_rule_id",
    "name": "规则名称",
    "type": "comparison|range|set|state|event|timer|count|sequence|cross|rank|score|transition",
    "enabled": true,
    "priority": 0,
    "scope": "market|sector|symbol|position|portfolio|account",
    "operator": ">",
    "left": {},
    "right": {},
    "window": {},
    "tags": ["breakout", "entry"],
    "on_match": {},
    "on_fail": {}
}
```

其中：

1. `type` 负责定义规则属于哪种原子类型。
2. `scope` 负责定义它作用于哪一层对象。
3. `window` 负责定义时间窗、bar 窗、次数窗。
4. `on_match` 和 `on_fail` 负责定义规则结果。

```json
                            "left": {"field": "symbol.replaced_by_new_leader"},
                            "right": {"value": true}
                        }
                    ],
                    "on_match": {
                        "action": "unwatch",
                        "payload": {
                            "state": "abandoned",
                            "reason": "candidate invalidated"
                        }
                    }
                }
            ]
        }
    ]
}
```

这个示例说明了一件事：

你想做的规则系统远不止“一个条件列表”，而是：

1. 阶段。
2. 规则组。
3. 规则原子。
4. 命中动作。
5. 状态流转。

### 12.11 第一批建议内置的规则模板

为了让使用者快速熟悉规则库，建议第一批直接提供模板，而不是让用户自己从空白开始写。

建议先内置以下模板：

1. 突破关注模板。
2. 突破回踩确认模板。
3. 龙头接力模板。
4. 放弃关注模板。
5. 固定止损模板。
6. 分批止盈模板。
7. 持仓超时退出模板。
8. 市场冻结模板。
9. 股票池准入模板。
10. 组合仓位约束模板。

每个模板都应包含：

1. 规则意图说明。
2. 适用阶段。
3. 规则组示例。
4. 可调参数。
5. 默认值。
6. 典型风险提示。

### 12.12 规则库的学习路径

如果目标是“我先熟悉规则库，再做自己的可配置规则”，建议学习路径固定成三步。

#### 第一步：先只看规则目录

先不要写规则。先按下面几个问题熟悉规则库：

1. 系统支持哪些规则原子。
2. 系统支持哪些动作。
3. 系统支持哪些阶段。
4. 系统支持哪些组合方式。

#### 第二步：先改模板参数

先不要从零造规则。优先做：

1. 改阈值。
2. 改时间窗。
3. 改逻辑关系。
4. 改优先级。

这样能先建立“这个规则库大概怎么运转”的感觉。

#### 第三步：再自己拼规则组

等熟悉模板后，再开始做：

1. 自己建新的规则组。
2. 自己定义新的阶段剧本。
3. 最后再决定是否要扩新的原子操作符。

### 12.13 对当前项目的具体建议

对这个项目来说，最合适的第一批规则库不应该先从 Execution Rule 开始，而应该先从更容易理解、也更容易配置的交易业务规则开始。

建议第一批优先做：

1. 股票池准入规则库。
2. 观察/放弃关注规则库。
3. 突破入场规则库。
4. 止损/止盈退出规则库。
5. 组合仓位约束规则库。

原因是：

1. 这些规则业务语义直观。
2. 容易做成模板。
3. 用户容易理解和调整。
4. 比执行编排规则更适合先训练规则库的表达能力。

执行编排规则当然很重要，但它更适合在第二阶段接到 C++ live 执行链，而不是作为第一批面向用户学习的规则库入口。

### 12.14 最终结论

你现在想要的不是“列出当前已有门禁规则”，而是“先有一份完整规则库地图，让人知道可配置规则系统到底能长成什么样”。

从这个目标出发，规则库至少要先回答四件事：

1. 系统支持哪些规则原子。
2. 系统支持哪些规则组合方式。
3. 系统支持哪些动作和状态切换。
4. 系统支持哪些阶段化规则模板。

只有先把这四件事固定下来，后面的“用户自定义规则”“规则编辑器”“规则模板中心”“规则回放验证”才有稳定地基。

## 13. 金融市场术语驱动的规则词库设计

前一节解决的是“规则库结构怎么搭”。

这一节解决的是另外一个更贴近交易实务的问题：

如果规则库最终是给交易者用的，那么它不能只停留在 `comparison`、`timer`、`event` 这种技术名词层面，还必须能对接金融市场里真实被使用的动作术语、盘口术语、资金术语和策略术语。

也就是说，规则系统最终不应只会表达：

1. `price.last > price.prev_high`
2. `volume.ratio_to_avg > 1.5`
3. `watch.elapsed_minutes >= 120`

它还要能表达更接近交易者日常语言的东西，例如：

1. 放量突破。
2. 缩量回踩。
3. 弱转强。
4. 分歧转一致。
5. 炸板回封。
6. 龙头被卡位。
7. 情绪退潮。
8. 反包失败。
9. 跌破承接。
10. 抢跑止盈。

如果没有这一层金融术语映射，规则库就会变成“程序员能配置，但交易者看不懂”的系统。

### 13.1 规则库需要两套语言

建议明确区分两套语言，而不是只保留一种表达。

#### A. 内核语言

这是给系统执行用的语言，例如：

1. `comparison`
2. `event`
3. `sequence`
4. `count_in_window`
5. `state_switch`

它要求精确、结构化、便于序列化。

#### B. 交易语言

这是给人理解和配置用的语言，例如：

1. 打板。
2. 半路。
3. 低吸。
4. 回封。
5. 反包。
6. 卡位。
7. 补涨。
8. 走弱。
9. 退潮。
10. 承接不足。

它要求贴近市场语义。

建议最终架构是：

1. 交易语言用于规则模板命名、页面显示和策略说明。
2. 内核语言用于真实配置存储和执行。
3. 两者之间通过“术语映射层”相连。

### 13.2 金融市场术语词库的六大域

建议把术语词库按下面六大域组织，而不是只按技术类型组织。

#### A. 行情结构术语

这是最基础的一层，主要描述价格、涨跌、形态和波动结构。

建议至少收录：

9. 放量滞涨。
10. 高开低走。
11. 低开高走。
12. 横盘震荡。
13. 平台整理。
14. 趋势转弱。
15. 趋势修复。

这类术语主要映射到：

1. 比较型规则。
2. 交叉型规则。
3. 序列型规则。
4. 区间型规则。

#### B. 量价行为术语

描述成交量、换手和价格之间的联动关系。

#### C. 题材与龙头术语

这是 A 股短线和强势股体系里最关键的一层。如果系统不支持这一层，很多交易者会觉得规则库“没有灵魂”。

### 13.3 术语不应只做名字，还要做标准语义

规则库里不能只是有个名字叫“弱转强”，然后每个人理解都不一样。每个术语必须至少定义三件事：

1. 标准业务含义。
2. 推荐的规则结构。
3. 可调参数。

例如：

#### 术语：弱转强

标准含义建议：

1. 前一阶段曾经转弱。
2. 当日或当前周期重新出现资金承接和价格修复。
3. 最终重新回到可进攻状态。

推荐规则结构：

1. 前一日或前一阶段存在走弱事件。
2. 今日高开或快速修复关键价位。
3. 成交量重新放大。
4. 板块情绪未进入退潮。

可调参数：

1. 修复阈值。
2. 量能阈值。
3. 时间窗。
4. 情绪阈值。

如果做不到这一层，术语只会变成一个好听的标签，而不是可复用规则模板。

### 13.8 规则库不只是“条件库”，还应该是“动作库”

金融市场里很多动作术语本身就代表一种执行意图，而不仅仅是条件。例如：

1. 打板。
2. 半路。
3. 低吸。
4. 抢跑。
5. 做 T。
6. 回封确认后打回封。

所以规则库应该明确区分三类模板：

#### A. 识别型模板

回答“现在是什么状态”。

例如：

1. 龙头识别。
2. 分歧识别。
3. 退潮识别。

#### B. 决策型模板

回答“现在该不该做”。

例如：

1. 是否进入观察。
2. 是否允许开仓。
3. 是否放弃关注。

#### C. 动作型模板

回答“如果做，怎么做”。

例如：

1. 打板还是半路。
2. 一次性下单还是分批。
3. 试错仓还是标准仓。
4. 止盈是分批还是一次性。

### 13.9 面向金融术语的页面设计建议

如果后续真要做规则配置页，建议页面不要先展示“comparison / timer / event”。

更自然的入口应该是：

1. 我想做“突破买入”。
2. 我想做“弱转强”。
3. 我想做“炸板回封”。
4. 我想做“龙头被替代后放弃”。
5. 我想做“分批止盈”。

然后页面再把这些术语模板展开成底层可调规则项。也就是说：

1. 用户入口用市场语言。
2. 系统内部仍用结构化规则语言。

### 13.10 对当前项目最重要的补充结论

如果这个项目后续要做自己的可配置规则系统，那么规则库设计不能只围绕“通用规则引擎”展开，还必须明确支持金融市场，尤其是 A 股交易里高频出现的动作术语和行为术语。

更具体地说，规则库至少还要补上三类东西：

1. 金融术语词典。
2. 术语到规则模板的映射。
3. 术语模板到执行动作的映射。

只有这样，规则系统才不是一个抽象的技术框架，而是一套交易者真正能拿来学习、理解和组合的规则材料库。
