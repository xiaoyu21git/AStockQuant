# 策略系统与策略回测抽象重构需求规格说明书

更新时间：2026-05-24

> 说明：本文是重构需求规格，保留了形成当时的旧策略回测链命名，不应直接视为当前代码现状。当前仓库中旧 `StrategyBacktestService` 已删除，策略回测主链已转向 typed `BacktestRequest` / `BacktestApplicationService` 方向。

## 1. 文档目的

本文不是实现方案草稿，也不是局部修复记录，而是一份可直接交给负责抽象重构的工程负责人使用的需求规格说明书。

本文要解决的问题是：

1. 当前策略系统、策略回测系统、运行时规则系统之间存在大量字符串兼容、QVariantMap 动态拼装、旧字段别名回退和跨层语义泄漏，导致功能虽然可用，但可维护性、可验证性、可扩展性和重构成本都明显恶化。
2. 后续需要有人从架构层重新抽象这些系统，但必须先有一份完整、明确、可执行、可验收的需求说明，避免“边做边猜”的二次返工。

本文的目标是把以下内容一次性讲清楚：

1. 当前系统涉及哪些模块。
2. 这些模块当前分别承担什么职责。
3. 当前设计中哪些地方已经形成结构性债务。
4. 哪些部分必须重建，哪些部分应保留。
5. 目标抽象模型必须满足什么合同和约束。
6. 重构完成后应达到哪些功能、性能、可维护性和验收要求。

## 2. 适用范围

本文覆盖以下系统链路：

1. 策略定义、创建、编辑、复制、导入导出。
2. 策略仓储与数据库持久化。
3. 策略缓存、展示模型、视图同步。
4. 策略回测页面、回测控制器、回测服务、回测引擎。
5. 策略回测结果生成、结果回写、结果展示。
6. 策略运行时规则评估、事件驱动信号、自动下单联动。
7. 规则模板绑定、运行时模板评估、组合调仓执行。
8. 股票池、指数成分股、策略上下文、市场环境与风险配置联动。

本文不覆盖以下范围：

1. 数据库从 MySQL 到 PostgreSQL 的底层迁移实现。
2. 因子引擎本身的数学定义、因子生产逻辑和因子数据清洗内部算法。
3. 交易柜台接入、券商 API 适配等外部集成细节。

## 3. 背景与现状结论

### 3.1 背景

当前系统是在功能持续叠加过程中逐步形成的，前期优先满足页面可用、回测能跑、结果能展示、策略能存取，后期又不断叠加组合因子、规则模板、市场环境、运行时策略评估和真实交易联动。由于早期没有统一的强类型领域模型与清晰的边界分层，很多功能演进依赖了以下做法：

1. 以 QVariantMap 为主合同在多层之间传递数据。
2. 以字符串键名表示真实业务语义。
3. 通过多个别名字段兼容旧页面、旧策略、旧结果快照。
4. 在 service/controller 内同时做输入校验、结构解析、默认值补齐、兼容回退、结果合并。
5. 把 UI 展示语义、研究回测语义、执行运行时语义混在同一个 map 中。

### 3.2 当前现状的核心判断

基于当前源码，现状可以概括为：

1. 核心执行内核并未彻底失效，仍然具有保留价值。
2. 但系统边界合同和装配层已经明显失控，属于必须重构的结构层问题，不再适合继续通过局部补丁长期维持。

### 3.3 当前最主要的结构性问题

#### 3.3.1 动态 map 作为主合同

当前策略系统和策略回测系统存在大面积的 QVariantMap / QVariantList 主合同传递，导致：

1. 类型约束弱。
2. 调用方和被调用方都依赖约定俗成的字符串键名。
3. 编译期无法发现字段缺失、字段误拼、字段歧义。
4. 重构时无法安全批量迁移。

#### 3.3.2 字符串键承载真实业务语义

当前大量业务语义依赖字符串键和字符串值，例如：

1. 策略类型、策略子类型、执行类型、规则绑定、股票池字段。
2. backtest_runtime、rule_profile、execution_policy、strategy_scope_context 等嵌套结构。
3. symbol_pool、backtest_symbol_pool、linked_stock_pool_symbols 等并行字段。
4. 旧字段名和新字段名并行存在，调用方经常需要双读或多读。

#### 3.3.3 多层混合吸收兼容逻辑

当前兼容逻辑分散在：

1. QML 页面。
2. StrategyService。
3. StrategyBacktestController。
4. StrategyStructureResolverSet。
5. ResultConfigBuilder。
6. 仓储层。

这会直接导致：

1. 同一个语义在多处被重复归一化。
2. 新需求很难判断“正确修改入口”在哪里。
3. 回归风险高，容易出现一处改了另一处仍在回退。

#### 3.3.4 研究语义与执行语义混用

当前很多结构同时承载：

1. 页面展示上下文。
2. 策略配置保存语义。
3. 回测研究语义。
4. 运行时执行语义。
5. 结果回写与历史快照语义。

这种混用已经在策略回测结果回写、运行时规则恢复、策略参数编辑恢复等路径上形成显著复杂度。

#### 3.3.5 结果回写链仍然是动态拼装

当前回测结果到策略绩效回写链依然大量依赖：

1. JS 侧 build payload。
2. service 侧 merge map。
3. repository 侧写 JSON。
4. 读取侧再从结果历史中倒推恢复策略可编辑结构。

这条链虽然能工作，但已经明显不适合作为长期主模型。

## 5. 目标重构原则

后续抽象重构必须遵守以下原则。任何实现方案若违背这些原则，应视为不满足本文需求。

### 5.1 强类型优先

1. C++ 内部领域语义必须优先使用 enum、struct、class、typed value object。
2. 不允许再以 QString、std::string 或 QVariant 承担真实业务类型判断。
3. 字符串只允许保留在受控边界：数据库文本字段、JSON 序列化字段名、QML 展示文案、外部接口协议字段。

### 5.2 单一真源

1. 同一业务语义只能有一个 canonical 字段。
2. 不允许长期保留同义兼容字段并行写入。
3. 兼容读取若必须存在，必须集中在单一 adapter 层，不得扩散到 service、controller、engine 多处。

### 5.3 边界清晰

必须明确分离以下边界：

1. UI 展示模型。
2. 应用服务输入模型。
3. 领域配置模型。
4. 执行时运行模型。
5. 持久化模型。
6. 结果展示模型。

### 5.4 失败显式化

1. 缺失关键元信息时必须直接失败。
2. 不允许继续通过猜测、字符串回退、隐式默认值来掩盖合同缺失。
3. 任何需要上下文才能正确执行的链路，必须在入口校验齐全。

### 5.5 增量替换而非爆炸式推翻

1. 不要求一次性重写所有执行内核。
2. 允许保留已有可工作的回测引擎与数据提供器。
3. 但要求通过新的强类型合同逐步绞杀旧 map/string 链路。

## 6. 重构范围划分

## 6.1 必须重建的层

以下层属于本次抽象重构的核心范围，必须重建：

1. 策略领域主合同。
2. 策略回测请求主合同。
3. 策略回测结果主合同。
4. 策略装配层和结构解析层。
5. 策略结果回写与读取恢复链。
6. 策略运行时规则输入与输出合同。
7. 仓储层主 DTO 与持久化 adapter。

## 6.2 原则上保留的层

以下层原则上不做推倒重写，但要适配新合同：

1. 行情数据提供器。
2. 因子数据提供器。
3. BacktestEngine 核心撮合与绩效计算框架。
4. 线程池与后台执行框架。
5. 事件总线基础设施。

## 7. 目标系统分层要求

目标系统必须拆成下面七层，并且每层职责清晰、禁止越层吸收兼容逻辑。

### 7.1 展示层

职责：

1. 收集用户输入。
2. 显示策略与回测结果。
3. 不承载业务归一化真逻辑。

要求：

1. QML 不得再保存真实业务字符串语义作为主状态。
2. QML 仅使用可序列化的简单展示状态。
3. QML 只允许调用 bridge 暴露的显式接口，不允许自己构造含大量隐式语义的散装 map。

### 7.2 展示适配层

职责：

1. 在 QML DTO 与应用层 DTO 之间做单向转换。
2. 吸收必要的 UI 兼容差异。

要求：

1. 若必须兼容旧字段，兼容逻辑只能集中在这里。
2. 不允许兼容逻辑继续散落到 controller、service、repository 中。

### 7.3 应用服务层

职责：

1. 编排调用。
2. 事务组织。
3. 缓存与仓储协作。
4. 事件通知。

要求：

1. 不得再以 QVariantMap 作为主模型在内部横向传递。
2. 必须操作强类型请求对象和结果对象。
3. service 只做编排，不做多轮别名解析。
4. `QVariantMap` / `QVariantList` 只允许停留在 UI 层输入输出边界；UI 层以外任何模块出现这两类类型都视为违规设计，而不是可接受适配。

### 7.4 领域模型层

职责：

1. 定义策略、回测、规则、股票池、绩效、快照等核心模型。
2. 定义枚举、值对象、约束和不变量。

要求：

1. 领域模型必须是纯类型模型。
2. 不允许 QVariantMap 成为领域实体字段主容器；受控扩展点也必须优先使用显式类型对象或 variant 封装，不得直接把 QVariantMap 留在 domain 主类型里。
3. 所有领域对象必须能做显式校验。
4. 禁止再引入 Normalized 或 Normalization 命名的中间兼容模型承接旧字段；旧 UI 结构必须在 UI 边界一次性变成最终 typed 对象，不允许先进一个“归一化记录”再二次装配。

### 7.5 装配与转换层

职责：

1. 把旧结构、持久化结构或展示结构转换为领域模型。
2. 把领域模型转换为执行模型或展示模型。

要求：

1. 所有旧字段兼容和别名吸收只能集中在此层。
2. 必须有清晰的输入输出边界，不得隐式依赖外部全局状态。

### 7.6 执行层

职责：

1. 执行回测。
2. 执行运行时规则评估。
3. 计算绩效。

要求：

1. 执行层只消费强类型配置对象。
2. 执行层不得知道 QML 字段名或数据库字段名。
3. 执行层不得再通过字符串 subtype 猜业务分支。

### 7.7 持久化层

职责：

1. 持久化 StrategyData 等 DTO。
2. 负责数据库 schema 与领域模型的边界转换。

要求：

1. 持久化层允许处理数据库文本字段，但不得让文本语义向上层泄漏。
2. 仓储层必须提供强类型接口，不再以 QVariantMap 作为仓储主合同。

## 8. 目标领域模型需求

### 8.1 策略主模型

系统必须定义一个明确的 StrategyAggregate 或同等语义的强类型模型，至少包含：

1. 标识信息：strategyId、strategyCode、strategyName。
2. 身份语义：storedType、behaviorKind、executionKind。
3. 生命周期：status。
4. 运行属性：assetTypeIndex、timeFrameIndex、riskLevelIndex。
5. 结构化策略配置：ruleProfile、executionPolicy、backtestAssumptions、strategyScopeContext、factorOverlay。
6. 结果信息：performanceSummary、latestBacktestSnapshot、backtestHistory。
7. 元信息：description、version、author、language、createdAt、updatedAt。

要求：

1. strategy_type、sub_type 等字符串不再是主语义字段。
2. 任何展示所需字符串，必须由强类型字段派生。

### 8.2 回测请求模型

系统必须定义 BacktestRequest 或同等语义对象，至少包含：

1. strategy identity
2. strategy spec
3. universe spec
4. market environment spec
5. cost spec
6. risk spec
7. execution spec
8. factor overlay spec
9. dataset/data source spec
10. runtime options

要求：

1. 不允许继续使用 strategyParams 和 strategyOptions 两个 string map 作为主请求合同。
2. 若某些执行器暂时仍需要 map，应在进入执行器前由 adapter 生成临时内部 map，且必须是单向转换。

### 8.3 回测结果模型

系统必须定义 BacktestResultDto 或同等语义对象，至少包含：

1. config snapshot
2. performance summary
3. trade statistics
4. risk metrics
5. time series
6. trade records
7. universe resolution summary
8. rule template summary
9. diagnostics

要求：

1. 回测结果不得再依赖“先序列化成 JSON，再反序列化成 QVariantMap”作为主输出模型。
2. 对 QML 的输出转换必须通过展示 adapter 完成。

### 8.4 运行时规则评估模型

系统必须定义 RuntimeStrategyContext、RuntimeMarketContext、RuntimeEvaluationResult 等显式对象。

要求：

1. 运行时规则输入必须来自强类型 snapshot，而不是散装 strategy map。
2. 自动下单请求也必须是强类型订单请求对象，之后再适配到外部 bridge 接口。

## 9. 各子系统详细需求

### 9.1 策略定义与生命周期系统

#### 9.1.1 功能需求

1. 支持创建、更新、复制、删除、归档、激活、停用策略。
2. 支持按强类型身份字段检索策略，而不是按 strategy_type 文本猜测。
3. 支持状态机约束，禁止非法状态迁移。

#### 9.1.2 合同需求

1. 生命周期状态必须统一为单一枚举合同。
2. 内部逻辑必须只认 status enum 或 statusIndex。
3. 任何 ACTIVE、INACTIVE 等文本只允许在数据库边界或展示层存在。

#### 9.1.3 禁止事项

1. 不允许继续通过 strategy.value("status") 的文本判断核心行为。
2. 不允许同时保留 status 和 statusIndex 两个长期业务真源。

### 9.2 策略仓储与持久化系统

#### 9.2.1 功能需求

1. 仓储接口必须以强类型 StrategyData 或 StrategyAggregateData 作为主合同。
2. 支持 find/save/update/remove/count/exists/updateStatus/updateParameters/updatePerformance。
3. 支持读取历史库存策略并显式完成旧数据迁移或失败上报。

#### 9.2.2 持久化要求

1. 数据库文本字段允许继续存在，但仓储层必须负责隔离。
2. parameters JSON 只能承载明确的嵌套结构，不允许继续作为任意散装垃圾桶。
3. performance_metrics 必须有明确 schema，而不是任意增量 merge。

#### 9.2.3 迁移要求

1. 旧 strategy.parameters 中残留的兼容字段必须定义迁移策略。
2. 迁移完成前，兼容读取集中在单一 persistence adapter 中。
3. 迁移完成后，旧字段必须删除，不得永久双写。

### 9.3 策略装配与结构解析系统

#### 9.3.1 问题定义

当前 StrategyStructureResolverSet 的价值在于把多个来源的参数收敛成结构化快照，但它当前承担了过多长期兼容别名吸收责任。

#### 9.3.2 目标要求

1. 必须保留“结构化解析”这个职责。
2. 但必须把“长期兼容字段吸收”从主业务路径中隔离出来。
3. 新系统应将解析分成两步：
   1. legacy normalization
   2. canonical structure assembly

#### 9.3.3 具体要求

1. LegacyNormalizationAdapter 负责旧字段名吸收。
2. StrategyStructureAssembler 只负责 canonical 结构生成。
3. assembler 输入必须是已归一化的数据对象，而不是原始 QML map。

### 9.4 策略回测请求装配系统

#### 9.4.1 功能需求

1. 从策略对象、页面运行参数、风险配置、市场环境配置组装出 BacktestRequest。
2. 支持标准策略执行与组合因子加权执行。
3. 支持显式 universe 解析和数据源解析。

#### 9.4.2 合同要求

1. createConfig 不得再直接向 string map 写入几十个键值对。
2. 必须拆成多个子对象构造器：
   1. buildIdentitySpec
   2. buildUniverseSpec
   3. buildExecutionSpec
   4. buildRiskSpec
   5. buildCostSpec
   6. buildFactorOverlaySpec
   7. buildRuntimeOptionSpec

#### 9.4.3 错误处理要求

1. 执行种类缺失时必须失败。
2. 股票池解析为空时必须失败。
3. 组合权重配置不完整时必须失败。
4. 市场环境、数据源、日期区间非法时必须失败。

### 9.5 回测执行系统

#### 9.5.1 功能需求

1. 支持 Standard 执行种类。
2. 支持 FactorWeightedPortfolio 执行种类。
3. 后续应允许继续扩展 executionKind，而不是继续拼 strategy_subtype 文本。

#### 9.5.2 核心约束

1. 执行路径分发必须优先依据 executionKind。
2. behaviorKind 负责策略行为语义，不负责执行分支分发。
3. 旧字符串 subtype 最多只允许在兼容 adapter 中出现，不得作为执行层主判定条件。

#### 9.5.3 内核保留要求

1. 允许继续复用 BacktestEngine 核心撮合逻辑。
2. 允许继续复用 portfolio backtest 分支。
3. 但 BacktestEngine 的对外入口必须收口到强类型请求对象，不能长期保留 std::map<string,...> 入口作为主 API。

### 9.6 结果输出与展示系统

#### 9.6.1 功能需求

1. 回测完成后必须产出完整结果 DTO。
2. 展示层必须能直接消费结构化结果，而非先 JSON round-trip。
3. 结果中必须显式包含快照、绩效、交易、风险、时间序列、股票池摘要、规则摘要。

#### 9.6.2 合同要求

1. QML 不得再依赖 result.config 中的临时补写字段去反推业务逻辑。
2. 所有展示所需字段必须由结果 adapter 显式生成。
3. 所有快照语义必须分开：
   1. ruleProfileSnapshot
   2. executionPolicySnapshot
   3. backtestAssumptionsSnapshot
   4. strategyScopeContextSnapshot
   5. factorOverlaySnapshot

### 9.7 结果回写与策略绩效历史系统

#### 9.7.1 功能需求

1. 支持 latestBacktest 更新。
2. 支持 backtestHistory 追加。
3. 支持按覆盖策略决定是否替换当前基线股票池。

#### 9.7.2 结构要求

1. performance_metrics 必须定义明确 schema。
2. latestBacktest 与 backtestHistoryEntry 必须是同一结果快照对象类型。
3. runtimeParameters 必须是结构化快照，而不是临时拼接的散装 map。

#### 9.7.3 禁止事项

1. 不允许继续在 JS 里把大量数值转成字符串再回写为策略真实绩效字段。
2. 不允许继续通过历史回测记录去反向修补策略编辑态，除非进入显式恢复 adapter。

### 9.8 运行时规则与自动执行系统

#### 9.8.1 功能需求

1. 支持市场事件驱动的候选信号评估。
2. 支持模板规则门禁。
3. 支持自动下单请求构建与状态追踪。
4. 支持回测链与运行时规则链共享结构化快照。

#### 9.8.2 合同要求

1. runtime evaluator 输入必须是 RuntimeStrategyContext，而非原始 QVariantMap。
2. batch execution、price limit、return attribution、short selling mode 等必须来自结构化 execution/backtest snapshot。
3. strategyStatusAllowsSignals 这类行为必须只认强类型状态，不得读 status 文本。

### 9.9 规则模板系统

#### 9.9.1 功能需求

1. 支持模板绑定列表。
2. 支持从规则编排结构中提取模板绑定。
3. 支持运行时模板评估。

#### 9.9.2 抽象要求

1. 模板绑定必须定义成 RuleTemplateBinding 列表对象。
2. group、phase、operator、templateId、filePath 等字段必须有显式类型。
3. 禁止再用多个 map/list 形态混合表示同一绑定集合。

### 9.10 股票池与标的范围系统

#### 9.10.1 功能需求

1. 支持显式 symbol list。
2. 支持已保存股票池。
3. 支持关联自选池。
4. 支持指数成分股。
5. 支持股票池合并和去重。

#### 9.10.2 抽象要求

必须定义 UniverseSpec，至少包含：

1. universeMode
2. universeType
3. sourceId
4. explicitSymbols
5. resolvedSymbols
6. sourceSummary

#### 9.10.3 约束

1. symbol_pool、backtest_symbol_pool、linked_stock_pool_symbols 等字段不允许继续并行横飞。
2. 新系统必须给出统一 canonical 归属，并在 adapter 层吸收旧字段。

### 9.11 市场环境与风险配置系统

#### 9.11.1 功能需求

1. 回测与运行时规则必须共享同一 marketEnvironmentProfile 主合同。
2. executionPriceModel、returnAttributionMode、priceLimitMode、calendarProfile、costProfile 等必须由市场环境解析派生。

#### 9.11.2 约束

1. 不允许继续散落使用 useMarketOnClose、enableShortSelling 等字段承担混合语义。
2. 不允许 environment 配置和 gate 结果混淆。

### 9.12 缓存、诊断与可观测性系统

#### 9.12.1 功能需求

1. 回测缓存必须包含足够的配置维度，避免错误复用。
2. 运行时必须能输出策略、股票池、数据源、市场环境、执行分支、规则门禁、结果摘要等关键诊断信息。
3. 所有诊断信息必须来自强类型对象，而不是临时字符串拼接。

#### 9.12.2 约束

1. 缓存键必须纳入 executionKind、behaviorKind、marketEnvironmentProfile、universeSpec、factorOverlay 等核心维度。
2. 不允许不同市场环境、不同执行模式共用同一缓存键。

## 10. 非功能需求

### 10.1 可维护性

1. 任何核心语义的改动必须能通过类型系统定位到受影响模块。
2. 新增一个执行种类时，不应要求在十几个 QVariantMap 路径里同步找键名。

### 10.2 可扩展性

1. 新增 executionKind 应通过新增枚举值和分发器分支完成。
2. 新增结果字段应通过 DTO 扩展和 adapter 扩展完成。
3. 新增策略上下文结构不应要求继续在 parameters JSON 里塞更多散装键。

### 10.3 性能

1. 回测执行主路径不得因为抽象重构显著增加运行时开销。
2. 类型转换应尽量集中在入口与出口，避免执行循环内频繁 map/string 转换。
3. 结构化 DTO 构建应一次完成，不得在执行过程中反复解析同一结构。

### 10.4 易用性

1. 调用方必须能明确知道“创建策略”“运行回测”“回写结果”分别需要什么结构。
2. 错误消息必须能指出缺的是哪类合同，而不是泛泛报“参数错误”。

### 10.5 可测试性

1. 领域对象必须可独立单测。
2. adapter 层必须可独立验证旧字段归一化。
3. 回测请求组装必须可独立断言输出。
4. 结果回写必须可独立断言 latest/history/股票池基线行为。

## 11. 明确禁止的实现方式

以下做法在本次抽象重构中明令禁止：

1. 继续以 QVariantMap 作为 StrategyService、StrategyBacktestController、StrategyBacktestService 之间的主合同。
2. 新增更多字符串别名字段维持兼容。
3. 新写返回 QString 的“语义归一化 helper”去承载真实业务类型。
4. 继续让 strategy_type、sub_type、strategy_subtype 成为核心执行分发条件。
5. 同一语义在 top-level、parameters、result.config、runtimeParameters 中长期多点并存且无单一真源。
6. 在 QML 或 JS 中承担真实业务归一化和主数据装配职责。
7. 通过“先写入临时字符串键，后续层自己猜”来传递执行语义。

## 12. 迁移实施要求

### 12.1 总体策略

必须采用增量绞杀式重构，而不是一次性推倒所有系统。

推荐阶段如下：

1. 第一阶段：定义新 DTO 与枚举合同。
2. 第二阶段：建立 legacy adapter，把旧 map 吸收到新 DTO。
3. 第三阶段：让 service/controller 只操作新 DTO。
4. 第四阶段：让回测服务与引擎只消费新请求模型。
5. 第五阶段：让结果输出与回写只操作新结果模型。
6. 第六阶段：删除旧兼容字段和旧 helper。

### 12.2 阶段性交付件

每个阶段必须有明确交付件：

1. 领域模型头文件。
2. adapter 层实现。
3. 迁移说明文档。
4. 回归测试清单。
5. 删除旧字段清单。

### 12.3 数据迁移要求

1. 现有库存策略必须能够被明确迁移或明确拒绝。
2. 对历史回测结果的 latestBacktest / backtestHistory 必须定义兼容读取窗口。
3. 兼容窗口结束后必须删除旧读取逻辑。

### 12.4 目标模块拆分要求

抽象重构后的代码结构必须至少能按职责拆分成下面这些模块，允许命名不同，但职责边界必须等价：

1. strategy-domain
   1. 放策略身份、生命周期、运行属性、结构化快照、策略聚合根。
2. strategy-application
   1. 放创建、更新、删除、复制、归档、激活、停用、导入导出、缓存同步等应用服务。
3. strategy-persistence
   1. 放 StrategyRepository、数据库 DTO、schema adapter、迁移读取逻辑。
4. strategy-adapters
   1. 放 LegacyNormalizationAdapter、DisplayAdapter、PersistenceAdapter、BacktestRequestAdapter。
5. strategy-backtest-domain
   1. 放 BacktestRequest、UniverseSpec、ExecutionSpec、RiskSpec、CostSpec、BacktestResultDto。
6. strategy-backtest-application
   1. 放回测编排服务、任务管理、缓存协调、结果回写协调。
7. strategy-backtest-execution
   1. 放 BacktestEngine 入口适配、执行种类分发、portfolio 执行分支。
8. strategy-runtime-domain
   1. 放 RuntimeStrategyContext、RuntimeMarketContext、RuntimeEvaluationResult、自动下单请求对象。
9. strategy-runtime-application
   1. 放运行时规则评估编排、事件联动、订单跟踪与状态回放。
10. strategy-ui-bridge
   1. 放 QML bridge、展示 DTO、最薄 UI 适配接口。

要求：

1. 任一模块都不得直接同时承担“旧字段兼容 + 业务编排 + 持久化 + 展示适配”四种职责。
2. 任何 `QVariantMap` / `QVariantList` 只允许存在于 UI 层最外边界；application、domain、repository、execution、runtime 层一律不得把它们作为公开接口、成员字段或横向传递合同。

### 12.5 分阶段进出标准

每个阶段必须有明确的进入条件和退出条件，不允许无限期并行双模型。

#### 阶段一：领域模型建立

进入条件：

1. 已冻结当前主链的字段继续扩散。

退出条件：

1. StrategyAggregate、BacktestRequest、BacktestResultDto、RuntimeStrategyContext 等核心类型完成定义。
2. 关键 enum 和值对象完成定义。
3. 新模型的单元测试通过。

#### 阶段二：旧输入归一化接管

进入条件：

1. 新领域模型已可被独立实例化和校验。

退出条件：

1. QML/旧策略/旧结果产生的原始 QVariantMap 只允许停留在 UI bridge 最外层，离开 UI 层前必须被一次性转换为强类型对象。
2. StrategyService 和 StrategyBacktestController 不再直接多处读旧别名字段。

#### 阶段三：应用服务切换

进入条件：

1. 归一化 adapter 可稳定输出新 DTO。

退出条件：

1. StrategyService、StrategyBacktestController、StrategyRepository 主接口改为强类型对象。
2. 主链不再横向传 QVariantMap。

#### 阶段四：执行层切换

进入条件：

1. BacktestRequest 已稳定。

退出条件：

1. StrategyBacktestService 和 BacktestEngine 外部入口改为新请求模型。
2. executionKind 分发完成替换。
3. 不再由 strategy_type / strategy_subtype 决定核心执行路径。

#### 阶段五：结果链切换

进入条件：

1. BacktestResultDto 已稳定。

退出条件：

1. 结果展示、结果回写、历史记录管理全部使用新结果模型。
2. JS 侧不再承担主结果拼装职责。

#### 阶段六：旧字段退场

进入条件：

1. 新链已通过集成回归。

退出条件：

1. 旧 helper、旧别名、旧字符串主分发字段删除。
2. 文档、测试、迁移说明同步完成。

### 12.6 关键风险与控制要求

#### 风险一：新旧合同长期并存

表现：

1. 新 DTO 建出来了，但旧 QVariantMap 主链没删，系统复杂度翻倍。

控制要求：

1. 每个阶段必须有旧路径删除清单。
2. 不允许以“后面再删”为理由长期双写。

#### 风险二：执行内核被无谓重写

表现：

1. 因为装配层太乱，重构负责人顺手推倒 BacktestEngine，导致范围失控。

控制要求：

1. 先只改入口合同，不动撮合算法主循环。
2. 只有当新合同已稳定且内核接口确实阻塞演进时，才允许做第二阶段内核清理。

#### 风险三：结果链和编辑链再次耦合

表现：

1. 继续依赖 latestBacktest.runtimeParameters 去修策略编辑态。

控制要求：

1. 编辑态恢复必须走专门的恢复 adapter。
2. 结果快照不得继续兼任策略配置真源。

#### 风险四：兼容窗口无限延期

表现：

1. 所有人都知道旧字段该删，但没人敢删，最终 adapter 层又演化成新的兼容黑洞。

控制要求：

1. 每组旧字段必须标注退场阶段。
2. 每次版本发布都要同步缩小兼容范围。

## 16. 最终结论

当前系统不是“所有东西都要重写”，但已经明确进入“边界合同和装配层必须重建”的阶段。

本次需求规格说明要求后续抽象重构达成以下最终状态：

1. 保留已有可工作的执行内核与数据能力。
2. 重建策略主合同、回测请求主合同、回测结果主合同。
3. 清理字符串驱动的业务分发和多层动态 map 主链。
4. 建立清晰的领域模型、adapter、持久化模型和展示模型边界。
5. 通过增量替换方式完成系统收口，而不是继续在现有字符串兼容层上堆叠复杂度。

只有达到这个状态，后续策略系统、策略回测系统、运行时规则系统的继续演进，才会从“每改一次都怕炸”转成“可以按合同扩展”。
