## 术语表

| 术语                 | 定义                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------- |
| **执行种类**   | 明确区分回测、模拟交易、真实交易等执行模式及其子类型（如标准单策略、因子加权组合）的枚举 |
| **行为语义**   | 策略自身行为模式（如趋势跟踪、均值回归）的领域分类，不直接决定执行分支                   |
| **强类型合同** | 使用 enum、class、struct 定义的数据结构，禁止用 string/QVariantMap 承载核心语义          |
| **归一化**     | 将旧有杂散字段、别名字段、字符串枚举转换为统一的新强类型字段集合的过程                   |
| **单一真源**   | 任一业务语义在系统中只能有一个字段/表示，其余为派生或展示                                |
| **快照**       | 对策略某一时刻完整配置结构的不可变记录，用于回测结果、审计和恢复                         |
| **策略上下文** | 策略执行时所需的全部配置快照集合（规则、执行、市场环境等）                               |
| **adapter**    | 专门负责在不同模型或协议间进行转换的模块，不包含业务逻辑                                 |
| **legacy**     | 指重构前以字符串、QVariantMap 为主的旧实现方式与数据结构                                 |

## 1. 文档目的

本文是抽象重构项目的正式需求规格说明书，用于：

1. 明确当前系统结构性债务的具体形态与位置。
2. 定义重构后的目标架构分层、领域模型、接口约束与验收条件。
3. 提供可执行的阶段化迁移方案及风险控制措施。
4. 确保所有参与方（架构、开发、测试、产品）对重构边界和预期成果达成一致。

本文不是实现方案草稿，不描述具体代码细节，而是给出“必须满足什么”以及“禁止做什么”。

## 3. 背景与现状结论

### 3.1 背景

系统在持续功能叠加中形成，长期依赖 QVariantMap 跨层传递、字符串键承载语义、多别名字段兼容、多层混合吸收转换逻辑，导致维护成本极高，扩展风险大。

### 3.2 当前核心判断

- 核心执行内核（撮合、绩效计算）仍具保留价值。
- 装配层、服务边界、持久化合同已经失控，必须通过抽象重构重建结构。

### 3.3 主要结构性债务（合并原3.3与原第11章）

#### 3.3.1 动态 map 作为主合同

- 类型约束弱，编译期无保护。
- 调用方依赖约定俗成的字符串键，容易误拼、缺失。
- 批量重构时无法安全定位。

#### 3.3.2 字符串键承载业务语义

- `strategy_type`、`sub_type`、`backtest_runtime` 等字符串用于核心分发。
- 多个并行字段（如 `symbol_pool`、`backtest_symbol_pool`）同时存在。
- 旧字段名与新字段名双读，兼容逻辑分散。

#### 3.3.3 多层吸收兼容逻辑

兼容代码散落在 QML、StrategyService、Controller、Resolver、ResultBuilder、Repository，导致：

- 同一语义被重复归一化。
- 修改点难以确定，回归风险高。

#### 3.3.4 研究语义与执行语义混用

同一结构同时承载页面展示、策略保存、回测执行、运行时快照、结果回写等多重职责，复杂度叠加。

#### 3.3.5 结果回写链仍为动态拼装

JS 构建 payload → service 合并 map → repository 写 JSON → 读取时再反向解析，缺乏结构化 schema。

## 5. 目标重构原则

1. **强类型优先**：领域语义必须使用 enum/struct/class，字符串仅用于序列化边界或展示文案。
2. **单一真源**：同一语义只保留一个 canonical 字段；兼容读取集中在单一 adapter。
3. **边界清晰**：明确定义 UI 展示模型、应用输入/输出模型、领域模型、执行模型、持久化模型。
4. **失败显式化**：关键信息缺失时直接失败并报告具体缺失项，禁止隐式默认值回退。
5. **增量绞杀**：保留可工作的执行内核，通过新类型合同逐步替换旧 map/string 链路，不进行“大爆炸”式重写。

## 7. 目标系统分层要求

系统必须严格分为七层，各层职责与约束如下：

1. **展示层 (QML/JS)**
   - 只收集用户输入、显示结果，不承担业务逻辑或归一化。
   - 不得保存带业务语义的字符串状态，不构造散装 map。
2. **展示适配层 (Bridge Adapter)**
   - 完成 QML DTO ↔ 应用层 DTO 的单向转换，吸收 UI 兼容差异。
   - 所有旧字段兼容集中于此，不得向 service/controller 扩散。
3. **应用服务层 (Application Service)**
   - 编排调用、事务组织、缓存协调、事件通知。
   - 操作强类型请求/结果对象，禁止内部横向传递 QVariantMap。
4. **领域模型层 (Domain Model)**
   - 定义策略、回测、规则、股票池等核心实体与值对象，提供显式校验。
5. **装配与转换层 (Assembly/Adapter)**
   - 负责旧结构→领域模型、领域模型→执行模型/展示模型的转换，集中吸收别名。
6. **执行层 (Execution)**
   - 仅消费强类型配置对象，执行回测、规则评估、绩效计算。
   - 不依赖任何 QML 键名或数据库字段名。
7. **持久化层 (Persistence)**
   - 提供强类型仓储接口，隔离数据库文本字段与业务逻辑。

> **硬性约束**：QVariantMap/QVariantList 仅允许出现在展示层边界（Bridge 输入输出）；在 application、domain、repository、execution 层作为接口参数或成员字段均视为违规。

## 8. 目标领域模型需求

### 8.1 策略聚合根 (StrategyAggregate)

必须包含强类型字段（示例）：

- 标识：`id`, `code`, `name`
- 身份枚举：`storedType`, `behaviorKind`, `executionKind`
- 生命周期枚举：`status`
- 运行属性：`assetTypeIndex`, `timeFrameIndex`, `riskLevelIndex`
- 结构化快照：`ruleProfile`, `executionPolicy`, `backtestAssumptions`, `strategyScopeContext`, `factorOverlay`
- 绩效摘要：`performanceSummary`（强类型）
- 回测历史：`latestBacktestSnapshot`, `backtestHistory`
- 元信息：`description`, `version`, `author`, `createdAt`, `updatedAt`

### 8.2 回测请求 (BacktestRequest)

结构化子对象：

- `StrategyIdentity`
- `UniverseSpec`
- `ExecutionSpec`
- `RiskSpec`
- `CostSpec`
- `FactorOverlaySpec`
- `RuntimeOptions`

禁止使用 `strategyParams` / `strategyOptions` 字符串 map 作为主合同。

### 8.3 回测结果 (BacktestResultDto)

- 配置快照
- 绩效摘要（结构化字段，非 map）
- 交易统计、风险指标
- 时间序列、交易记录
- 标的池解析摘要、规则模板摘要
- 诊断信息

不得以 JSON→QVariantMap 作为主输出模型。

### 8.4 运行时模型

- `RuntimeStrategyContext`
- `RuntimeMarketContext`
- `RuntimeEvaluationResult`
- `AutoOrderRequest`（强类型）

运行时输入必须来自强类型快照，禁止读取散装 map。

## 9. 各子系统详细需求

### 9.1 策略定义与生命周期

- **状态管理**：使用统一枚举（如 `StrategyStatus`），禁止通过 `strategy.value("status")` 文本判断。
- **操作**：创建、更新、复制、删除、归档、激活、停用，均通过应用服务调用，需校验状态机。
- **禁止**：同时保留 `status` 和 `statusIndex` 两个业务真源；若数据库存 int，只在持久化层转换。

### 9.2 策略仓储与持久化

- **仓储接口**：以 `StrategyData` 强类型 DTO 为主合同，方法签名不使用 QVariantMap。
- **数据库字段**：`parameters` 仍可为 TEXT/JSON，但必须在仓储层进行结构化校验和转换；`performance_metrics` 必须有明确 schema，禁止随意增量 merge。
- **数据迁移**：旧策略 `parameters` 中的兼容字段通过单一 `LegacyPersistenceAdapter` 读取，新策略只写新结构。无法自动迁移的旧数据标记为“需手动修复”状态，不在后台静默丢弃。

### 9.3 策略装配与结构解析

- **拆分职责**：`LegacyNormalizationAdapter` 负责旧字段名吸收与归一化；`StrategyStructureAssembler` 负责基于已归一化数据构建 canonical 快照。
- **输入限制**：assembler 只能接收已归一化对象，禁止直接消费原始 QML map。

### 9.4 回测请求装配

- `createConfig` 必须拆分为 `buildIdentitySpec`, `buildUniverseSpec`, `buildExecutionSpec` 等独立子构造器。
- 缺失执行种类、股票池为空、权重配置不完整等必须立即返回错误并指明缺失项。

### 9.5 回测执行

- 分发器依据 `executionKind` 枚举，不再依赖 `strategy_type` 字符串。
- `BacktestEngine` 入口改造为接收 `BacktestRequest` 强类型对象，内部可保留原有撮合循环，但新公开接口必须是类型化的。
- 绩效计算器同样遵循类型化输入。

### 9.6 结果输出与展示

- QML 接收的展示模型应由 `BacktestResultDisplayAdapter` 生成，不依赖 result 中的补写字段反推业务。
- 快照明确分为：`ruleProfileSnapshot`, `executionPolicySnapshot` 等子对象。

### 9.7 结果回写与绩效历史

- `performance_metrics` 必须使用结构化对象，序列化时保证 schema 一致。
- `latestBacktest` 与 `backtestHistory` 条目类型统一。
- 禁止在 JS 中将数值转字符串回写策略绩效字段；数值类型必须保持原生类型直到持久化边界。
- 策略编辑态恢复走专门 `StrategyRecoveryAdapter`，不直接从历史回测 `runtimeParameters` 修复。

### 9.8 运行时规则与自动下单

- 评估器输入为 `RuntimeStrategyContext` 强类型。
- `strategyStatusAllowsSignals` 只认状态枚举。
- 自动下单请求为 `AutoOrderRequest`，再由 bridge 适配给交易接口。

### 9.9 规则模板绑定

- 模板绑定定义为 `RuleTemplateBinding` 列表，包含 `templateId`, `group`, `phase`, `operator` 等显式类型字段。
- 禁止用多种 map/list 形态混合同一绑定集合。

### 9.10 股票池与标的范围

- 定义 `UniverseSpec`，包含 `universeMode`, `explicitSymbols`, `resolvedSymbols` 等。
- 旧有 `symbol_pool`, `backtest_symbol_pool` 等字段统一在 adapter 层归入 `UniverseSpec`，内部不再并行使用。

### 9.11 市场环境与风险配置

- 回测与运行时共用 `MarketEnvironmentProfile`。
- `executionPriceModel`, `returnAttributionMode` 等从其派生，禁止散落使用 `useMarketOnClose` 等混合语义字段。

### 9.12 缓存、诊断与可观测性

- 缓存键必须包含 `executionKind`, `behaviorKind`, `universeSpec.hash`, `marketEnvironmentProfile.hash` 等核心维度，防止错误复用。
- 所有诊断日志基于强类型对象的格式化输出，不依赖临时字符串拼接。

## 10. 非功能需求

### 10.1 可维护性

- 通过类型系统即可定位受影响模块，不允许依赖全局文本搜索。

### 10.2 可扩展性

- 新增 `executionKind` 只需增加枚举值和对应 handler，无需修改 map 解析路径。
- 新增结果字段通过 DTO 扩展完成。

### 10.3 性能

- 回测全链路因类型转换引入的总耗时增量不得超过 **5%**（基准为当前主链相同策略 100 次回测中位数）。
- 执行循环内禁止出现字符串比较、map 查找等操作，所有结构解析在请求入口一次完成。
- 结构化 DTO 在入口构建后，执行过程中不可发生二次解析。

### 10.4 易用性

- 调用方可根据类型定义明确知晓“创建策略”、“运行回测”、“回写结果”所需结构，错误消息指出缺失何种合同（如“缺少 UniverseSpec”）。

### 10.5 可测试性

- 领域对象可独立实例化并校验。
- adapter 转换可独立输入/输出断言。
- 回测请求组装、结果回写均可进行独立单元测试。

## 11. 明确禁止的实现方式（禁则清单）

1. 在 application/domain/repository/execution 层使用 QVariantMap/QVariantList 作为主合同或成员字段。
2. 新增任何字符串别名字段以维持兼容。
3. 编写返回 QString 的“语义归一化 helper”作为业务分支判断依据。
4. 继续以 `strategy_type`, `sub_type`, `strategy_subtype` 文本作为执行分发或核心状态判断条件。
5. 同一业务语义在 top-level、`parameters`、`result.config`、`runtimeParameters` 中长期多点并存且无单一真源。
6. 在 QML/JS 中承担真实业务归一化和主数据装配职责。
7. 通过先写入临时字符串键再让下游猜测的隐式契约传递执行语义。
8. 保留 `Normalized` 或 `Normalization` 命名的中间兼容模型来承接旧字段，归一化必须在边界一次性完成。

各子系统小节不再重复列举，若出现疑义以本章为准。

## 12. 迁移实施要求

### 12.1 总体策略

采用六阶段增量绞杀式重构，每阶段有明确进出条件、交付件和旧路径删除清单。双模型并行仅限同一阶段窗口，期满后旧模型必须删除。

### 12.2 分阶段交付与进出标准

**阶段一：领域模型建立**

- 进入：已冻结主链字段扩散。
- 退出：所有核心 DTO、枚举定义完成并通过单元测试。
- 交付：领域模型头文件、单元测试套件。

**阶段二：旧输入归一化接管**

- 进入：新领域模型可实例化校验。
- 退出：离开 UI 边界的数据全部转换为强类型对象；service/controller 中不再直接读取旧别名。
- 交付：`LegacyNormalizationAdapter` 实现、相关模块改写代码。
- 涉及文件（示例）：`StrategyService.cpp`, `StrategyBacktestController.cpp` 中 `QVariantMap` 消费点。

**阶段三：应用服务切换**

- 进入：adapter 稳定输出新 DTO。
- 退出：`StrategyService`, `StrategyBacktestController`, `StrategyRepository` 主接口改为强类型，内部无 QVariantMap 横向传递。
- 交付：改造后的服务与仓储接口。
- 涉及文件：上述服务头文件、仓储接口。

**阶段四：执行层切换**

- 进入：`BacktestRequest` 稳定。
- 退出：`StrategyBacktestService` 和 `BacktestEngine` 新入口使用强类型；分发器使用 `executionKind` 枚举；旧字符串分发逻辑移除。
- 额外验证：对比同一策略重构前后 100 次回测的每日净值，偏差需在 1e-6 以内。
- 交付：执行层入口代码。

**阶段五：结果链切换**

- 进入：`BacktestResultDto` 稳定。
- 退出：结果展示、回写、历史管理全部基于新结果模型；JS 侧不再拼装主结果。
- 交付：`BacktestResultDisplayAdapter`，更新后的结果回写逻辑。

**阶段六：旧字段退场**

- 进入：全链路集成回归通过。
- 退出：所有旧 helper、别名、字符串分发字段删除；数据库兼容读取窗口关闭；文档与测试同步更新。
- 退场验证：全代码库 grep 确认核心层不存在 `strategy_type` 字符串比较、旧字段名等；新创建的策略在数据库中不包含废弃字段。

### 12.3 数据迁移方案

- 提供一次性迁移脚本，将现有策略的 `parameters` 中可识别字段转换到新结构。
- 无法自动迁移的策略设为“挂起”状态，并在管理界面提示用户手动修复。
- 历史回测结果兼容读取窗口维持两个版本周期，之后移除旧解析逻辑。

### 12.4 目标模块拆分

重构后代码必须按以下边界拆分，允许命名不同但职责等价：

1. `strategy-domain`
2. `strategy-application`
3. `strategy-persistence`
4. `strategy-adapters`（含 LegacyNormalizationAdapter, DisplayAdapter, PersistenceAdapter）
5. `strategy-backtest-domain`
6. `strategy-backtest-application`
7. `strategy-backtest-execution`
8. `strategy-runtime-domain`
9. `strategy-runtime-application`
10. `strategy-ui-bridge`

## 13. 风险控制

### 13.1 新旧合同长期并存

- 每个阶段必须列出旧路径删除清单，在阶段退出时完成清理。
- 不得以“后续再删”为由保留双写。

### 13.2 执行内核被无谓重写

- 严格控制范围：先只改入口合同，不动撮合算法主循环。
- 阶段四引入净值回归对比，防止意外逻辑变更。

### 13.3 结果链与编辑链再次耦合

- 编辑态恢复必须使用 `StrategyRecoveryAdapter`，严禁结果快照兼任策略配置真源。

### 13.4 兼容窗口无限延期

- 每组旧字段标注计划退场阶段，版本发布评审时检查兼容范围是否按计划缩小。
- 提供 feature flag 或编译开关，支持新老链路并行验证和快速回退。

### 13.5 回退策略

- 每个阶段在发布时保留旧代码路径于独立编译单元或通过运行时开关控制，一旦集成环境出现重大回归，可通过配置切回旧链路。
- 阶段六完成后，旧代码路径彻底删除。

## 14. 测试与验收要求

### 14.1 单元测试覆盖

- 所有领域对象校验、adapter 转换、UniverseSpec 解析、RuleTemplateBinding 解析、结果 DTO 转展示 DTO。
- LegacyNormalizationAdapter 针对已知旧格式的转换测试。

### 14.2 集成测试闭环

- 策略创建→保存→读取→编辑→再保存。
- 标准策略回测全流程。
- 组合因子加权回测全流程。
- 回测结果回写策略。
- 运行时规则评估与自动下单请求构造。

### 14.3 回归测试

- 策略 identity roundtrip、运行时三元组 roundtrip。
- executionKind 显式分发、marketEnvironmentProfile 对齐。
- result 快照真实结构验证。

### 14.4 验收标准（可检验）

1. 核心层代码（application, domain, repository, execution）头文件无 `QVariantMap`/`QVariantList` 参数或成员。
2. 新增 `executionKind` 枚举时，通过遍历枚举值的测试确保分发器全覆盖，无 fallback 到字符串逻辑。
3. 回测结果 JSON schema 与 `BacktestResultDto` 序列化一致，不包含 legacy 散装键。
4. 批量运行 20 个不同历史策略回测，全链路时间增量 < 5%，净值偏差 < 1e-6。
5. 所有旧字段名（如 `strategy_type` 字符串比较、旧别名）通过静态脚本扫描确认已从核心层移除。
6. 仓储接口不接受 `QVariantMap`，仓储方法调用均在编译期通过类型检查。

## 15. 补充要求

### 15.1 数据库 schema 适配

- `parameters` 字段继续使用 TEXT/JSON，但在仓储层进行反序列化时强制校验 schema，不合规的记录转为“待迁移”状态。
- `performance_metrics` 列也对应强类型序列化，仓储层必须保证写入和读取的结构一致性。

### 15.2 UI 交互行为调整

- 策略编辑页面应使用枚举下拉框、结构化输入组件，不再使用自由文本字段拼接策略类型。
- 回测参数面板应直接映射到 `BacktestRequest` 的子结构，提交时由 bridge 组装为强类型对象。

### 15.3 测试数据

- 需准备包含至少 50 个不同时期、不同类型、不同复杂度的历史策略数据集（脱敏），覆盖所有已知别名和缺失字段边界情况。
- 其中 10 个为无法自动迁移的破损策略，用于验证拒绝处理逻辑。

### 15.4 交付物

除代码外，每个阶段必须交付：

- 旧字段删除清单及影响范围
- 测试用例与报告
- 迁移操作手册（含数据备份与回滚说明）

## 16. 最终结论

本需求规格明确要求在不重写执行内核的前提下，通过强类型领域模型、清晰的分层架构和严格的适配器隔离，彻底消除字符串驱动的业务分发与动态 map 主链。

重构完成后，系统应达到：

- 核心业务路径类型安全、编译期可校验。
- 新增功能修改点可控、可枚举、可测试。
- 旧兼容逻辑收敛于边界 adapter，不再扩散。
- 历史策略数据可平滑迁移或明确拒绝，不再维持双语义并行。

任何偏离本规格的设计或实现，均视为未满足需求。
